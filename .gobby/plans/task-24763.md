# Restore Operator-Launched Panes And CLI Sessions After A Reboot

## Overview
`kind: framing`

Task #24763 (Restore operator-launched panes and CLI sessions after a reboot), under
epic #24821 (Terminal and client). Planning task #25414. The scope is full state resume
after a system crash: all panes survive a machine restart, all agents, including
operator-activated agents, resume in their CLIs, and they stay quiet until the operator
or an authorized seat sends a targeted wake (Decision Record item 14). The plan expands
as a sub-epic under #24821.

A machine reboot kills the gterm host and every process in it. Today the daemon then
forgets the operator's work:

1. Startup reconciliation marks each prior-epoch terminal `orphaned`, and the next
   health-loop pass marks it `exited`
   (`src/gobby/terminals/host_reconcile.py:383-389`).
2. The first workspace read sweeps every pane whose terminal is `exited` and drops tabs
   left empty (`src/gobby/storage/workspaces.py:889-955`). The committed test
   `tests/terminals/test_reboot_pane_preservation.py` carries a strict xfail on exactly
   this case.
3. Nothing relaunches an operator's shell or the provider CLI the operator typed into
   it, and nothing records where that shell ran.
4. A session that was mid-turn at the reboot expires as ownerless with no drain marker
   (`src/gobby/storage/sessions/_field_update.py:261-297`), so its task claims are
   released as if the operator had closed it.
5. Task-owned managed seats parked by the daemon stop are never relaunched; they wait
   24 hours for the reaper, which releases their claims.
6. A relaunched CLI would start work unattended. The managed resume prompt, DAEMON
   BACK, wake replay, durable wait timeouts and idle reprompts all reach it with nobody
   having decided that it should run.

The plan delivers:

1. Durable facts: the terminal's process record keeps its spawn folder and a
   `host_lost` flag set when the host loses it, and the session records the approval
   posture its CLI launched with.
2. Panes whose terminal the host lost survive the sweep until restored or closed.
3. At daemon start, each operator pane gets a new shell in the same pane row. If its
   provider session can resume natively, the shell runs the provider's resume
   command. Otherwise it prints one line naming the reason and the exact resume
   command. A pane whose CLI had already ended before the reboot comes back as the
   plain shell it was.
4. Managed seats refill their own pane in place, and parked task-owned seats are
   relaunched.
5. Every CLI restored after host loss waits under a hold. The operator's typing, an
   operator comms wake, or a targeted wake from a definition the project YAML lists
   releases it.
6. gclient draws a pane with no live terminal as an explained pane instead of a blank
   slot.

## Decision Record
`kind: framing`

1. **Retained history is the session and transcript (Option A).** Orchestrator
   ruling (gobby#17281, 2026-10-31) on the Plan Writer's request: the session row and
   its transcript are never deleted or archived. A restored pane that cannot resume
   prints one line naming the reason and the exact resume command. Gterm scrollback is
   not persisted across a reboot. Option B (on-disk gterm scrollback snapshots) was
   rejected: it adds a large Rust persistence layer and writes terminal text, which can
   hold secrets, to disk. `gterm-handover.json` survives only exec upgrades, not a
   reboot (`crates/gterminal/src/host/handover.rs`). Josh approves the stamped plan before
   expansion.
2. **Host loss is a flag on the terminal's process record.**
   `TerminalSettlementMixin.mark_orphaned` (`src/gobby/storage/terminal_settlement.py:428-430`)
   is the only `live` to `orphaned` writer, and its docstring scopes it to host-epoch or
   host-crash loss. It merges `{"host_lost": true}` into `terminals.process`. Key merges
   (`merge_process_reap_record`, `record_orphan_identity`) keep keys outside
   `HOST_PROCESS_KEYS`, so the flag survives `orphaned` to `exited`. `mark_kill_failed`
   also writes `orphaned` but is not host loss, so it sets no flag. Rejected: a new
   `terminals` column, which needs a migration, five derived schema carriers and crate
   bumps for one boolean. Also rejected: comparing host epochs alone, which cannot tell a
   shell the operator exited before the reboot from one the reboot killed.
3. **The spawn folder is recorded in the same process record.** `spawn_web_terminal`
   (`src/gobby/terminals/web_spawn.py:186-197`) already writes
   `{host_terminal_id, shell, pgid, start_time}`; it adds `cwd`. A pane keeps pointing
   at its last terminal until it is rebound, so that terminal row is the pane's
   last spawn folder. Rejected: a `workspace_panes.cwd` migration, for the same carrier
   cost. Also rejected: deriving the folder from the tab's project and worktree, because
   operator personal-project panes carry an explicit folder stored nowhere else
   (`src/gobby/terminals/workspace_pane_access.py:69-117`).
4. **Operator panes restore through a new sibling path, not managed resume.**
   `launch_resume` and its `_preflight` (`src/gobby/agents/resume_placement.py:77-236`)
   require a pane reserver, a managed SRT sandbox and a parent session.
   `prepare_terminal_resume(relaunch=True)` overwrites `parent_session_id`, which would
   turn a root into a child. Roots stay roots: the new module
   `src/gobby/terminals/pane_restore.py` spawns into the existing pane row.
5. **Which provider sessions resume.** A reboot leaves the pane's last terminal row
   bound to its session. `TerminalManager.release_session`
   (`src/gobby/storage/terminals.py:756-772`) unbinds only a `pending` or `live` row,
   on `SessionEnd` (`src/gobby/hooks/event_handlers/_session_end.py:251`) or a liveness
   expiry (`src/gobby/sessions/liveness_monitor.py:442`), and the reboot leaves the row
   `orphaned`. A CLI ended before the reboot was unbound then. Its pane was already a
   plain shell, so it restores as one, with no line. Rejected: looking up the pane's
   last session through `terminal_context` to explain it, which adds a lookup for a
   pane the operator had already returned to a shell. The bound session resumes only
   when all of these hold:
   - its `agent_run_id` is null;
   - its source is in `SUPPORTED_RESUME_PROVIDERS`
     (`src/gobby/agents/resume_executor.py:79`);
   - it has a native thread id (the rule in `resolve_resume_target`,
     `src/gobby/mcp_proxy/tools/spawn_agent/_resume.py:58-113`);
   - its status is in `LIVE_SESSION_STATUSES`, or it is `expired` carrying the
     `terminal_drain` contested-expiry marker;
   - no `pending` or `live` terminal is bound to it.

   A `SessionEnd` expiry writes no marker (`src/gobby/hooks/event_handlers/_session_end.py:101-103`),
   so a deliberately ended session that is still bound stays closed and its pane prints
   the reason line. The exception is a `SessionEnd` caused by the host's death (item 9).
   `completed`, `cancelled`, `closed` and `deleted` stay closed. The 24-hour revival horizon clears session variables, marker
   included, so a stale seat stays closed.
6. **The restore command is one `zsh -i -c` script.** The pane's shell is
   `PANE_SHELL_COMMAND = ("zsh",)` (`src/gobby/terminals/workspace_ops.py:85`). The
   restored command is `("zsh", "-i", "-c", script)`. A resuming pane's script runs
   `cd <folder> && <resume argv>`, keeps its exit status, and on a nonzero status prints one
   `gobby:` line with that status and the exact quoted manual resume command. A clean exit
   prints nothing. Any other pane's script is `printf '%s\n' <reason line>`. Both end with
   `exec zsh -i`. Every value is quoted with `shlex.quote`, argv with `shlex.join`.
   `-i` sources the operator's `.zshrc`, so the provider binary resolves on the
   operator's own PATH, and the pane ends in an ordinary interactive shell. A resume the
   provider rejects would otherwise reach a plain prompt with no reason, which criterion 3
   forbids. Rejected: typing the command into a fresh shell's PTY, which has no prompt-ready
   signal and races typeahead handling.
7. **Provider argv comes from `build_cli_command` with the recorded approval posture.**
   `src/gobby/agents/spawners/command_builder.py::build_cli_command` with
   `resume_session_id=<thread>`, `model` and `reasoning_effort` from the session,
   `auto_approve=terminal_context.get("launch_auto_approve") is True` (item 16), no
   prompt, no working directory, and a fixed mode per provider:
   claude `agent` (`claude --resume <id>`; `interactive` would add stream-json I/O),
   codex `agent` (`codex resume … <id>`), grok `terminal` (`--resume <id>` without
   `--single`), droid `interactive` (`droid --resume <id>`), agy `interactive`
   (`agy --conversation <id>`). The env dict it returns is discarded. The restored shell
   gets only the pane identity env. A restored CLI never runs with more authority than it
   launched with. Codex's non-headless flags are `--ask-for-approval never --disable
   guardian_approval` (`command_builder.py:155`), so a CLI launched with the full bypass
   comes back lower. Droid's `interactive` mode emits no approval flag
   (`command_builder.py:185`), so a restored droid asks for approvals.
8. **Managed seats refill their own pane in place.** A new placement kind,
   `{"pane": {"pane": <pane id>, "title": <title>}}`, binds a new terminal into an
   existing pane whose terminal is proven dead (item 13). Both managed resume routes
   use it first when the previous run's pane still exists: `_preflight` for automatic
   daemon-stop recovery and `resumed_seat_plan` for `spawn_agent(resume_session_id=…)`.
   Rejected: today's split beside the dead pane, which relies on the sweep to collapse
   the old pane. It changes the pane id, and once the sweep keeps host-lost panes it
   would leave a ghost pane beside the successor.
9. **Sessions active at the reboot are shielded like paused ones.** When the
   session's bound native terminal carries `host_lost`, `expire_if_active` records the
   `terminal_drain` marker in the same transaction as the expiry. This is the guarantee
   `expire_if_paused_terminal_exited` already gives paused sessions (`_field_update.py:299-370`).
   `rebind_resumed_terminal_session` (`src/gobby/storage/sessions/_terminal.py:217-288`)
   sets the session `active` with direct SQL and skips `update_status`'s rule that a
   status change clears the marker (`_field_update.py:62-80`). It now clears it too, so
   a resumed seat's marker cannot shield a later final expiry. A provider may fire
   `SessionEnd` when its host dies. Codex installs it enqueue-only. On a drain, HTTP
   admission closes (`src/gobby/runner_lifecycle_shutdown.py:725`) before the host stops
   (742-752), so the hook lands in the inbox the way it does on a reboot. The inbox
   replays it after the restart, inside `agent_run_reconciliation`
   (`src/gobby/runner_lifecycle_reconcile.py:431-445`), after host reconcile has set
   `host_lost`. A `SessionEnd` expiry therefore gets the same rule only for the generic
   reasons `other` and `exit` (Grok's `shutdown` maps to `exit`,
   `src/gobby/hooks/hook_types/enums.py:155-191`). `prompt_input_exit`, `logout`,
   `clear`, `resume` and `idle` are explicit closes and stay closed through replay.
   The operator ruled that `exit` stays in the generic set (V1).
10. **Parked task-owned seats are relaunched by the existing retry loop.** The query
    behind `_retry_parked_non_task_resumes` (`src/gobby/runner_lifecycle_agents.py:340-401`)
    admits `task_id IS NULL` only. The comment that task-owned runs "ride the dispatch
    tick" is stale: fe8e05f7c7 (#23851) retired the dispatcher, leaving
    `list_daemon_stop_resume_candidates` (`src/gobby/storage/agents/_queries.py:114-146`)
    with no production caller. The candidate query now also admits task-owned runs
    whose task is not closed. A run whose task is closed is refused with
    `refuse_parked_daemon_resume` (`src/gobby/storage/agent_resume.py:79-125`), which
    hands it to the reaper. A Dev Manager's manual resume and the automatic retry
    cannot both win, because consuming a parked run takes the resume fence
    (`_lock_resume_fence`, `agent_resume.py:68-72`). The dead query is deleted.
11. **Restore runs once per daemon start.** It is a startup phase, `pane_restore`, in
    `_recover_after_restart` (`src/gobby/runner_lifecycle_subsystems.py:643-757`),
    after `agent_run_reconciliation`. It is machine-local, so it also runs in node mode.
    A gterm host crash while the daemon stays up is not restored until the next daemon
    start. Its panes stay, explained, until then or until the operator closes them.
12. **gclient explains a slot with no live terminal.** `render_panes`
    (`crates/gclient/src/ui/panes.rs:73-173`) skips a layout slot whose terminal it
    cannot resolve, leaving it blank. It now draws a one-line note there. Rejected:
    keeping exited terminals attached in the client, which would change the client's
    terminal lifecycle for every exit, not just host loss.
13. **A pane is refilled only when its terminal is proven dead, under an exclusive
    claim.** `orphaned` is unresolved ownership. `mark_kill_failed`
    (`src/gobby/storage/terminal_settlement.py:375-426`) writes it after an unproven
    kill, and `handle_host_death` (`src/gobby/terminals/host_manager.py:476-496`) writes
    it with `host_lost` in the current host epoch. The proof is the one reconcile
    already settles on (`src/gobby/terminals/host_reconcile.py:385-390`): `exited`, or
    `orphaned` from a host epoch other than the live one with
    `recorded_process_group_is_alive` false. A refill claims the pane in one transaction.
    `WorkspaceManager._guard` (`src/gobby/storage/workspaces.py:957-986`) locks the pane
    row, refuses an in-flight pane or an in-doubt terminal, and checks that the pane
    still points at the old terminal. The pane is then marked in flight. The bind
    updates the pane only while it still points at that old terminal. Operator restore
    and managed refill share these rules.
14. **Scope is the operator's statement.** Josh, relayed by the Orchestrator
    (gobby#19309): "It's just a full state resume after a system crash." "By state resume
    I just mean that all panes survive machine restarts and all agents, including
    operator-activated agents, resume in their CLIs. When the Assistant or Operator are
    activated the Operator can send targeted wakes to the crew (or give to the recovery
    manager, do you have one spawned?) if it has authorization to in the project YAML."
    The Orchestrator reads this as: wakes are targeted, authorized by project YAML, and
    sent by the activated Orchestrator or handed to the Recovery Steward. "Plan crew can
    start on 24763, we can expand into the gclient epic as a sub-epic."
15. **Pane details are captured at session registration, which already records almost
    all of them.** Josh's idea, offered as an idea and not a fixed design: "record the
    details we're recording when we start an agent run", on first user prompt or at
    session registration. The code supports registration, and it shows that one fact is
    missing. A fresh startup defers row creation to the first materializing activity
    event (`src/gobby/hooks/session_lookup.py`,
    `src/gobby/hooks/session_materialize.py::activate_deferred_session`), so first prompt
    and registration are the same moment there. A first-prompt hook alone would miss
    resume and compact starts, which register through
    `src/gobby/hooks/event_handlers/_session_start/flow.py`. A CLI with no row at the crash
    has no conversation to resume and restores as a shell. Registration already records
    the folder (`register_session` writes `workspace_path` from the hook cwd,
    `_session_start/flow.py:453`, `src/gobby/storage/sessions/_crud.py:246,381`), the
    terminal, pane and process identity (`terminal_context`), and the external id, source
    and transcript path. Model and reasoning effort follow from hooks. Only the approval
    posture is missing (item 16). Rejected: copying `placement_snapshot`
    (`src/gobby/agents/resume_placement.py:33-47`) onto a root, because it goes stale when
    the operator rearranges, and the pane row is the live authority. Also rejected:
    `build_resume_metadata` (`src/gobby/agents/resume_metadata.py:121-199`), which requires
    a parent session and hardcodes auto-approve.
16. **Approval posture is one recorded boolean (R1, Josh's ruling).**
    At registration, derive `terminal_context.launch_auto_approve` from the
    argv of the CLI process the hook already inspects, and persist only the boolean, never
    argv. It is true when an argv element equals `--dangerously-skip-permissions` (claude,
    agy), `--dangerously-bypass-approvals-and-sandbox` (codex) or `--always-approve` (grok),
    or the pair `--ask-for-approval never` appears (codex). These are the flags
    `build_cli_command` itself emits. Anything else, including an unreadable process, a
    settings file or another flag spelling, leaves the key absent or false, and absent
    means off. Without this, a bypass-mode seat returns blocked on approval prompts,
    which defeats full state resume. Rejected: the hook payload's `permission_mode`
    (`src/gobby/hooks/hook_types/session.py:52`), which only Claude-style hooks carry. This
    restores authority, so 1.4 takes a security review.
17. **One session-level hold, `restart_wake_hold`, keeps restored CLIs quiet.** Five
    unattended sources reach a restored CLI: the managed resume prompt
    (`src/gobby/agents/resume_executor.py:237-241`), DAEMON BACK
    (`src/gobby/sessions/daemon_notices.py:39-79`, global fanout), `WakeReplayCoordinator`
    (`src/gobby/events/wake_recovery.py`, replays undelivered `wake_requested` rows at
    startup and on each status transition), durable wait timeouts
    (`src/gobby/storage/coordination_waits.py:175-189`) and idle reprompts
    (`src/gobby/agents/idle_check_handler.py::IdleCheckHandler._handle_idle_check`).
    Rejected: suppressing each source, which spreads one decision over five owners and
    misses the next source. Four of the five pass through
    `WakeDispatcher._preflight_live_side_effect`
    (`src/gobby/events/wake.py:701-755`). The fifth is checked beside the existing
    `coordinated_hold` (`idle_check_handler.py:368-379`). The prompt is removed at its
    source (item 19). A declined wake returns `ism_persisted: True`, so
    `wake_result_is_delivered` (`src/gobby/events/completion_registry.py:21`) is true,
    durable waits settle and nothing loops. The message stays queued for the next turn. A
    hold is set only on a restore after host loss, so a plain restart with a surviving
    host is unaffected. `BEFORE_AGENT` clears it, so the operator's typing or any real
    turn ends it. The 24-hour revival horizon clears it with the other session variables.
18. **Release authority is declared in project YAML (R3, Josh's ruling).**
    `project_policy.restart_wake_senders: [orchestrator,
    recovery-steward]`. A direct wake releases a held recipient only when its sender is
    the operator's own terminal (`src/gobby/agents/team_communications.py:38`), it is an
    operator comms wake (`replace_composer`, reserved for the system sender,
    `src/gobby/sessions/mailbox.py:206-211`), or the sender's `_agent_type` is listed in
    the recipient project's installed policy. An activated definition has a role, so it
    is not an operator terminal and needs the key. The policy is read through
    `installed_project_policy` the way
    `src/gobby/mcp_proxy/tools/spawn_agent/_launch_settings.py:245` reads it, never from
    session variables, which cannot authorize security decisions
    (`src/gobby/tasks/closure_snapshot.py:34`). No key, a malformed value or an unreadable
    policy means nobody. Fanout never releases. Admission runs first
    (`recipient_policy`, `mailbox.py:222`), so a listed sender still cannot reach a seat
    whose `message_sender_capabilities` refuses it, and the Recovery Steward cannot wake
    the Orchestrator, Assistant or Archivist. The system session's row has no run, depth 0
    and no role (`src/gobby/storage/sessions/_constants.py:166-172`), so it would pass
    `operator_terminal`. A system sender therefore releases only through operator comms, and
    an ordinary system send such as a task assignment
    (`src/gobby/servers/routes/tasks_assignment.py:97-104`) stays queued. Code never names a
    definition (rule 16).
    `send_keys` stays out of scope: it is terminal control, only definitions with that
    capability hold it, and the turn it starts clears the hold.
19. **Managed seats resume with no prompt after host loss (R2, Josh's ruling).**
    A run whose terminal carries `process.host_lost`
    resumes with an empty prompt under the hold. Josh's wording, "all agents ... resume in
    their CLIs" with wakes targeted, requires it. Every other resume keeps
    `DAEMON_STOP_CONTINUATION_PROMPT`, so existing managed recovery stays as it is. A seat
    with no first turn is safe: `finalize_resume_handoff_threadsafe` runs at managed hook
    ingress (`src/gobby/hooks/agent_run_ingress.py:141`), and
    `_session_start/agents.py:29-34` keeps `_agent_type`, so an operator-activated
    definition survives. `check_initialization_timeout` stops applying once the external id
    is known, and `cleanup_stale_runs` skips a run with a live terminal
    (`src/gobby/storage/agents/_cleanup.py:97-102`). Item 22 covers the monitors and the run
    deadline. The conversation and the task claim carry the seat's state, and the targeted
    wake carries the instruction.
20. **Seats discover held sessions through `get_session`.** Cross-session `get_variable`
    returns 403 for seats (`Session does not match agent capability`), so procedures
    cannot read the variable directly. `get_session` gains a `restart_wake_hold` boolean.
    The Orchestrator and the Recovery Steward build one inventory: managed seats from
    `list_running_agents`, and operator-launched roots from `list_sessions`
    (`src/gobby/mcp_proxy/tools/sessions/_crud.py:157`), which `list_running_agents` never
    returns because a root has no agent run. The root listing runs once per live status for
    this project and machine, because an unfiltered listing returns every session ever
    recorded. `src/gobby/install/shared/workflows/pipelines/assistant-status-wake.yaml:21-39`
    already lists sessions this way. `list_sessions` defaults to 20 rows and has no offset, so
    when `count` is below `total` the seat calls again with `limit` at `total`. The seat
    deduplicates by session ref and reads each with `get_session`. An `expired` session whose
    resume failed is absent, which loses nothing: it has no CLI to wake, and its pane shows the
    failed-resume line. The inventory feeds the existing targeted-wake choice, and nothing
    wakes automatically.
21. **Stated limits.** A gterm host crash while the daemon stays up relaunches managed
    seats quietly through the retry loop, and roots wait for the next daemon start (item
    11). A crash keeps parked runs in range, because reconcile parks them at boot and the
    `recent` filter (`src/gobby/storage/agents/_queries.py:148-190`) starts there. A
    planned drain followed by more than 24 hours off ages out parked managed runs, and the
    same horizon closes roots (`src/gobby/storage/sessions/_constants.py:83`).
22. **Automatic monitors leave a held seat alone, and physical death still counts.** The
    preflight in item 17 only sees wakes, and these act on a pane directly:
    `TerminalPromptMonitor` answers loop and approval prompts and presses periodic Enter
    (`src/gobby/agents/terminal_prompt_monitor.py:194-203,258,347`);
    `check_autonomous_stuck_agents` presses Enter or cleans up
    (`src/gobby/agents/lifecycle_monitor.py:663-694`); `check_provider_stalls` kills on pane
    text (`src/gobby/agents/agent_health.py:576-630`); `InteractiveCapacityRecovery` reprompts
    a root on a capacity error (`src/gobby/agents/interactive_attention_monitor.py:222`); and
    `check_unhealthy_agents` kills a live terminal past `timeout_seconds`
    (`agent_health.py:340-348`). Each would act on a seat nobody woke, so each skips a held
    session. The dead-terminal and process-identity checks still run, because a dead CLI is
    not waiting. `check_completed_task_agents` still runs, because a closed task's run may end.
    A run's budget is full at each resume and nothing executes while it is held, so ending a
    hold sets `started_at` to now. That also starts the stuck detector's progress window there
    (`lifecycle_monitor.py:637`), which extending `timeout_seconds` would not. Sweeping
    `origin="automatic"` writes finds no others: the rest pass the wake preflight
    (`src/gobby/runner_init/orchestration.py:110`), sit below the idle hold check
    (`src/gobby/agents/watchdog/recovery.py:259`), need a prompt a quiet resume does not have
    (`spawn_executor_support.py:351`), or are the operator's own UI action
    (`src/gobby/servers/websocket/handlers/plan_approval.py:396`,
    `src/gobby/servers/websocket/handlers/session_config.py:242`).

## Constraints
`kind: framing`

- **RED evidence (observed).**
  `DATABASE_URL=postgresql://gobby_test:gobby_test@127.0.0.1:60892/gobby_test GOBBY_TEST_PROTECT=1 uv run pytest tests/terminals/test_reboot_pane_preservation.py -q -p no:cacheprovider`
  on `0.5.0`, 2026-11-04: 4 passed, 2 xfailed
  (`test_reboot_inventory_and_workspace_sweep_keep_recoverable_pane[operator|managed]`,

- **No secrets in recovery state.** The only new persisted values are `process.cwd`,
  `process.host_lost`, `terminal_context.launch_auto_approve` and the session variable
  `restart_wake_hold`. Argv is read for one boolean and never stored or logged. Restore
  reads session fields (source, external id, model, reasoning effort, workspace path,
  terminal context) and persists nothing else. No restore path enters or types
  credentials.
- **No definition names in code (rule 16).** Tests of the release path use synthetic
  definition names. Only YAML names a bundled definition.
- **Test isolation.** Python tests use the isolated test hub
  (`DATABASE_URL=postgresql://gobby_test:gobby_test@127.0.0.1:60892/gobby_test GOBBY_TEST_PROTECT=1`)
  and fake terminal runtimes (`tests/terminals/fakes.py`). No test spawns a real
  provider CLI or touches the operator's daemon.
- **Rust release discipline.** `gclient` is in `UNPUBLISHED_MANAGED_BINS`
  (`src/gobby/install/version_pins.py:15`), and a changed unpublished source without a
  bump is refused promotion. 3.1 bumps `crates/gclient/Cargo.toml` by 0.0.1 from its
  version at implementation (`0.1.106` on 2026-11-04) and updates `Cargo.lock` in its own
  commit. Per project policy, gclient is built in the same cutover run as the daemon.

## Granularity

Fourteen deliverables in four phases. The settlement flag and spawn folder (1.1) are
facts written at different times, but both live in one record and are tested
together. The sweep (1.2) and the session marker (1.3) are separate lifecycle owners
with separate tests. The posture boolean (1.4) belongs to hook enrichment, a separate owner
from restore, and takes its own security review. Operator restore (2.1), managed in-place
placement (2.2) and the parked task-seat retry (2.3) are three owners: the new restore

owner, the managed resume executor. 1.2 holds the sweep's keep rule and the refill claim
together because both are storage rules over the same pane and terminal rows, and 2.1
and 2.2 consume both. 2.1 exceeds six acceptance items because eligibility, command
shape, folder fallback, idempotence, secrets, rollback, death proof, failure isolation,
the hold, a failed resume and shell quoting are separate faults in one restore lifecycle. Splitting it would ship a
restore that can duplicate a process, leak env or start work in between. 1.5 exceeds
six production files and six acceptance items because the hold is one state machine:
set, checked, cleared and released. Splitting the check from the release would ship a
hold that nothing authorized can lift, and splitting the release from the check would ship
an authority over nothing. The monitors (1.6) are separate owners that act on panes without a
wake, and nothing sets a hold until 2.1 and 2.4 land, so 1.6 can follow 1.5 safely. The wake

suite (4.1) is its own deliverable because it crosses 1.5, 1.6, 2.1, 2.2, 2.3 and 2.4. The
gclient leg (3.1) and the docs (3.2) follow behavior.
