# Keep overlay indexing for a worktree behind its parent under the preflight ceiling

**Plan ID:** task-25678
**Implementation root:** #25678
**Status:** Draft for plan-team review.

## R1 Decision record
`kind: framing`

Task #25678 reported that overlay indexing for a worktree behind its parent cost about 635 s, against a preflight budget of about 100 s. This plan names where that time went, what has already been fixed, what remains, and the fix for the remainder.

**Does this work still need to exist?** Yes, in a narrower form. Two landed fixes removed most of the reported cost: `fd00c994` took reconcile from 75.4 s to 1.2 s, and `70a2f6c7` took local-import resolution from 64.6 s to 8.9 s on a same-fixture A/B. Live spawns have not timed out since those fixes: `daemon.log` after 2026-11-04 14:00 shows 120 runs, 0 timeouts, p90 9.6 s and max 44.9 s, against 73 earlier runs with 5 over 100 s. Those spawns were not behind their parent by the reported distance, so they do not prove the case. The remaining cost is `overlay.files`, which parses every gap path. It measured 68.5 s on the A/B and 267.5 s in the original row for about 950 files. No measurement of the behind case exists on the current gcode 1.9.103, and the roughly 83 s candidate-mode figure is an estimate. A1 therefore carries its own measurement.

**Root cause of the remainder.** `crates/gcode/src/commands/pin.rs::apply_pin` (evidence `0d7262ff`) pins only current effective selectors whose `git_blob_id` equals the base tree entry, and `replace_pins` (evidence `4250dd5b`) deletes every prior row. A base behind the parent therefore turns every path changed since the base into a gap, and `index_file` (evidence `46af3194`) parses each one. The parent usually still holds that exact content version in `code_indexed_files`, because content versions are immutable and are retained by pins, recent Git history and the retention window.

**Decision.** Three deliverables:

- A1 fills pin gaps from content versions the parent already holds, matched by content hash of the base tree entry, and holds same-blob selectors to the same check. This is the fix.
- A2 makes a preflight index timeout report which phase consumed the budget. Today `_run_gcode` discards stderr on timeout, which is why this plan had to reconstruct attribution from manual runs.
- A3 makes a pass killed at the deadline recoverable. The residual below can still reach the deadline, and today a killed pass strands its local-import rows permanently.

**Contract change.** `.gobby/plans/workspace-index-pin.md` R1 and B2.3 say only indexed files whose recorded Git blob ID equals the selected commit's tree entry qualify, and that a re-pin replaces prior rows. A1 replaces that qualification: a content version qualifies when its content hash equals the selected commit's tree entry, filtered under the selected commit's attributes. A blob match alone no longer qualifies. The contract's purpose, that a pinned read returns the selected commit's bytes, is unchanged, and this closes the case where it did not hold. That plan is landed history and is not edited.

**Blob matches do not prove checkout bytes.** A selector records a blob ID only when its working bytes hash to the `HEAD` blob (`crates/gcode/src/index/indexer/selector_blob.rs::HeadBlobs::clean_blob`, evidence `55fa1673`), so a same-blob selector owned by the source holds the raw blob. The base checkout holds that blob converted under the base's attributes. The two differ when an attribute commit arrived without changing the file's blob and the parent never re-checked the file out, and the difference can involve smudge filters and encodings as well as line endings. A1 therefore hashes every same-blob candidate under the base's attributes, in one pass with the retained lookup, and pins only a match. Source-owned selectors on unconverted paths always match, because their stored hash is the hash of those same bytes.

**Pin cost.** Every pin now pays for that pass. About 10,630 entries at `HEAD` took 8.6 s with bulk input at load 45, and 28.7 s with a Python driver using per-entry requests like `Batch::request_filtered` at load near 50. No Rust or idle figure exists, and A1.10 records the first. The live pin phase today is p90 0.70 s and max 2.90 s over 131 spawns. The Orchestrator ruled to accept this cost: the preflight budget is 100 s, and bytes correctness must not depend on Git's list of conversion attributes.

**Pin callers' limits.** Preflight gives pin whatever remains of its 120 s deadline. `src/gobby/code_index/gcode_gateway.py::GcodeGateway.pin_project` (evidence `dd0e6ec6`) runs under the gateway's 30 s default, which this cost can reach, and `create_worktree` and clone creation fail on a pin timeout. A1 passes a 60 s timeout, which team-tree pinning also gets.

**Declared exposure.** The `WORKTREE_CREATE` hook also calls `pin_project`, but it keeps its 26 s endpoint limit (`hooks.adapter_timeout`) and 30 s `ghook` POST limit, shared with `git worktree add`. A pin that outlasts them makes the hook report that no worktree was created. The Orchestrator ruled against a per-hook exemption, because `daemon.log` since 2026-11-03 shows no worktree created through that hook.

**Hash failure.** A failed hash pass, including Git older than 2.41 or a required filter that fails, sends every tracked path to gaps. That costs a full parse, which can reach the deadline, and A3 resumes it. It never pins unverified bytes.

**Accepted consequence.** A retained-version pin has the same shape as a pin whose source later moved: `src/gobby/code_index/_storage/files.py::CodeIndexFileStorageMixin.get_pending_pinned_files` (evidence `1dae0260`) treats it as due, background projection recovers it, reads and content GC already handle it, and `crates/gcode/src/vector/code_symbols/search.rs::has_pending_pinned_projection` (evidence `bf0a2bdd`) degrades the semantic lane until recovery finishes. The previous cost of that state was a preflight parse of the same file.

**Declared residual.** Bytes the parent never indexed, and versions already collected, still parse at the measured 69 to 284 ms per file. The ceiling therefore holds up to about 350 to 1,400 such paths. Past that, the pass is killed at the deadline, the spawn continues with its existing warning, and A3 makes the next pass finish the work. A2 makes that case attributable.

**Rejected alternatives.**

- A committed-attribute guard that trusts a blob match unless a `.gitattributes` in its directory changed between the base and `HEAD`. Attributes that arrived without changing the file pass it, so it leaves a wrong-bytes case open. The Orchestrator ruled a documented wrong-bytes bypass unacceptable.
- Hashing only paths with a conversion attribute, from a `git check-attr` pass. It took 3.8 s at load 45 (check-attr 2.79 s, then hashing 1,347 flagged paths 1.04 s) against 8.6 s for all entries, and it stays inside every caller's limit. The Orchestrator ruled against it so that bytes correctness stays independent of Git's list of conversion attributes.
- Recording conversion provenance at index time. It adds schema and indexing machinery the hash comparison does not need.
- A per-hook timeout exemption for `WORKTREE_CREATE`. It spans `ghook`, the endpoint and the config validator to protect a path with no recent use.
- Raising the 120 s budget. It masks the cost and adds spawn latency to every spawn that reaches it.
- Parallel parsing with batched writes. The cost is load-sensitive (69 ms against 284 ms per file on the same work), and the per-file commit is what lets a killed pass resume.
- Keeping prior pins only. It misses trees created behind the parent and worktrees whose index was invalidated. A1 covers kept pins as well, because a prior pin roots its version until the replacement commits, so the lookup finds it.
- A `git_blob_id` column on `code_indexed_files`. It needs a migration, carriers and a backfill, and the hash comparison already answers the question.
- Changing GC retention. It trades storage for hit rate without changing the failure mode.
- Doing the lookup in `overlay.rs`. It misses direct worktree, clone and integration pin callers, which pin without indexing.
- Letting the index run past the deadline in the background. It changes the read contract for the spawned agent.

**Considered during drafting.** The advisor proposed a separate retention leaf and a choice between parallel parsing and blob lookup. This plan uses one lookup mechanism, because prior pins already root their versions, and rejects parallel parsing for the reasons above.

**Research context:** `apply_pin` (evidence `0d7262ff`) reads the base tree with `read_tree`, keeps effective selectors whose `git_blob_id` equals the tree entry, derives gaps as the remaining tracked paths and calls `replace_pins`. `replace_pins` (evidence `4250dd5b`) runs four statements through `execute_counted`: DELETE pins, DELETE gaps, unnest INSERT pins, unnest INSERT gaps. `replace_pins_issues_a_constant_statement_count` pins that count. `crates/gcode/src/commands/status/content_gc/history.rs::hash_blobs` (evidence `8bf7ba10`) already hashes `(path, blob)` pairs through `cat-file --batch -Z --filters` and returns `HashSet<(path, hash)>`. `--filters` reads attributes from the current working tree, so used as-is it would convert a base blob under the parent's later `.gitattributes`, and a retained version converted that way would match bytes the base checkout does not contain. `git --attr-source=<tree-ish>` (Git 2.41) reads attributes from a tree instead. A probe on Git 2.54 returned LF under the base's `eol=lf` where the current `eol=crlf` returned CRLF, did the same from a nested working directory, and exited 128 on a bad source. Use the flag over `GIT_ATTR_SOURCE`: older Git rejects an unknown flag, which degrades to gaps, but silently ignores the variable. `recent_path_hashes` (evidence `8126a01f`) shows the required prefix handling: tree entries and attributes key on top-level paths, so a nested project root prepends `rev-parse --show-prefix` and strips it from results. The module path is private today: `mod content_gc;` in `crates/gcode/src/commands/status.rs` and `mod history;` in `crates/gcode/src/commands/status/content_gc.rs`.

`code_overlay_pins` (migration `471_code_overlay_pins.sql`) has primary key `(machine_id, overlay_project_id, file_path)`, foreign key `code_overlay_pins_source_content_fkey` to `code_indexed_files(project_id, file_path, content_hash)`, and flags `graph_projected`, `vector_projected`, `graph_attempted_at`, `vector_attempted_at`. `gobby_gcode_capability` has SELECT, INSERT, UPDATE and DELETE on it under overlay-scoped policies, so an upsert works for a scoped principal. `FOR KEY SHARE` on a parent `code_indexed_files` row is unusable: it needs the UPDATE policy, which hides parent rows from an overlay principal. `discover_content_gc` (evidence `99d57b63`) treats pins as GC roots, protects versions reachable from recent Git history, and uses `content_retention_days` (default 1).

Retained-version pins are due for projection from the moment they exist, because `get_pending_pinned_files` and `has_pending_pinned_projection` key on the source selector not naming the pinned hash. Today a re-pin never keeps a moved version, so resetting flags on replace is harmless. After A1 a re-pin keeps them, and resetting would discard finished recovery on every spawn and re-degrade the semantic lane. That is why replacement must preserve projection state for unchanged rows.

Existing fixtures assume a blob match is enough. `pin_inherits_effective_selectors`, `pin_records_only_safe_selectors_and_gaps`, `pin_cold_and_replacement` (evidence `2aa4036e`), `pin_persists_gaps_for_overlay_indexing`, `pin_gap_is_removed_when_repin_pins_it` and `pin_writes_under_scoped_capability_role` give same-blob selectors synthetic hashes such as `hash-clean`, which can never match. `overlay_index_indexes_persisted_pin_gaps` (evidence `838c91e1`) seeds its `dirty` selector from the committed bytes with no blob ID and expects a gap, and under A1 that is a retained match.

**Implementation:**

1. In `crates/gcode/src/commands/status/content_gc/history.rs`, give `hash_blobs` and `Batch::spawn` an `attr_source: Option<&str>` parameter, which `Batch::spawn` passes as `--attr-source=<commit>` before `cat-file`. `recent_path_hashes` and `candidate_blobs` pass `None`, so GC semantics do not change. Add `pub(crate) fn hash_tree_entries(root: &Path, commit: &str, entries: &BTreeSet<(String, String)>) -> anyhow::Result<HashSet<(String, String)>>`. It applies the same `--show-prefix` handling as `recent_path_hashes`, calls `hash_blobs` with `Some(commit)`, and returns project-relative paths. Widen the two module declarations to `pub(crate) mod`.
2. In `apply_pin`, split the effective selectors: candidates are those whose `git_blob_id` equals the tree entry. Add a private `retained_source_pins` helper. It selects `file_path, content_hash` from `code_indexed_files` where `project_id` is the source project, `file_path = ANY(tracked)`, and `language <> TOMBSTONE_LANGUAGE`. It covers all tracked paths, because a candidate that fails verification can still match a retained version. A DB error stays the existing storage failure.
3. Hash the tree entry of every candidate path and every path that returned a row, in one `hash_tree_entries` call with `source.base_commit`. With neither, start no Git process. A hash failure logs one warning naming the path count and error and leaves the hashed set empty, so every tracked path becomes a gap; the pin still succeeds and stays warm.
4. Walk the tracked paths. A candidate whose `(path, content_hash)` is in the hashed set pins unchanged and keeps its source project, including one inherited through the source's own pin. Otherwise a row whose `(path, hash)` is in the hashed set becomes an `EffectiveSelector` with the source project, that hash and the tree entry's blob ID. Otherwise the path is a gap.
5. Rewrite `replace_pins`, keeping four counted statements in one transaction:
   - DELETE pins for this overlay unless their exact `(file_path, source_project_id, content_hash)` tuple is requested. A requested path with a different source or hash loses its old row here, so it can never outlive a replacement whose version vanished.
   - INSERT from the unnest, `JOIN code_indexed_files` on source project, path and hash, `ON CONFLICT (machine_id, overlay_project_id, file_path) DO UPDATE SET git_blob_id = EXCLUDED.git_blob_id`. After the DELETE a conflict can only be an exact tuple match, so both projected flags and both attempt timestamps survive by not being set, and a changed row inserts with column defaults. `RETURNING file_path`, issued through a new `query_counted` beside `execute_counted`.
   - DELETE gaps for this overlay.
   - INSERT gaps from the unnest of the given gaps plus any requested pin path the INSERT did not return.
6. `replace_pins` returns those vanished paths. `apply_pin` removes them from `pinned` and adds them to `gaps`, so `PinReport` matches the rows. `write_cold` ignores the return, because it passes no pins.
7. Update the `crates/gcode/src/commands/pin.rs` entry in `crates/gcode/security/managed_postgres_privileges.json` for the two new `.query(` call sites. The classification stays `project-write`, and `code_indexed_files` is already in its relation set.
8. In `GcodeGateway.pin_project`, pass `timeout=60.0` to `_run_command`. The gateway file is at 975 lines, so also move `_bounded_timeout_output`, `_kill_collect_and_reap` and their two constants from `src/gobby/code_index/gcode_gateway.py` to the new `src/gobby/code_index/gcode_process.py`, and import the two functions back. Nothing outside the gateway references them, no test patches them, and the gateway's `signal` and `suppress` imports go with them.
9. Correct the fixtures. Give each same-blob selector meant to pin its real `hasher::content_hash`, and keep synthetic hashes on paths meant to stay gaps. In `pin_cold_and_replacement`, clearing a blob ID no longer drops a path, because its retained version still matches, so the re-pin selects a new commit whose `src/dirty.rs` bytes the source never indexed. In `pin_gap_is_removed_when_repin_pins_it`, the re-pin indexes the real hash with its blob ID. In `overlay_index_indexes_persisted_pin_gaps`, edit `dirty` before seeding its selector, so the source holds only the edited bytes and the path stays a gap.

The JOIN turns a version collected between lookup and INSERT into a gap instead of a foreign-key failure. A delete committing in the remaining window between the JOIN's read and the foreign-key check still fails the pin as the existing storage failure; that window is one statement and only an unrooted version past retention can hit it. `overlay.rs` is unchanged: a filled path is no longer a gap, so `pinned_base_states` and the existing reconcile arms treat it as inherited.

**Measurement.** After the code passes, the developer writes `docs/evidence/overlay-behind-parent-2026-11/measurements.md` from one sequence:

1. Choose the base: the newest first-parent `0.5.0` commit whose `git diff --name-only <base> HEAD` names at least 500 paths.
2. Run `git branch overlay-behind-measure <base>`, then create two fresh worktrees through `gobby-worktrees:create_worktree` with `base_branch=overlay-behind-measure`, so each carries a real marker. Use two worktrees because `gcode invalidate` leaves overlay `code_indexed_files` rows.
3. In the first worktree run the installed `gcode pin` and `gcode index` with `GCODE_INDEX_TIMINGS=1`. In the second run the release build of this change the same way. Both run candidate mode, without `--full`.
4. Record the base SHA, and for each run: 1-minute load, pinned count, gap count, pin wall time, `overlay.files` summed `elapsed_ms`, `command.index`, and pin plus index wall time.
5. Remove both worktrees and the branch.

The bar for the release build is pin wall time under 60 s and pin plus index wall time under 100 s. A miss blocks closure: send the recorded phases to the team lead for a decision. Do not relax the bar or the base selection.

**Research context:** `ensure_isolation_code_index` (evidence `9f959c37`) runs `gcode index --quiet` through `_run_gcode` (evidence `6fd9f9ef`), which uses `proc.communicate(timeout=...)` and on `subprocess.TimeoutExpired` kills the process and raises `RuntimeError(f"{timeout_code}:{timeout:g}s")`, discarding stderr. `crates/gcode/src/index/indexer/timing.rs::IndexTimings` emits `gcode_index_phase pid= phase= event=start|end elapsed_ms= total_ms=` to stderr when `GCODE_INDEX_TIMINGS=1`, regardless of `--quiet`. It emits per file (`file.parse`, `file.facts`, `file.commit` and others in `crates/gcode/src/index/indexer/file.rs`), so a raw dump would be hundreds of KB on a 1,000-file pass. The daemon's trigger path sets this variable at `src/gobby/code_index/gcode_gateway.py:645`, strips the same line prefix from error text there, and logs phases on timeout at `src/gobby/code_index/trigger.py:380`; preflight has neither. CPython fills `TimeoutExpired.stderr` with the bytes read so far on POSIX; a probe against `Popen.communicate(timeout=0.5)` returned the written line. Do not call `communicate` again after the kill: a surviving Git child can hold the pipe open, which is why the existing code uses `wait`. `_process_detail` uses `stderr or stdout`, and `_preview_process_detail` keeps the last 500 characters.

**Implementation:**

1. Add `_INDEX_PHASE_PREFIX = "gcode_index_phase "`.
2. In `ensure_isolation_code_index`, pass `{**(probe_env or {}), "GCODE_INDEX_TIMINGS": "1"}` to the index `_run_gcode` call only. Status, pin and search smoke keep `probe_env`.
3. In `_run_gcode`'s `TimeoutExpired` branch, after the kill and wait, call new helper `_index_phase_summary(exc.stderr)`. When it returns text, log one warning containing `timeout_code`, the phases that started without ending, and summed `elapsed_ms` per phase, largest first. The helper decodes with `errors="replace"`, skips any line it cannot parse, still counts every complete record, returns an empty string when it finds none, and never raises. `exc.stderr` can be `None`, can hold non-UTF-8 bytes, and can end in the middle of a line. The raised `RuntimeError` text is unchanged in every case.
4. In the non-zero exit branch, remove phase lines from stderr before `_process_detail`, so a failure preview stays the error text and falls through to stdout when only phase lines were written.

This deliverable is Python-only and needs no version bump.

Consumers unchanged:

- `crates/gcode/src/index/indexer/primary.rs` — no-edit-reason: keeps its own trigger-filtered local-import calls, and its just-indexed owners are already dirty, so the shared resolver's new dirty write changes nothing for them.
- `crates/gcode/src/commands/repair.rs` — no-edit-reason: calls the same resolver, whose new dirty write is correct for a repaired owner.
- `src/gobby/code_index/nightly_repair.py` — no-edit-reason: `repair_project` keeps returning `skipped_overlay`, which this deliverable makes safe.
- `tests/install/test_version_pins.py` — no-edit-reason: compares each pin to its crate manifest, which is this deliverable's bump check.

**Research context:** A pass killed at the deadline has committed per-file transactions (`index_file`, evidence `46af3194`) but never reached local-import resolution, so those files keep `callee_target_kind = 'local_import'` rows. The next pass reports them current (`overlay_is_current` at `crates/gcode/src/index/indexer/overlay.rs:334`) and Skips them. `resolve_local_import_calls` reads through `read_local_import_calls` (evidence `61c17cc7`), which filters to `outcome.indexed_file_paths`, so it never sees them. `src/gobby/code_index/nightly_repair.py::repair_project` returns `skipped_overlay`, so nothing else repairs them. The rows are stranded for the overlay's life and calls into those files stay unresolved.

`crates/gcode/src/index/indexer/local_imports.rs::resolve_project_local_import_calls` and `resolve_project_local_import_inheritance` already exist as `pub(crate)` and return `LocalImportRepair { pending, resolved, owners }`; `primary.rs` uses the first for full indexes and `commands/repair.rs` uses both. An overlay project holds only overlay-owned rows, so a project-wide read is bounded by the overlay's own divergence.

No-op cost differs by table. A call row always leaves pending on a pass, because a miss rewrites it to unresolved through `unresolved_call`, so a settled overlay reads zero rows and `promote_local_import_calls` loops over nothing. An inheritance row with no resolution stays pending and is retried each pass, at up to two `resolve_local_callee_symbol_id` lookups per row. The existing trigger-filtered path already reads the whole project set, so only the retry lookups are new, and they are bounded by rows that cannot resolve.

Promoted facts need durable projection state. Background projection can sync a killed pass's committed files while their calls are still pending, leaving `graph_synced = true`. `resolve_pending_local_import_calls` commits the promotion with no dirty write, and graph recovery through `CodeIndexFileStorageMixin.get_pending_sync_files` requires `graph_synced IS FALSE`. The owners on `IndexOutcome` are in memory, are skipped when `sync_projections` is false (`crates/gcode/src/index/indexer/lifecycle.rs::attach_projection_sync`), and are lost if the process dies after the commit. That owner would never re-project. `resolve_pending_local_import_inheritance` already avoids this by calling `db::dirty_graph_sync_for_file` in its promotion transaction, which resets `graph_synced` and `graph_sync_attempted_at` and leaves vector state alone.

**Implementation:**

1. In `index_overlay_files`, replace the two resolve calls (`overlay.rs:440` and `overlay.rs:450`) with `resolve_project_local_import_calls` and `resolve_project_local_import_inheritance`, keeping the `overlay.local_imports` and `overlay.local_inheritance` timing phases. Pass the union of both results' `owners` to `outcome.record_promotion_owners`, which stays the immediate path. Remove `adopted_paths` and `trigger_paths`. Update the import in `overlay.rs:25`.
2. In `resolve_pending_local_import_calls`, inside the existing transaction and after `api::promote_local_import_calls`, call `db::dirty_graph_sync_for_file` once per distinct `(file_path, content_hash)` among the pending rows. A rewrite to unresolved changes the row too, so both outcomes dirty. This adds one UPDATE per owner, which A3.4's combined-build measurement covers.

 Primary indexing is unchanged, and its callers keep `resolve_local_import_calls` and `resolve_local_import_inheritance` alive.

**Measurement.** This deliverable's retry lookups land after A1's measurement, so rerun that sequence once on a release build containing both A1 and A3. Use the base SHA A1 recorded, one fresh worktree created the same way, and candidate mode, with no second baseline. Append the same fields to `docs/evidence/overlay-behind-parent-2026-11/measurements.md`, then remove the worktree and branch. The bar is the same: pin plus index wall time under 100 s. A miss blocks closure: send the recorded phases to the team lead for a decision. A gap count above A1's row means versions were collected since A1, so name that in the report. Do not relax the bar or change the base.

**Acceptance:**
- A3.1 - A call row left at `local_import` on a file a second pass Skips is promoted by that pass even with `sync_projections` false. The owner starts with `graph_synced` and `vectors_synced` true and ends with `graph_synced` false and `graph_sync_attempted_at` NULL in the database, with vector state unchanged, so recovery survives the process ending before projection. With `sync_projections` true its owner also appears in the graph projection paths. test: `crates/gcode/src/index/indexer/tests/overlay.rs::killed_pass_call_rows_promote_on_the_next_pass`.
- A3.2 - An inheritance row left at `local_import` on a Skipped file is promoted by the next pass, its owner ends with `graph_synced` false in the database, and its owner appears in the graph projection paths. test: `crates/gcode/src/index/indexer/tests/overlay.rs::killed_pass_inheritance_rows_promote_on_the_next_pass`.
