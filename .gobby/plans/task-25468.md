# R0: Worker Boundary And Frozen Lifecycle Contract

## Overview
`kind: framing`

Task #25468 (R0: Worker boundary and frozen lifecycle contract), slice R0 of the runner
epic #25467 under #21544. Planning task #25582. Sources: the R0 row of research #25351
(`.gobby/plans/research/runner-first-1.0-25351.md`, slice table, "R0: worker boundary and
frozen lifecycle contract") and rust-port-order v2 Phase 1
(`.gobby/plans/research/rust-port-order-v2-2026-10-31.md`). R0 gates every Stage 2 family
(plan `.gobby/plans/task-25460.md` 1.2) and R1-R7 (#25469 onward).

The task's acceptance criteria:

1. A committed lifecycle inventory with fixtures names every startup job, service owner,
   identity and error in `runner.py` and `runner_lifecycle_*.py`, including tasks
   created inside constructors.
2. A versioned private command protocol and a Python facade run the initialization
   phases without calling `run_daemon`.
3. The existing Python runner still boots unchanged, and facade unit tests pass.
4. The work claims no Rust runner completion.

The plan delivers four leaves in the task's two checkpoints. Checkpoint 1 (inventory and
fixtures): 1.1, a static inventory pinned to the runner source, and 1.2, a runtime census
of an isolated boot that catches tasks created inside constructors. Checkpoint 2
(protocol and facade): 1.3, the versioned worker protocol with its handshake stub, and
1.4, the facade that runs `GobbyRunner.create`'s phases one command at a time. They map
to v2 Phase 1 porter tasks (1), (2) and (3).

## Decision Record
`kind: framing`

1. **Scope is #25351's R0 row and v2 Phase 1 porter tasks (1)-(3).** v2 task (4),
   "optional checklist generator scripts", is marked "nice-to-have, not a gate" and is
   not built: nothing consumes it.
2. **The inventory is JSON in `tests/contracts/`, explained by one contract doc.**
   `tests/contracts/runner_lifecycle.json` is the machine contract. Rust tests already
   read this directory (`crates/gcode/tests/contract.rs` uses
   `include_str!("../../../tests/contracts/gcode.contract.json")`;
   `crates/gdaemon/tests/http_contracts.rs` replays `tests/contracts/http/`), so R1-R7
   can pin their Rust owners against the same file. `docs/contracts/runner-lifecycle.md`
   states the schema, the ownership rule and how to change an entry. It does not list
   entries, so the JSON stays the single source.
3. **Completeness has two proofs.** Static pins cover the files the criterion names:
   unit tests parse `runner.py` and `runner_lifecycle_*.py` and fail on any task-creation
   site, periodic task, started or stopped service, explicit raise or exit code missing
   from the inventory (1.1). Constructor-created tasks live in domain classes the runner builds;
   a static sweep cannot bound them (observed: `rg -c` for `create_task(`,
   `ensure_future(` and `threading.Thread(` over `src/gobby` gives 264 sites in 168
   files). A runtime census of one isolated boot records every task and thread created
   from Gobby code, so 1.2 catches them (#25351's "chief risk").
4. **R0 binds no transport.** R0's criteria need a protocol and a facade, not a
   listener. R1 (#25469) is the first caller of the handshake and binds the protocol on
   the private backend channel. #25351 fixes the constraints R1 inherits: authenticate
   with the inherited front-door secret (`X-Gobby-Front-Door`, checked by
   `src/gobby/servers/auth_service.py::verified_front_door_identity`), bind a minimal
   control app before domain construction, no PyO3, no generic RPC. The protocol doc
   records this hand-off.
5. **The facade runs `GobbyRunner.create`'s five phases.** `GobbyRunner.create`
   (`src/gobby/runner.py`) runs five steps in order: `open_storage_and_config`,
   `bundled_content_refusal` (raising `StartRefusal`), `init_startup_content`,
   `config_runtime.start()` with `bootstrap_overlaid_config`, and
   `_initialize_runtime_services`. #25351 names exactly this material as the
   "Initialize phase" group (evidence E6, `runner.py:271-356`). The phases are
   `storage_and_config`, `content_refusal`, `startup_content`, `config_runtime`,
   `runtime_services`.
   - Rejected: splitting `runtime_services` into its four calls. It would bypass the
     `GobbyRunner._initialize_runtime_services` patch point that
     `tests/config/test_restart_config_consumers.py` uses, and R2 sequences the service
     graph as one checkpoint.
   - Rejected: adding `run_gobby`'s steps (bootstrap refusals, PID ownership,
     supervisor watch, schema verify, break-glass credential, lease view, AGY probe) and
     the post-create `_bind_runtime_grants`. They interleave with PID ownership, and
     `tests/providers/test_version_gate.py::test_run_gobby_awaits_probe_after_pid_ownership_before_runner`
     pins their order in `run_gobby`'s source. They stay in `run_gobby` and are
     inventoried with owners R1 (identity and process) and R2 (grant binding).
6. **One phase sequence.** The `InitPhase` enum's declaration order is the phase
   order. `GobbyRunner.create` loops over it, and the facade enforces it. No second
   list exists to drift.
7. **The protocol is named `worker`.** The schema identity already carries
   `runner_protocol` (`crates/gcore/src/schema/assets.rs::RUNNER_PROTOCOL_VERSION`,
   added by #19425 "add gcore schema authority"; pinned in
   `src/gobby/storage/schema_expected_identity.json`). That field versions the schema
   asset contract, not the daemon worker. The new constant is `WORKER_PROTOCOL_VERSION`.
8. **Versioning and identity.** `WORKER_PROTOCOL_VERSION` is an integer, starting at 1.
   Both sides must match exactly, because Rust and Python ship from one checkout. Any
   wire change bumps it, and its corpus changes in the same commit. One worker process
   serves exactly one generation. Rust assigns it, and the first handshake binds it.
   Any other generation is refused as stale, whether lower or higher. The handshake
   reports `expected_schema_identity()`
   (`src/gobby/storage/schema_contract.py::expected_schema_identity`), which R1 can
   compare with `SchemaIdentityContract::embedded()` to reject a worker from another
   checkout.
9. **Unknown outcomes.** A handshake is not effectful and repeats idempotently. An
   `initialize` is effectful and never re-runs: a repeat of a finished phase is refused
   as out of order. A lost reply mid-construction leaves the outcome unknown. Rust's
   recovery is to stop the worker and start a fresh generation, because construction is
   not resumable across processes. No status command is needed.
10. **v1 carries no deadline, degraded status or config revision.** No construction
    phase reports degraded, and Rust can time a call on its side. R2 adds what it needs
    with a version bump.
11. **Wire models copy `src/gobby/hub/node_commands.py::NodeModel`:** pydantic
    `ConfigDict(extra="forbid", strict=True)`. Responses are canonical JSON
    (`separators=(",", ":")`, `sort_keys=True`, `ensure_ascii=False`). Requests are
    bounded to 65,536 bytes.
12. **New package `src/gobby/worker/`.** It holds the worker boundary that R1-R6
    extend. R1 adds its entrypoint there.
13. **No `crates/` Targets.** Criterion 4 forbids Rust runner claims, and a crate change
    would force a shipped-binary version bump for no behavior.

The inventory (`inventory_version: 1`) has five record kinds. Each entry names its owner
as `path::qualified_name`, its `stage` (`preflight`, `construct`, `serve`, `subsystems`,
`recovery`, `shutdown`), `hub_only`, and `next_owner`. `next_owner` follows #25351's
slice map: identity and process entries go to R1, construction and readiness to R2,
recovery to R3, periodic, cron, pipeline and system automation to R4, hook, MCP,
WebSocket and chat services to R5, and stop order to R6.

- `phases`: ordered startup steps from `main` to `_recover_after_restart`.
- `tasks`: each asyncio task or thread, with `creator`, `runner_attr` (nullable),
  `name`, `cancel_owner` and `condition` (nullable, for config-gated tasks).
- `services`: each long-lived runner attribute path, with `start_owner` and `stop_owner`,
  each a list of owning functions (`runner.lifecycle_manager`, for example, has a hub
  and a node start owner).
- `identities`: each identity, with `source` (`env`, `pipe`, `file`, `database`,
  `process`), `producer`, `consumers` and `current_owner` (`rust` or `python`).
- `errors`: each explicit raise, refusal and exit, with `raised_by`, `exception` or exit
  code, and `effect` (refusal exit 78, crash exit 1, clean exit 0, clean return, or
  `propagates` to the caller with no process effect of its own, such as the
  `RuntimeError` raises in `src/gobby/runner_lifecycle_agents.py`).

`tests/contracts/test_runner_lifecycle_inventory.py` pins it by parsing source with
`ast` and `inspect`, never by importing heavy services:

- Phases: the ordered string literals of `timed_startup_phase(...)` and
  `hub_only_phase(...)` calls in `init_subsystems` and `_recover_after_restart` equal the
  inventory's `subsystems` and `recovery` phases, and `HUB_ONLY_STARTUP_PHASES` equals
  their hub-only ids. Construction order is pinned by behavior so it survives 1.4's
  refactor. The test runs `GobbyRunner.create()` with the `gobby.runner_init` callables
  and `GobbyRunner._initialize_runtime_services` patched to record calls, using the
  technique of `tests/runner_init/test_config_runtime_startup.py::_patch_runner_phases`
  with a stub runtime. It asserts the recorded order equals the `construct` phases.
- Tasks: every `create_task`, `ensure_future`, `threading.Thread` and periodic `spawn`
  call in `runner.py` and `runner_lifecycle_*.py`, keyed by enclosing function
  qualname, has an inventory task entry, and every entry whose creator is in those files
  matches a live site.
- Periodic: the `runner.<attr>` assignments and task names in `start_periodic_tasks`
  equal the inventory's periodic entries. `HUB_ONLY_PERIODIC_TASKS` equals their hub-only
  names. Each attribute appears in `_cancel_periodic_tasks`' `periodic_task_attrs`
  literal, or the entry names another cancel owner whose source mentions it.
- Services, in both directions. Stop side: every runner attribute whose `stop`, `close`,
  `aclose` or `shutdown` attribute is reached in `runner_lifecycle_shutdown.py`
  (directly, as `runner.x.stop`, or through a local bound from `getattr(runner, "x", ...)`)
  is an inventoried service. Start side: every `.start(...)` call and every first
  argument of `_start_tracked_service(...)` in `runner.py` and `runner_lifecycle_*.py`
  resolves to an inventoried service's attribute path. The receiver resolves by one hop:
  `runner.x` or `self.x`, `getattr(runner, "x", ...)`, a nested path such as
  `getattr(runner.http_server.services, "web_chat_runtime_manager", None)`, or a local
  bound once in the same function from one of those (`host`, `monitor`,
  `automation_loop` and `runtime_manager` today). A start site that does not resolve
  fails the test. A call inside a lambda, such as the `communications_start` phase,
  counts for the enclosing function. The generic `service.start(**start_kwargs)` inside
  `_start_tracked_service` is excluded, because its callers' first arguments are the
  sites. A `.start()` passed to `create_task`, such as `runner.websocket_server.start()`,
  is both a task site and a start site. Each service's attribute name appears in every
  start and stop owner's source. Rejected (the enhancer's broader form): treating every
  runner attribute assignment as a start candidate. It would sweep in storage managers
  and config objects that have no start or stop, and need an exclusion list.
- Errors: every explicit `raise <expression>` and every `sys.exit(<int>)` in `runner.py`
  and `runner_lifecycle_*.py` maps to an error entry, keyed by `raised_by` (the enclosing
  function qualname) and `exception`. `exception` is the class name for `raise X(...)` or
  `raise X`, and otherwise the expression's source text (`raise deferred_cancellation`
  in `runner_lifecycle_shutdown.py`). `raise ... from ...` keys on the raised
  expression. A bare `raise` re-raises an exception that another entry or the caller
  already owns, so it is not an entry, and the doc says so.
- Identities: each identity's producer resolves, and its name appears in each consumer's
  source.

`docs/contracts/runner-lifecycle.md` states the schema, the stage and `next_owner`
vocabularies, the rule that a lifecycle change edits the JSON in the same commit, and
that `next_owner` is a plan, not a completion claim.

Each creation appends one JSON line to `$GOBBY_HOME/logs/task-census.jsonl`:
`{kind, stage, creator, target, name}`. `creator` is `<module>:<co_qualname>` of the
nearest stack frame whose module starts with `gobby.`. `target` is the coroutine's or
thread target's `<module>:<qualname>`. Records with no `gobby.` frame are library
internals and are skipped, and so are `concurrent.futures.thread._worker` pool threads.
The census key is `(kind, creator, target)`.

(`e2e` marker) boots with `runner_module="tests.e2e.task_census_bootstrap"`. It polls

first periodic iterations land. It asserts every census key maps to an inventory task's
`census` list, and reports unmapped keys with their stage. Tasks that are inventoried
but not observed are allowed (they are config-gated), so the check only fails on a new
or uninventoried task.

The leaf adds `census` keys to existing task entries, and an entry with stage
`construct` for each task first created inside `GobbyRunner.create`, with its creator,
cancel owner and `next_owner`. It adds a "Runtime census" section to the doc that
defines the record, key and skip rules.

Research context. Precedent for a versioned command protocol shared with Rust:

`src/gobby/worker/protocol.py` (new) holds the wire contract only:
