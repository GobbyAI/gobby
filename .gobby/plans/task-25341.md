# Gobby 1.0: big-bang port in Claude Code cloud sessions

**Plan ID:** task-25341

## Overview
`kind: framing`

Root: #25341 under #21542. Planning task: #25342. This plan revises the
playbook `~/.claude/plans/trying-to-finish-1-0-fuzzy-shamir.md`
(gobby#18571) into executable form. It folds in Josh's six feedback items and
the pilot recorded on #25341.

The local per-family process is correct but too slow to finish #21542. Over the
21 days before the playbook, `0.5.0` took 1,649 `fix` commits against 162
`feat`. Claude Code cloud sessions add authoring capacity that does not load the
local daemon. A cloud session has no daemon, MCP proxy, task database, memory or
code index. This plan therefore builds only what the cloud cannot get from
Gobby:
- a committed project record generated from Gobby state;
- a stdlib gate script that enforces each slice's owned paths;
- local oracles for the low-traffic families;
- the local merge gates and landings.

Everything else reuses existing owners:
- the family plans and leaf tasks are the spec;
- #21559's leaves are slice A1;
- the stamped tasks-family plan is slice B0;
- the front door's `proxy | native | compare` routing and `gdaemon compare-report`
  carry parity;
- the HTTP contract corpus holds frozen fixtures;
- `.gobby/plans/s2-11-hub-hooks-rules.md` §1.1 owns the rule-engine corpus.

The pilot comes first: Phase 0, then A1, then B0, then a Tasks compare soak
that measures the partial and stub rate. Fan-out (P3) starts only when Josh
approves it at the pilot gate (1.4).

### 0.1 Cloud-port record generator [category: code]
`kind: deliverable`

Targets:
- `scripts/cloud_port_record.py`
- `tests/scripts/test_cloud_port_record.py`
- `.gobby/cloud-port/slices.json`

**Research context:**

*Inputs.* The task backup holds `seq_num`, `title`, `task_type`, `state`
(`is_closed`, `is_claimed`), `description`, `deps_on`, `parent_id`,
`path_cache`, `labels` and `claimed_by_session_id`. Expansion labels each
leaf `covers:<plan-id>:<section>:<item>`. Validation criteria sit in
`review.criteria`; `src/gobby/sync/task_review_serialization.py` owns that
shape. The memory backup holds `content`, `rationale`, `tags` and `type`; 21
memories carry the tag `josh-ruling`. Family plans name their debt section
with a `## ` heading that starts with "Debt":
- `## Debt not to port`: agents, AI providers, memory, s2-11, s2-7 and sessions;
- `## Debt corrections and shared conventions`: cron;
- `## Debt-first amendment record`: projects;
- `## Debt dispositions and shared conventions`: skills and tasks.

Parity-ledger shards are `docs/contracts/parity-ledger-status.d/*.json`. Each
maps a surface key to `{status, note}`, and the notes cite owners as `#N`.

*`slices.json`.* It holds:
- `shared`: the Constraints list;
- `frozen`: empty until 1.1;
- `local_roots`: D5;
- one entry per slice with `roots`, `plans`, `crates` and an optional
  `sections` filter.

0.1 defines A1 and B0. A1 has roots `#24439` (P4) and `#24440` (P5), plans
`.gobby/plans/gdaemon-runtime-family.md`, no crates and sections
`4.1`–`5.16`. B0 has roots `#21560`, plans `.gobby/plans/tasks-family.md`,
crates `crates/gtasks` and sections `1.1`–`4.2`. The sections filter matches
expansion labels `covers:tasks-family:<section>:*`.

*CLI.* `uv run python scripts/cloud_port_record.py slice <ID>` writes
`.gobby/cloud-port/slices/<ID>.md`. `uv run python scripts/cloud_port_record.py rulings`
writes `.gobby/cloud-port/rulings.md`. The script imports only the standard
library.

*Items.* A slice's items are the open leaf tasks under its roots. Leaves under
`local_roots` and leaves claimed locally are excluded. Items are ordered
topologically by `deps_on`, with ties broken by `seq_num`. Each item carries:
- `### #N <title>`, then type, in-slice dependencies and external dependencies
  with their state;
- the Targets block parsed from the description, or `spec: missing` (D9);
- the description and validation criteria, copied without rewriting except
  for redaction;
- `status: todo` and an empty `evidence:` line.

Status rules:
- An item with an open external dependency outside the slice gets
  `blocked(#N open)`.
- An item whose Targets are all `.py` gets `needs-local`.
- An item with some `.py` Targets lists them under `local-parts:`.
- An item whose Targets touch a `frozen` path gets `needs-local` with reason
  `frozen <path>`.

*Readiness.* Expansion is the proof that Josh approved a plan, so the
generator reads readiness from its inputs. A configured plan is ready when its
file has a `## M1 Task Manifest` heading and each selected deliverable section
has at least one task under the slice's roots labeled
`covers:<plan-id>:<section>:*`. The selected sections are the `sections`
filter, or every `###` deliverable section when the slice has no filter. Any
unready plan refuses the whole slice, and the refusal lists the missing
sections. The Orchestrator then waits for the plan, or moves the root to
`local_roots` or to another named slice in the same `slices.json` commit,
citing its ruling in the commit message. A bare removal leaves the root with no
owner and fails the record deliverable's acceptance (3.3). A slice never
launches with part of its roots missing.

*Header.* The slice header carries:
- `generated:` with the date, backup mtime and `git rev-parse HEAD`;
- `owns:`, the union of the non-`.py` item Target paths and each `crates`
  glob (`<crate>/**`);
- the launch counts per status.

It is followed by each plan's Debt section, the ledger rows whose note cites a
root or an item, and an empty `## Found Work`.

*Refusals.* The generator refuses four cases, and each refusal writes nothing:
- overwriting a slice file in which any item is past `todo`, `blocked` or
  `needs-local`;
- owns that overlap another generated slice outside `shared`;
- a slice with no `todo` item;
- an unready configured plan (Readiness).

*Rulings.* `rulings.md` lists each `josh-ruling` memory as its content plus
`when:` and its rationale.

*Redaction.* One redactor runs over every text the generator writes: item
titles, descriptions and criteria, Debt sections, ledger notes and rulings. It
rewrites:
- emails to `[email]`;
- UUIDs to `[uuid]`;
- session refs `gobby#\d+` to `[session]`;
- absolute home paths `/Users/<name>/` and `/home/<name>/` to `~/`.

Task refs `#N` stay.

**Granularity:** one leaf with nine acceptance items. The generator, its
refusal rules and the rulings writer share one loader and one output contract.
The rulings writer is about 30 lines, and a separate leaf would duplicate the
backup loading.

### 0.2 Slice gate tool [category: code]
`kind: deliverable`

Targets:
- `scripts/cloud_port_gate.py`
- `tests/scripts/test_cloud_port_gate.py`

**Research context:** The gate tool must run in cloud, where no venv exists
(D3). It imports only the standard library. Cloud runs it as
`python3 -I scripts/cloud_port_gate.py`, and local runs it as
`uv run python scripts/cloud_port_gate.py`.

`check-slice <ID> <head>` validates one slice's cloud commits. The caller
fetches `origin/port/1.0` first. The tool derives the launch base with
`git merge-base --all origin/port/1.0 <head>` and refuses when that returns no
commit or more than one. `port/1.0` moves only by fast-forward, and landings are
merge commits (D4, 0.3 §10). So this base is the commit the session started
from, and it stays fixed across gate retries. The tool reads `owns:` and the
item inventory from the slice file, and `shared` and `frozen` from
`slices.json`, as bytes at the base (`git show <base>:<path>`). Nothing in the
range can widen its own authority. It reads the range from
`git diff --name-status <base> <head>` and `git log --format <base>..<head>`.
It refuses:
- a changed path outside owns, `shared` and the slice's own file;
- a frozen path;
- any `.py` path or any path under `src/gobby/`;
- a commit whose subject does not start with `[gobby-#N]` for an item of the
  slice;
- a head slice file whose item IDs differ from the base inventory, through a
  missing, duplicated or foreign item;
- an invalid status value;
- a `done` item whose `evidence:` lacks red and green SHAs in the range with
  red an ancestor of green (`git merge-base --is-ancestor`).

`report <ID>...` counts statuses across the named slices and prints the D11
rate: `(partial + stub) / (done + partial + stub)`. It exits 1 in three cases:
- any item is still `todo` or `specced`;
- a file's item count differs from its header's launch counts, or an item ID
  repeats;
- no item is `done`, `partial` or `stub`, in which case it prints
  `no attempted items`.

The status vocabulary is `todo | specced | done | partial | stub | needs-local
| deferred-local | blocked(<why>)`. The evidence line format is
`evidence: red <sha> green <sha> test <command>`. The item's evidence commit
writes that line after both SHAs exist (0.3).

**Granularity:** one leaf with ten acceptance items: one command-line tool
with two subcommands over one slice-file parser and one launch-base rule.

**Acceptance:**
