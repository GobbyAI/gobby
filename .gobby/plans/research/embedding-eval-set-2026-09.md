# Embedding eval set (2026-09-24)

This is a fixed set of 100 real retrieval queries with their expected hits, for decision D4 (see `embedding-models-2026-09.md`). It was prepared without serving any model. Run it after the 0.6 golden path; the result is a yes or no for each option.

The set is kept as Markdown because Gobby's task gate blocks a bare `.jsonl` write into the repo from a session that has no claimed task. The data sits in one fenced `jsonl` block at the end. To extract it:

```bash
awk '/^```jsonl$/{f=1;next} /^```$/{f=0} f' .gobby/plans/research/embedding-eval-set-2026-09.md > eval.jsonl
```

## Composition

| Workload | Queries | Natural language | Mixed | Identifier | Grade 2 / 1 |
|---|---|---|---|---|---|
| memories | 44 | 13 | 31 | 0 | 26 / 18 |
| tools | 12 | 8 | 3 | 1 | 11 / 1 |
| gcode | 44 | 30 | 7 | 7 | 42 / 2 |

- **Time window:** queries were issued between 2026-08-19 and 2026-09-24. They were mined from 1,646 Claude Code and 3,511 Codex transcripts.
- **Headroom:** under current retrieval, 44 of the queries have their expected target somewhere below rank 1.

## How relevance was decided

1. **Signal of use.** A query counts only if the agent that ran it then used a result within its next few calls. What counts as use depends on the workload:
   - memories: `get_memory`
   - tools: `get_tool_schema` or `call_tool`
   - gcode: `symbol-at`, `outline` or `Read`
2. **Grading.** Each pair was graded by hand: 2 means the target clearly answers the query, 1 means it is relevant or a partial answer. Pairs where the follow-up looked incidental were dropped.
3. **Live check on 2026-09-24.** Every memory ID still exists. Every tool still exists on its server. Every gcode file and symbol exists in the current checkout, confirmed with `gcode search-symbol`.

## Fields

- `id`, `workload` (`memories` | `tools` | `gcode`), `query`, `query_type` (`natural_language` | `mixed` | `identifier`).
- `expected`: one or more targets, in one of three forms:
  - full memory UUIDs;
  - `server/tool`;
  - `repo/path::Symbol`, or just `repo/path` for the 8 file-level gcode targets.
- `grade` (2 or 1) and `target_note`, a short description of the target for human checking.
- `source`: the CLI, the transcript basename and timestamp, the use signal, and `result_rank`, the target's rank under the retrieval in use at the time.

## How to run it (after the golden path)

1. Re-embed the three corpora for each option at its native dimension, in staging collections. The corpora are memories, MCP tools and gcode symbols.
2. Embed each query exactly as written, adding the model's query instruction. `MemorySearchService` embeds the raw query (memory 432fe22d).
3. Score each workload with recall@5, recall@10 and nDCG@10. Score the dense lane on its own and the hybrid (BM25 plus dense) result.
4. Report the identifier queries separately. Dense models are expected to fail them, and the BM25 lane should carry them.
5. Run nomic-embed-text-v1.5 through the same harness as the baseline.
6. Load one model at a time, on a single server, in a quiet window, never next to the daemon's live model (memory a5ad8b5c).
7. A file-level gcode target counts as a hit when any symbol in that file ranks.

## Caveats

- **The incumbent is favoured.** An agent could only use a result that the current retrieval surfaced, so the set leans toward what nomic already finds. The 44 queries whose target sits below rank 1 give the headroom.
- **The sources are skewed.**
  - 41 of the 44 memory queries, and every tool query, come from Codex sessions. Claude Code sessions read memory content inline and seldom call `get_memory`.
  - Most tool queries come from one plan-review burst, 2026-08-19 to 2026-09-07.
- **Memory content drifts.** Re-check each expected ID before a run. One candidate was already dropped because its memory was rewritten after the search.
- **`result_rank` is historical.** It comes from the retrieval pipeline of the day, which was hybrid for memories and gcode, so it is not a pure nomic dense rank.
- **Mining scripts are temporary.** They live in the originating session's scratchpad: `mine_search_history.py`, `shortlist.py`, `selection.py` and `emit_candidates.py`. Regenerate them if the set needs to be extended.
