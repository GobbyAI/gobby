# #24417 Grok panes freeze after compaction: option A report

Orchestrator gobby#15977, 2026-10-15 18:45 CDT. Sources: Security Reviewer gobby#16011 (via LM7 gobby#16727, message 7de89256), developer gobby#16725 (message b6fc26be), LM7's external search, and `.gobby/plans/research/24417-grok-sandbox-investigation.md`. All work was read-only. No live proof was run.

## The problem

Four Grok seat freezes each came within about 1 s of a sandbox denial of `mach-lookup com.apple.windowserver.active`, after a second compaction. The captured hang (seat 16717) shows Grok's main/UI thread blocked in a macOS SkyLight event-source flags query (`SLEventSourceFlagsState` → `CGSEventSourceShutdown` → mutex wait). Gobby's Grok sandbox profile (SRT 0.0.79, `srt_runtime.py::render_srt_settings`) emits no `allowMachLookup`, so that service is denied. Claude and Codex seats show zero such denials.

The link between the denial and the freeze is a strong correlation and has not been proven.

## Options

- **A**: allow exactly `com.apple.windowserver.active` for Grok profiles only. Recommended, with a Security Reviewer pass and a controlled double-compaction proof.
- **B**: change compaction timing for Grok seats.
- **C**: detect and recover a hung Grok UI (bounded stop and resume, handoff preserved).
- **A+C**: A, plus C as a fallback.

## Security implications of A (Security Reviewer 16011)

1. **macOS privacy permissions (TCC): not established.** We haven't proven which process macOS treats as responsible for a Grok seat (terminal host or gdaemon). Josh's gdaemon privacy prompt today doesn't establish which privacy service it was, or that it applies to Grok. Do not assume A inherits Screen Recording, Accessibility or Input Monitoring. A removes one sandbox lookup barrier; macOS privacy checks still apply.
2. **Key-state exposure: possible, unverified.** Apple documents `CGEventSourceKeyState` as reading current key up/down state, with no stated permission requirement. Whether current macOS reveals ordinary keys without Input Monitoring is unverified. Treat key and modifier observation as a possible added exposure.
3. **Narrowest scope: the one exact service name.** SRT maps a literal name to `(allow mach-lookup (global-name "com.apple.windowserver.active"))`. Only a trailing `*` means a prefix. There is no per-API, read-only or compaction-only option. Limiting it to Grok profiles limits who gets it, not what the connection can do.

## Best practice

- **xAI** ships its own opt-in sandbox in Grok Build: Seatbelt on macOS, Landlock on Linux, with workspace, read-only and strict profiles (xai-org/grok-build, user guide `18-sandbox.md`).
- **Claude Code 2.1.300 and Codex 0.160.0** embed sandbox profiles that allow only specific named services: directory/user lookup, TLS/trustd, configuration and power. Neither names WindowServer. This evidence comes from the binaries, not a captured runtime profile.
- **Codex** adds single named services case by case (for example `opendirectoryd.libinfo`).
- **Microsoft MXC** blocks WindowServer by default and allows it only behind an explicit GUI-access option.
- Our SRT 0.0.79 default profile omits WindowServer. Option A would add exactly one rule.

## Recommendation

If you pick A, it is a single exact-service exception, limited to Grok profiles, with two known open points: TCC attribution and key-state exposure. Proving it stops the hang needs a controlled double-compaction proof on one Grok seat, which needs your go. A tighter alternative would need a separate broker design or a fix from xAI. A+C adds detect-and-recover as a fallback if A doesn't fully fix it.

Decisions:
1. Fix: **A**, B, C or A+C (A recommended).
2. xAI report: **withdraw** (recommended) or rewrite.
3. If A: approve the double-compaction proof on one Grok seat.
