The architecture deliberately keeps semantic authority at the hub. Node parity means an equivalent user outcome with correct machine ownership; it does not mean running a second scheduler, memory dream or database on the node. #17436 specifies no node datastore credentials, no local semantic fallback, opaque node paths, typed offline failures and machine-correct process/filesystem actions. A Python hub backend remains permitted at this milestone; completing every Stage 2 port and deleting Python on the hub would unnecessarily move the milestone.

**Two readiness gates:**

1. **Agent live testing can begin:** an isolated enrolled pair and the capability being tested exist. Transport-only checks can run before all provider duties and installation work are finished. No claim of full parity follows.
2. **Josh's extensive smoke can begin:** all inventory rows have executed live evidence, all five real providers pass their required cases, clean node installation/update and recovery pass, the budgets pass, and the packet reports no missing, broken or untested required workflow.

No daemon HTTP/DB access, secret-file reads, provider launches, process termination, source edits, task creation or task description edits occurred in this research. Gobby task/memory MCP reads supplied registry evidence. Test references below were inspected, not executed. A test's presence proves intended coverage; it does not prove a passing current run.

**Proposed latency budget and measurement**

Acceptance profile: local UI feedback is immediate; remote semantic work may add modest network cost. Use a measured warm direct-hub baseline B and node result N on identical request/data. Let R be node-to-hub request/response RTT, p95, measured immediately before each sample block. For each class, require both the absolute p95 and the added p95 limit below. Standalone is a second comparison and must appear in the report; direct hub isolates network/routing overhead from service implementation differences.

| --- | --- | --- | --- | --- |

Current reconnect defaults conflict with the proposed L9 warm recovery target in a sustained outage: `ChannelTiming::default`, `crates/gdaemon/src/nodes/channel.rs:35`, backs off from 1 s to 60 s, uses a 20 s attempt timeout and a 90 s idle timeout. Recovery can therefore miss 10 s even after the hub returns. This is a source-supported latency risk for F9/N4, not a measured incident. Either the executor improves recovery under the existing node lifecycle scope or Assistant obtains Josh's approval for a slower recovery budget. Never declare the proposed target already satisfied.

Measurement protocol: warm each bounded operation, collect at least 200 paired samples for L1–L6/L8 and 30 samples for process/workspace operations; report sample count and uncertainty for expensive real-provider cases. Do not infer statistically stable p99 from 30 launches. Capture p50/p95/p99 where sample count permits, max, errors and raw monotonic timestamps. Use client-side monotonic start/end clocks for end-to-end time; server stage spans use each host's monotonic clock and correlation IDs, without subtracting unsynchronized clocks. Measure an unloaded baseline and the intended concurrent seat count, stated explicitly. Run actual-network profile first; add controlled 20/50/100 ms RTT and bounded loss/disconnect profiles. The 100 ms profile is a degradation characterization, not a silent widening of the normal-network absolute budget. Large payloads, cold starts and provider-service outages are separate reported classes; they cannot dilute warm percentiles.

### Risks

- **Readiness overstatement:** generic HTTP/WS forwarding and a passing registration test do not establish local execution or full parity. Preserve status distinctions until live evidence exists.
- **Existing acceptance conflict:** #24603 intentionally prevents some remote worktree actions. Its safety behavior needs supported routed counterparts before parity, not a softer checklist.
- **Ordering conflict:** #21571 waits the complete Stage 2 port, while a Python-free node needs ordinary operator verbs earlier. Reconcile the milestone subset through Orchestrator. Avoid the #24604/#24657 cycle described in F7.
- **Real-provider prerequisites:** all five installed CLIs, service access, auth, SRT and composer admission are required. A transport-only or fake-provider proof cannot close #24604. Costs and missing prerequisites remain visible.
- **Latency remains proposed and unmeasured:** current backoff can exceed the proposed recovery budget. Budget/platform exceptions require Josh through Assistant. No default number in this report changes active policy.
- **Local effects can hide behind semantic success:** task close gates, skill scripts, code search, external stdio tools, voice, Git and workspace actions must use N's resources. Detect wrong-host effects with deliberately absent/different H paths.
- **Native takeover regressions:** after a family flips from Python to Rust, rerun its existing node parity evidence. #25201 specifically guards remote writes across terminal coordinator activation. Full hub Python retirement is not a prerequisite for the initial parity milestone.
- **Scope and execution safety:** do not touch fleet resources or credentials to make isolated tests convenient. Only Orchestrator delegates production restart/cutover and process/session intervention. This research report authorizes none.
- **Snapshot freshness:** task expansions and commits were arriving during the investigation. Re-read active rows/candidate identities before folding or launching work; older “needs-planning” prose is not proof that an expansion is absent.
