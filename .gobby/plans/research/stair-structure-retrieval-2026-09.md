# STAIR (structure-aware generative retrieval): applicability to Gobby

Date: 2026-09-25. Researcher gobby#14550, for Comms gobby#14069 (Josh's request).
Paper: Kumar et al. (IBM), "STAIR (STructure Aware Information Retriever)", arXiv 2609.03874, submitted 2026-09-03.

## Verdict: don't use

Gobby can't adopt STAIR as written. The model has to be retrained whenever the corpus changes, and every corpus Gobby searches changes daily. What is left to borrow is using a document hierarchy as the address space, and Gobby already does that.

## Claim check (source post vs. paper)

| Claim | Status | What the paper says |
| --- | --- | --- |
| Recall@1 82.6% | VERIFIED | 82.6% for STAIR vs. 76.9% for plain DSI on the authors' new SearchTome benchmark (18 books, 6 domains). |
| Beats BM25 and DPR | VERIFIED, on this benchmark only | BM25 59.5%, DPR 68.7%. Both are old baselines. There is no comparison with modern dense retrievers, hybrid search or re-rankers. |
| Hallucination rate < 0.05% | VERIFIED, but narrower than the post implies | "Hallucination" means generating a document ID that is not a valid table-of-contents leaf. It is not answer hallucination, and constrained decoding over valid leaves almost guarantees a low number. |
| "65x less than fine-tuned RAG" | NOT IN PAPER | The figure appears nowhere in the paper. It comes from the social post. |
| No vector DB, embeddings or re-ranker | TRUE, but a trade | The index lives in LoRA weights of Mistral-7B-Instruct v0.2, trained per corpus (up to 200 epochs) on synthetic queries generated by Mixtral 8x7B for every paragraph. |

Other facts from the paper:
- Out-of-the-box Mistral with the same structure scores 13.8% Recall@1, so the gain comes from fine-tuning. Prompting with a table of contents does not produce it.
- The paper reports no training cost or inference latency.
- It describes no path for updating documents; new content means retraining.
- The authors limit their claims to corpora with a global structure, such as books.

## Fit against Gobby surfaces

- **Memory retrieval** (`src/gobby/memory/`: vector store, keyword, Falkor graph, RRF merge in `memory/services/_search_rrf.py`): no fit. Memories are written, updated and "dreamed" continuously, and they have no table of contents. Differentiable search indexes (DSI) are known to forget when retrained incrementally.
- **gcode search**: no fit. Code changes with every commit. gcode already addresses code structurally (outline, symbol-at and repo-outline) with exact symbol IDs and no model.
- **Skill and reference loading**: already covered. Skills use hierarchical path addressing (`references/<area>/<topic>.md`) with router tables ("Load when ..."). The agent picks a valid path from a listed table of contents, which is STAIR's addressing idea without the training, and `get_skill_file` rejects invalid paths deterministically.
- **Handoffs**: no fit. There is nothing to retrieve; handoffs are one structured document per session.
- **docs/**: this is the closest match, a stable hierarchical corpus. Even so, it changes weekly and is small enough that gcode search plus the markdown heading outline already finds the right section. A per-corpus LoRA would cost a GPU training pipeline and re-training on every docs change, all to serve a corpus small enough for lexical search.

## Cost if we tried it anyway (INFERRED)

- A local GPU or a hosted fine-tuning pipeline.
- Synthetic-query generation for every paragraph, meaning one LLM call per paragraph and per retrain.
- Retraining on every content change.
- Serving a 7B model for retrieval, compared with the millisecond-scale BM25 and vector lookups Gobby uses today.

The trade is strongly negative for every Gobby surface.

## Idea worth keeping (no new work proposed)

Validating the chosen address against the set of valid IDs is what drives the paper's near-zero "hallucination". Gobby already applies the same principle wherever an agent names a path or ID: skill paths, tool schemas and task refs. Nothing to file.
