## Research Findings

### Research Questions

- Task #25351, **Research: runner-first 1.0 port (Rust owns the daemon runner, Python becomes a library)**. Researched 2026-10-30 in the main checkout; researcher gobby#18618. This report informs proposal #25352 and changes no implementation or existing plan.
- What does Rust already own, what remains in the Python runner, and what must move before “runner port complete” is an accurate milestone?
- What callable Python boundary permits Rust lifecycle ownership while preserving domain behavior?
- Should that boundary be a supervised process or PyO3 embedding? How should a runner config switch and smoke comparison work?
- How does runner-first reorder every cloud-port chunk in `.gobby/plans/task-25341.md` and the Stage 2 families of #21542?

### Domain Context

**Recommendation.** Make runner-first the first implementation chunk of the full chunked cloud port. Extend the existing Rust supervisor into the lifecycle owner; retain one supervised Python domain worker behind the existing private backend boundary. Extract callable initialization, recovery, maintenance and shutdown operations from Python. Port domain families in the existing later chunks. Do not introduce PyO3 for this migration: it adds a second event-loop integration and interpreter packaging problem without removing Python execution or its GIL.

This work needs to exist: Rust supervision is already implemented, but service lifecycle orchestration remains Python-owned. Calling the existing supervised `python -m gobby.runner` architecture “runner-first complete” would deliver no new ownership. Conversely, porting every rule, cron action, pipeline transition and MCP implementation before calling the runner complete would collapse the entire domain port into the first chunk. The useful boundary is **Rust owns when work starts, is admitted, recovers, repeats and stops; Python initially implements the requested domain operations and their internal continuations**. [E1–E8]

**Latest scope and precedence.** The task originally asks whether to reshape the cloud plan. Subsequent Orchestrator relays of Josh's 2026-10-30 instructions clarify that the full port still happens in cloud chunks; runner-first comes first and is smoke tested with a config switch. Another relay says to assume the drain tasks are complete before the push and size resumable chunks to the available account usage window. These are planning inputs, not evidence that the drain is currently complete or approval to push. This report preserves #25341's existing cloud restrictions, local gates and D5 roots unless the proposal receives an explicit changed ruling. No tasks were created, edited or reparented.

**What “Python library” means here.** It is a Python package called by a small, supervised process adapter, rather than a Python process that chooses the daemon's startup graph and runs its own top-level supervisor. It still needs Python and its dependencies on the hub until the last library family is ported. It does not introduce Python onto the Rust node. The process adapter owns its asyncio execution context and connection cleanup; Rust owns daemon lifecycle policy. Library-owned socket readers and in-flight coroutine state can remain until their family moves. They must be explicit service handles, not hidden schedulers or autonomous restart recovery.

**Boundary choice.** The process option reuses current mechanisms and wins the restraint test. Embedding remains technically possible; no proof-of-concept benchmark was performed.

| Criterion | Supervised Python domain process — recommended | Embedded Python via PyO3 |
| --- | --- | --- |
| Existing fit | Reuses `BackendSupervisor`, loopback backend, credentials and HTTP streaming; add a bounded internal lifecycle command surface | Adds interpreter linkage and runtime bridges to a daemon already built around Tokio/process isolation |
| GIL | Python work still contends inside that worker; Rust-only lifecycle/transport work can execute separately. No promised speedup for a Python rule pass | Rust-only work can also run without the GIL, but entering ordinary Python still requires interpreter attachment/GIL. Embedding does not make Python handlers execute in parallel [X1] |
| Async | One owned asyncio loop in the worker, Tokio in Rust; byte messages cross the seam | `pyo3-async-runtimes` bridges futures/coroutines but retains Python's asyncio loop; event-loop references and test main-thread ownership remain explicit concerns [X2, X3] |
| Failure/stop | Existing child drain, refusal, process-group kill/reap and restart isolation remain available | Fatal extension/interpreter failures share the daemon process. A stuck interpreter call lacks the existing independently killable child boundary; cooperative cancellation still needs design |
| Packaging | Keep the current Python environment temporarily; delete the adapter with the last library family | Must package/link compatible libpython and all remaining Python dependencies as well as implement the library extraction |
| Cost | Serialization, a private API, bounded queues, reconnection and duplicate-command handling | Less serialization and direct object access, at the cost of cross-language lifetimes, locks, error conversion and two-runtime teardown |

The historical GIL evidence supports separation, not a claim of current measured speedup. The September evaluation records hooks/workflows holding 21.5% of GIL-holder samples on September 24 and 34–36% on September 25, mostly off-loop. Those are sampled occupancy figures, not CPU percentages or an Amdahl speedup prediction. More Python threads do not remove that contention. [E13] `docs/daemon-gil-profile-2026-09-25.pxd` is an untracked ZIP-format visual document (`file` and `unzip -l` inspected); it is not a Cython declaration or a directly readable profiler trace. This report relies on the committed interpretation and source call path rather than pretending to have re-derived the PXD image's numbers. Later measurements may differ.

**Proposed Python API and cut.** All names in this paragraph are proposed, not existing symbols. Reuse the existing private backend HTTP channel for versioned, authenticated internal lifecycle calls; keep ordinary HTTP/streaming routes on their existing proxy path until their family moves. The new adapter must bind a minimal authenticated control app before domain construction: today's fully constructed HTTP server cannot receive a command to construct itself. Use the inherited supervisor secret for this bootstrap control admission, then attach domain routes only after their phase succeeds. Do not build a generic RPC bus, remotely invoke arbitrary Python attributes, or serialize the entire mutable `GobbyRunner` object.

Required seam semantics: caller authentication stays fail-closed; loopback alone is not authority. Keep secrets in the inherited/private launch mechanism rather than argv or logs. Rust assigns generation and operation IDs; reject stale generations. A lost reply to an effectful call is **unknown outcome**, not permission to repeat it: reconcile against durable operation/domain identity before retry. Transaction boundaries stay inside the current domain owner. Cancel closes admission and requests cancellation; it does not assert that a thread stopped or a database transaction rolled back. Keep effect continuations attached to the daemon lifecycle, and close all worker handles within the existing overall shutdown budget. [E1, E2, E9, E12]

Do not add durable schema for every maintenance tick. Use existing domain IDs/claims for effects; add a narrow durable command record only for an effect that otherwise cannot distinguish completion from a lost response. Bound request size, concurrency, queue length, execution deadline and event buffering. Keep control requests separately admitted so a saturated domain worker does not consume every control slot; this still cannot make a GIL-stalled Python worker answer instantly.

Total planning envelope: **17 resumable implementation/verification checkpoints**, with L checkpoints split further if their branch cannot reach a working commit inside the available usage window. This is a partition recommendation, not a forecast that one account can complete 17 checkpoints. R5 can develop after R2, but merge shared seams serially. No family port is a prerequisite for the runner chunk except already required infrastructure/contracts; invoke its Python operation instead. No remaining domain leaf closes just because Rust invokes it.

**Usage-window execution.** Exact account capacity and “ultracode” consumption were not measured and cannot be inferred from lines of code. Before each launch, the operator/authorized coordinator checks remaining usage and reserves enough for committing, pushing the provider branch and reporting the exact SHA; no researcher credential or account actions. Assign the largest checkpoint that fits the observed previous checkpoint cost plus that reserve. Each session begins from a committed base with owned paths, frozen protocol version and focused tests; it ends with red/green/evidence commits, remaining work and next command. Account rotation resumes that record on its branch. It does not reset the task or permit a second implementation of the same ownership seam. Local merge/test/release proof remains local, after the assumed drain.

**Config switch proposal.** Add a typed, restart-bound top-level bootstrap key `runner: python | rust` in `~/.gobby/bootstrap.yaml`, parsed consistently in Python bootstrap and `gcore` bootstrap. This key is proposed; it does not exist in the inspected bootstrap struct. Start with `python` as the migration default; promote `rust` only at the runner landing gate. Keep `front_door.enabled`, `mode`, and `front_door.routes` independent: both modes keep the Rust front door and `BackendSupervisor`; node mode remains Rust-only and rejects an explicit Python runner selection. [E14; G10]

- `runner: python`: launch the existing Python runner, which owns its startup/recovery/schedulers/shutdown; Rust uses today's supervision path. Do not also start the new Rust service orchestrator.
- `runner: rust`: launch the minimal Python domain adapter, validate handshake, then Rust executes the lifecycle graph and schedules domain calls. The adapter must not call `run_daemon`, install competing top-level signal policy, run autonomous daemon recovery, or start duplicate maintenance/cron loops.
- The selector changes **orchestration owner**, not implementation language for every route. Keep the same family `proxy/native/compare` settings during runner smoke tests; otherwise a route migration can mask a lifecycle regression.
- Report selected/effective runner, worker generation and protocol version in bounded startup diagnostics. Unknown values, missing capabilities and conflicting `GOBBY_BACKEND_COMMAND` overrides fail before admission. Do not silently fall back to Python after Rust has started effects. Rollback means a controlled stop/restart with the previous selector and compatible binaries, retaining one owner and reconciling durable work.
- Both modes can coexist in the release while migrating. Remove the selector and Python path only at Stage 3's approved retirement, after every remaining Python library obligation is delivered. This switch is a requested migration control, not a permanent product abstraction.

**Smoke comparison proposal.** Use the existing isolated-daemon test harness (`tests/e2e/conftest.py`, including `spawn_daemon_instance` and alternate `runner_module`) as the starting fixture, extended by the implementing team. No live smoke tests or daemon operations were performed during this research. [G11]

1. Start from one sanitized database/fixture snapshot and identical config, clock inputs, hook envelopes and operation identities. Run Python mode, then Rust mode against separately restored isolated state/ports/homes; compare normalized outcomes and durable effects. Never run two effectful orchestrators against the production database to “compare.”
2. Exercise cold start; content refusal; unavailable optional service/degraded readiness; config initial snapshot and hot revision; HTTP/WS reconnect; terminal adoption; hook replay during restart; session/handoff/wake reconciliation; one cron claim; pipeline recovery; MCP connection and tool call; cancellation; shutdown and restart. Verify exactly one owner/job and one intended domain effect, preserved ordering/receipts, bounded admission and finalization, no leaked children and correct missing-service behavior.
3. Fault the **isolated** worker before effect, after durable effect/before reply, during streaming, during recovery and during shutdown; simulate stale generation, wrong protocol, lease loss and refusal exit. Verify unknown-outcome reconciliation, no blind effect replay, bounded drain and terminal survival. Compare lifecycle transcripts and database/receipt state, not just HTTP status or body.
4. Capture startup/recovery timings, runner responsiveness under a busy Python worker, shutdown duration and error classes. Compare to measured Python-mode baseline; establish any numeric regression budget in the executable proposal from those measurements. This report supplies no invented latency threshold or claimed performance result.
5. After isolated parity passes, conduct a coordinated local canary using the selector and the same route settings, record exact installed binary/source/schema identities, and prove rollback. Keep #25341's separate B0 Tasks compare soak of at least 72 hours and its operator fan-out gate; the runner smoke does not replace them. [E15]
