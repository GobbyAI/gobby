Severity anchors from SKILL.md (paraphrased): critical means unauthenticated code execution, full-store access or arbitrary-account takeover; high fully defeats an explicit control with real consequences; medium has limited blast radius or uncommon preconditions; low exposes non-secret internals or minimal gain; informational has minimal confirmed impact. Explain likelihood separately from impact and cap overall severity at demonstrated impact. `needs_validation` receives no severity. This is an upstream methodology, not a proposal to replace Gobby's approved/rejected attestation result enum.

Gobby comparison:

- **Keep:** installed auditor 2.2.0 already requires independent exact-full-SHA `security-review` attestations, approval/rejection history, supersession, commands/results and truthful limitations. It cannot implement, format, commit, land or close. Boundary mapping produces a security_paths proposal for operator approval through the Assistant and Orchestrator.
- **Existing procedure:** both installed prompts load `code-review` and language skills. Neither references a dedicated security-auditor procedure. Repository inventory contains the generic `src/gobby/install/shared/skills/gobby/references/agents/procedures/code-reviewer.md`; its installed reference version 2.1.0 was read through `get_skill_file`. It requires exact candidate/worktree, independent review, criteria and source evidence, and preserves the author's files. This is general review guidance, not a security-specific evidence rubric.
- **Existing skill:** installed `code-review` supplies OCR file/status scope, per-file reviewed/skipped accounting, severity/category/location findings and source evidence hashes. It silently discards likely false positives. Security-specific evidence would benefit from retaining refuted hypotheses and precise blockers separately from reportable findings. Its source is `src/gobby/install/shared/skills/code-review/SKILL.md`.
- **Gap:** “focused isolated checks” in the auditor prompt does not enumerate the hostile-code execution controls above. A returned definition's `network: none` field alone is not proof of OS enforcement. No runtime enforcement claim was tested here.

Ranked recommendations (proposals only):

1. **Evidence and severity contract.** Add `src/gobby/install/shared/skills/gobby/references/agents/procedures/security-auditor.md`; update both prompts in `src/gobby/install/shared/workflows/agents/security-auditor.yaml` to load it. Require actor, input, intended control, crossed boundary, effective authority, affected resource, source trace, strongest preventing controls, conditions, observed result and narrow invariant-enforcing fix/regression suggestion. Separate confirmed findings, blocked leads and refuted claims inside existing attestation evidence. Preserve approved/rejected results; unmet decisive security criteria cannot silently count as met. Adopt the demonstrated-impact ceiling. Expected effect: fewer speculative findings and more reproducible verdicts.
2. **Gobby-focused checklist in that procedure.** Add memory provenance, action/argument binding, MCP identity/correlation, delegation authority, IPC peer/resource identity, and retry/resume/batch alternatives. Load optional domain details only when relevant. Expected effect: cover Gobby's distinctive boundaries without expanding seat authority.
3. **Explicit safe verification limits in that procedure and both auditor prompts.** Separate source-only checks from target-controlled execution, list required containment, dummy data and minimum effects, and record missing controls as precise blockers. Preserve isolated test-hub requirements. Verify available enforcement before claiming compliance; wording alone supplies no sandbox. Expected effect: prevent audit execution from exposing daemon state, credentials or other seats.
4. **Proportional coverage table in that procedure for explicitly routed broad boundary audits.** Record boundary, current source ref/paths, checks, disposition, blockers and comparison with prior source. Routine diff review keeps OCR's existing file accounting. Expected effect: expose omissions and stale assumptions without importing a new ledger engine.

Every implemented bundled definition/reference/skill change needs its repository-required version bump; the research report changes none of those files. These proposals are not an implementation plan or permission to launch a runbook.

Do not adopt wholesale:

- Automatic hunter/verifier spawning and six phases for every review. Gobby already has independent approval and explicit orchestration authority; a fleet hunt requires a separately authorized runbook decision.
- Another JSON registry/validator stack as approval authority. Exact-SHA PostgreSQL attestations already own that responsibility; begin with structured evidence in the existing carrier.
- Default external output paths, private source copies or artifact promotion promises that conflict with registered workspaces. Preserve the safety invariant; actual safe promotion requires implemented APIs, not prompt text.
- Checklist-only vulnerabilities or severity for unresolved deployment assumptions. Those would undermine the strongest parts of the upstream method.
