# The chunk protocol

Every chunk follows this protocol; each chunk task's brief holds what is specific to that chunk. docs/port/map-v2.md holds every decision and assumption, and docs/port/rulings.md every operator ruling.

## Steps

1. Run step 3's gport start check first, from the main checkout, and claim nothing while it refuses. Then claim the chunk task in a default-agent session, spawned by the port dispatcher or operator-opened (D39, D116), in a task worktree off 0.9.0 at the launch base that check recorded. An operator-opened session makes that worktree with gobby-worktrees:create_worktree(branch_name=<branch>, base_branch='0.9.0', task_id=<task>), because git worktree add and the provider's own worktree tool are refused in it (src/gobby/install/shared/workflows/rules/worker-safety/block-git-worktree-mutations-interactive.yaml:5; src/gobby/install/shared/workflows/rules/worker-safety/block-native-enter-worktree.yaml:5); its own directory stays the main checkout, so it works in the worktree by absolute path and names that path in every Workflow agent's prompt. A session the dispatcher spawned finds this check done and this claim made, and starts at step 2. If get_worktree_by_task (gobby-worktrees) finds a worktree for this task, an earlier session on it stopped or died. The stale claim sweep releases a dead session's claim (src/gobby/storage/tasks/_automation.py:89); until it has, get_task names the owner, and claim_task(force=true) takes the claim once get_session shows that owner is no longer active. Reuse that worktree, settle its uncommitted files, and resume after the branch's last checkpoint commit, rebuilding any lost scratch report from the branch. If that session's candidate already landed, only step 8's close remains.
2. Merge 0.9.0 into the worktree, and rerun differential replay for every touched family that is ported or in flight. From P0-RECORD's landing on, read docs/port/record.md next: this chunk's Found Work section, its family's debt-not-to-port list and owned rows, the frozen seam contract section and the known-bad index, because step 4 builds on them. Read this chunk's Found Work section again after every later merge of 0.9.0: a seam change or a fix from A may have added a line to it (step 9, D40 item 3), and this chunk handles that line before it lands.
3. gport start <chunk id>, run before the claim as step 1 says: every depends_on chunk's Gobby task is closed with closed_reason done, and for every kind except checkpoint its linked commit is an ancestor of 0.9.0 HEAD; it records the launch base. Until P0-RECORD lands gport, check the same rule by hand with get_task. gport is never promoted, so it is not on PATH: run it as cargo run --locked -q -p gobby-port -- <arguments>, in the main checkout for start and in the worktree for check-slice and ledger, because a path-invoked ./target/debug/gport counts as script execution, which the task gate refuses a session with no claim (src/gobby/install/shared/workflows/rules/task-enforcement/require-task-before-edit.yaml:18). A task outside the map, such as a review's no-go fix or a fix or port between reviews (D40 item 3), is filed as a child of #21542, so the port dispatcher starts it (D116). It has no chunk id, so gport start and gport check-slice refuse it: it checks its dependencies by hand with get_task, skips check-slice at step 6 and follows every other step. A fix that completes a closed chunk's row updates that chunk's docs/port/status/<chunk id>.json with its evidence line, because D17's rate reads that file.
4. Run one ultracode Workflow (at most 16 subagents): the debt-not-to-port pass, the oracle recording first when the brief says so, adversarial design review, tests rewritten from contracts, implementation, adversarial code review.
5. Use 1-3 checkpoints, each a commit on the chunk branch plus a scratch report. A chunk with ledger rows keeps docs/port/status/<chunk id>.json, one entry per row (P0-RECORD); a row marked done names a red commit and a later green commit on this branch, so commit each failing test before the code that passes it, because gport check-slice refuses a done row without both SHAs in its range. While the Workflow runs, the session yields with wait_for_coordination(background_task_id=<the Workflow's provider task id>, timeout=3600), omitting owner_session (src/gobby/mcp_proxy/tools/coordination.py:45-49), and registers it again after every timeout wake and after every prompt; after a compaction it fetches the wait tool's schema again first. A stop message that names this chunk, from a review's no-go or a cutover's outcome 3, holds the session at its next checkpoint, landing nothing, until the matching release message arrives; it waits with wait_for_coordination(owner_session=<the dispatcher>, reply=true, timeout=3600), registered again after every timeout and every prompt. It does not wait on the sender, because a review's fixes outlast the session that sent the stop, and a wait on a session that has ended returns owner_ended at once and leaves this run to the idle check (src/gobby/agents/idle_check_handler.py). The release is a project send with wake=true, which reaches a session holding a claim whichever session it waits on.
6. Validate locally: cargo tests, the isolated full-daemon harness (never the live hub, never ~/.gobby/bin), the dormancy proof (code defaults replay every existing corpus unchanged), gport check-slice <chunk id> --task <this task's ref>, and gport ledger, or scripts/port/check_coverage.py until gport ledger's diff is 0. Managed SRT changes what some checks prove inside a spawned session: a test that launches an agent under SRT fails there, because macOS refuses a nested profile (tests/e2e/conftest.py:416-424); a process check can miss what it may not inspect (docs/guides/gterminal-development-guide.md:450-458); and a proof that a non-loopback connection fails passes there whatever the code does. Docker is refused there too (src/gobby/agents/srt_settings.py:63-64). Send such a check's test command and this worktree's path to the port dispatcher with send_message(target='parent'), register wait_for_coordination(owner_session=<the dispatcher>, reply=true, timeout=3600) as step 8 does, and cite the reply in the validation attestation (D116).
7. Spawn the independent code-reviewer seat on the task worktree with spawn_agent(agent='code-reviewer', worktree_id=<this worktree's id, from get_worktree_by_task>, claim=false, prompt='Review <full SHA> of <task ref> in <worktree path>. Send your verdict and findings with send_message(target=parent). No pipeline, lead or claim hand-off applies here; land, merge and close nothing.'). It takes no task_id, as Josh's 2026-11-03 rule says, so the claim stays with this session, and claim=false joins the tree at its HEAD, because without it the spawn merges the base into the tree, which moves the candidate, and refuses a tree that a live session has claimed (src/gobby/mcp_proxy/tools/spawn_agent/_implementation.py:470, 512-529; src/gobby/mcp_proxy/tools/spawn_agent/_worktree_reuse.py:57-116, 119-149; tests/mcp_proxy/tools/spawn_agent/test_associated_worktree_join.py:28). The seat starts on the provider project_policy names, whose CLI must be on P (D119). Wait with wait_for_coordination(owner_session=<the seat>, reply=true, timeout=3600), registered again after every timeout and every prompt. When a wait ends without a reply and gobby-agents:list_running_agents no longer shows the seat, spawn it once more with the same arguments; a seat still listed after three such waits counts as lost once stop_agent ends it. A second loss escalates the task to Josh, and once he says the seat can start, run de_escalate_task and claim_task and resume at this spawn. Fix and recheck, stop it, then record the seat's result and the candidate SHA on the task as an attestation. Send nothing to a session on A: the security auditor and coordinator gobby#19309 that Josh's 2026-11-03 rule names run on A, and no chunk depends on cross-machine messaging (D40 item 5). If Josh opens a coordinator seat on P, send the SHA to it as well; the security-auditor seat on P takes only the candidates named below. A candidate whose changed paths match project_policy.security_paths, whose task carries the security-review label or whose brief names a security review, a gated chunk under D106 among them, also waits for the security-auditor seat that Josh opens on P (D115), because land_commit refuses that exact SHA without the seat's approved security-review attestation, and a spawned default-agent session cannot spawn the seat itself: after step 8's merge and version bump and before land_commit, send it the task ref and the resulting commit's full SHA, with target='session' and the session ref that gobby-agents:list_running_agents gives, then register wait_for_coordination(owner_session=<the seat>, reply=true, timeout=3600) and register it again after every timeout and every prompt. On a rejection, fix, rerun the code-reviewer seat and send the new SHA; every changed SHA needs its own approval. If a landing during the wait changed a path this candidate also changes, and the gdaemon version line usually is one, merge 0.9.0 again, bump again and send the new SHA before land_commit, because land_commit refuses that candidate (step 8). When list_running_agents shows no live seat, at the send or after a wait that ends without a reply, escalate the task to Josh, who reruns D115's command, and land nothing until the seat has approved. Escalation releases the claim, so once Josh says the seat is live, run de_escalate_task and claim_task and resume at the send.
8. Merge 0.9.0 into the worktree again. A chunk session lands and bumps, and never promotes (D39): on P it never runs gobby install, gobby cutover or gobby rollback restore (GEN-ROLLBACK's live drill is the one planned exception, D39), because gobby install rebuilds and promotes gdaemon whenever its managed pin is above the installed version, which every landing's bump makes true (src/gobby/cli/install_setup_gdaemon.py:79-112, 141-170), and rebuilds gclient, gmcp and gterm on every run; its landing bumps gdaemon by 0.0.1 when its fingerprint changed since its last bump, and leaves gcode, ghook, gmcp, gclient and gterm to the next activation commit, because the gcode and ghook pins are runtime floors (src/gobby/code_index/gcode_versions.py:5-6; src/gobby/hooks/runtime_compat.py:17, 28). A chunk that carries schema inputs or, after TPL, a template change lands its dormant code here and puts those inputs and its own tests that need them, validated with that code in the isolated harness, in one prepared commit on port/prepared/<chunk id>, recorded by SHA at close, which the checkpoint cut that needs it lands in its step 6 (D22). A chunk whose code or tests need a schema that a depends_on chunk's prepared commit carries, and that lands before the cut that lands that commit, applies the upstream prepared commit (its SHA is on that task's close record) only to its isolated harness tree, which for a spawned session is a local scratch branch in this worktree because its write scope stays on this worktree, never to its landing candidate, and puts its own tests that need that schema in its own prepared commit on port/prepared/<chunk id>, based on the upstream one and recorded by SHA at close; the same cut lands it right after the upstream commit. CI on 0.9.0 never runs a test that needs a schema 0.9.0 does not carry. During a landing freeze, send the cutover session a direct message, then register wait_for_coordination(owner_session=<cutover session>, reply=true, timeout=3600) and register it again after every timeout and every prompt; the cutover session messages back when the freeze clears. The merge and the bump make a new candidate SHA, and land_commit refuses a candidate whose implementation, test-after, validation and self-review attestations name another SHA (src/gobby/install/shared/workflows/rules/task-closure/coding.yaml:115-126). So commit them, link that commit, rerun step 6's checks on it, and record those four attestations on its full SHA, implementation before test-after (:86-93), with the self-review citing the seat's result and the SHA the seat reviewed. The seat runs again only when the merge resolved a conflict outside the version lines. Then land_commit onto 0.9.0 and push 0.9.0. A spawned session can neither push nor read CI, because spawn_agent runs it under managed SRT with no git network and no git or gh credentials (src/gobby/agents/sandbox_gate.py:22-33; docs/guides/sandboxing.md:245-249), so it sends the landed SHA to the port dispatcher with send_message(target='parent'), registers wait_for_coordination(owner_session=<the dispatcher>, reply=true, timeout=3600), sends again after a timeout with no reply, and registers the wait again after every prompt; the reply is its CI result (D116). Check the pushed commit's CI, then record the closing attestation and close_task with that attested SHA, never a generated land merge's, because a validation attestation has no landing-receipt exception (:95-113). If land_commit refuses with base_update_required or merge_conflict, because another landing moved 0.9.0 through a path this candidate also changes, it has also escalated the task and released the claim (src/gobby/tasks/land_commit.py:441-456, 657-670, 685-687; src/gobby/storage/tasks/_transitions.py:417-456), so this session resumes it itself: de_escalate_task, claim_task, then this step again from its merge, with the attestations the new SHA needs.
9. Found work follows AGENTS rule 4. From P0-RECORD's landing on, a line goes under the Found Work section of the chunk it concerns in docs/port/record.md, in the commit that fixes it; gport check-slice passes a Python or frozen seam path outside this chunk's slice only when a Found Work line under this chunk names that path. A seam contract change is found work of this kind: it lands on 0.9.0 in the owning seam file, with any landed caller it breaks fixed in the same commit so that 0.9.0 stays green, and in-flight chunks pick it up when they merge 0.9.0 (steps 2 and 8).

A checkpoint review instead follows the manual protocol in its goal (escalate_task, then de_escalate_task after Josh's go, then close_task), and a cutover chunk follows its nine steps. A corpus or golden case that a plan gives a waiver citation keeps its recording until the activation commit that flips its surface, which lands the citation: a citation makes the case fail while the old answer serves, so it would fail step 6's dormancy proof. Until then the chunk's own replay reads a fixture copy of the entry and citation in its tests, which tells the cut what to land (D48). Where a family plan, a task card or other pre-map text disagrees with a map decision or a chunk's explicit text, the map wins; docs/port/plan-drift.md lists the disagreements known at approval, and a chunk that finds another records it under Found Work. Where the map is silent, the plan applies. A map choice that proves broken is a gap: report it through Found Work instead of working around it from the plan. No chunk landing adds an entry to docs/contracts/parity-waivers.json or changes the parity ledger, even where a family plan's leaf says it appends its entry: the entry lands with its citation in the activation commit that flips its surface, because each entry writes a Waived note on a ledger row that the old answer still serves (scripts/generate_parity_ledger.py:190-194) and gdaemon embeds the manifest (crates/gdaemon/src/front_door/waivers.rs:12) (D84). A CI run that a later push to 0.9.0 cancelled (.github/workflows/ci.yml:16-18) is superseded, not red: step 8's check records that and goes on, because the later push's run covers the commit, and a red result there is found work for the session that landed it (D85). Plan short names in briefs: s2-11 is .gobby/plans/s2-11-hub-hooks-rules.md; S2.7 is .gobby/plans/s2-7-hub-attention-dispatch.md; sessions, the sessions plan and sessions-family are .gobby/plans/sessions-family.md; memory and the memory plan are .gobby/plans/memory-family.md; code-index is .gobby/plans/code-index-family.md; agents-family is .gobby/plans/agents-family.md; tasks-family is .gobby/plans/tasks-family.md; the AI plan is .gobby/plans/gdaemon-ai-providers-family.md; the Projects plan is .gobby/plans/gdaemon-projects-files-docs-family.md; the multiplexer plan is .gobby/plans/external-mcp-transport-multiplexer.md; gmcp-stdio is .gobby/plans/gmcp-stdio.md; hub-mode is .gobby/plans/hub-mode.md; DR1-DR8 are in .gobby/plans/rust-rule-evaluation.md; and #25341's numbered sections are in .gobby/plans/task-25341.md. A plan's text that a later Python fix changed does not apply: on that point the port follows Python at the chunk's base, because its corpora record that behavior, and the session notes the plan's stale text under Found Work. A usage limit or a provider outage is not a red result and closes nothing, and the branch stays. A spawned session that one stops loses its pane and its claim once the watchdog ends the run with a provider terminal reason (src/gobby/agents/lifecycle_monitor.py:663-683; src/gobby/agents/idle_check_handler.py:293-300), and the replacement the port dispatcher starts afterwards resumes under step 1 (D116). An operator-opened session keeps both: a usage limit holds its pane on the provider's menu, where no wake lands until Josh submits a prompt there after the reset (src/gobby/hooks/event_handlers/_misc.py:80-84, 377-378), and after an outage its next wake or prompt reaches it. Whichever session resumes reruns the stopped Workflow from the branch's last checkpoint commit (step 5). crates.io or GitHub down is an outage too, so retry after the next wait. A brief over 15,000 characters comes back from get_task as an offload envelope whose preview holds only its first 2,000: read the whole brief with gobby-results:get_tool_result, following next_offset until it is null, and call get_task again after the 7-day retention (src/gobby/config/features.py:127-143; src/gobby/mcp_proxy/tools/results.py:149-188). A port carries every trust check in the module it ports, named in its brief or not: whatever refuses, bounds, redacts or confines untrusted input, with Python's negative tests replayed as native cases, because a recorded corpus holds no attack and a missing check passes replay. A native HTTP client keeps its Python client's policy: httpx follows no redirect by default and reqwest follows ten, so each client sets redirect::Policy::none() unless its Python source sets follow_redirects=True, and trust_env=False becomes .no_proxy(). A native route that reads a body states its limit, because axum's body extractors stop at 2 MiB by default and Starlette has no limit. A native child whose Python spawn passes env= calls env_clear() and sets that map, because Rust's Command inherits gdaemon's environment (D124). A chunk that reuses existing native code lists Python's steps on that path against the native code's before its oracle runs, and ports each missing step or reports it under Found Work, because an oracle that compares native output with native output proves nothing about parity (D124). Josh approved this map on 2026-11-05 with every default (ruling 23), so a decision status that waits on his word at map approval is settled.

## Branching

0.9.0 is the integration branch on the port machine (P), and P's main checkout sits on it (D40). Each chunk works in its own task worktree off 0.9.0 (for example 0.9.0-rust) and lands with ordinary land_commit. Nothing merges into 0.9.0 from another branch, and D1's option A is not built. Python fixes, POST-CLEAN and Stage 4 all land on 0.9.0. This machine (A) forks 0.9.0 at the cut SHA as 0.9.0-gg, which is append-only (never rebased, amended or force-pushed), and the pre-cut branch freezes at the cut (ruling 15). A's gobby fixes land on 0.9.0-gg and reach 0.9.0 only as cherry-picks with -x that a cutover lands after its review approves them (D40 item 3). In the other direction, A adopts a checkpoint, when Josh decides and in checkpoint order, by running that cutover's steps on its own install and merging its port/<checkpoint id> tag into 0.9.0-gg in step 6's place, after its own backup and rehearsal (D40 item 4). The start gate moves project_policy's integration branch to 0.9.0 on P and to 0.9.0-gg on A, through 0.9.0-gg's policy commit, which is never picked; it rewords AGENTS.md rule 15's prose (AGENTS.md:128) while its dated operator ruling stays verbatim, rewords rule 10, and makes the 0.9.0 runs of ci.yml and rust-ci.yml required on push and on pull requests (D34, D85).

## Live checkout constraints

The live daemon runs from the 0.9.0 checkout, so every landed commit must keep it working:

- No template moves before S3-DELETE.
- A template edit lands only as A17-TEMPLATES allows: a ruling 6 bug or friction fix, or a rewrite that preserves behavior on Python's engine, such as RULE-1A's. The live daemon must accept it unchanged, it carries its rule-17 bump, and once TPL declares the template tree as an embedded input it also bumps gdaemon and is a prepared commit that the next checkpoint cut lands in its step 6, under that cut's backup, and that cut's activation promotes it (ruling 20).
- Migrations are expand-only until CP-FINAL-CUT (D22). A chunk's schema inputs (its migrations with their assets.rs entries, and the tests that need the new schema) form one prepared commit on the append-only branch port/prepared/<chunk id>, reviewed with the chunk and recorded by SHA at its close; the first checkpoint cut whose activation needs that schema lands it in its step 6, after the verified backup and the rehearsal and immediately before the activation commit, under the same freeze. Between cuts no landing changes the schema pin, because gobby restart and hub-backup refuse while the checkout's pin differs from the installed identity (src/gobby/storage/schema_divergence.py:251-265, via src/gobby/cli/daemon_preflight.py:67-77). The preflights accept a cut's migrations only with a pin generated from a real build, a regenerated catalog manifest, transactional migrations inside the 5 s lock and 60 s statement limits, serial numbers and no edited applied migration. From CP-RUNNER-CUT on every retained generation accepts a hub ahead by expand-only receipts (SCHEMA-WINDOW), so a rollback across an expand step is the binary restore plus the deactivation commit; only a drop, at CP-FINAL-CUT or POST-CLEAN, needs the backup restore.
- Python edits are dormant (D4), except bug fixes, R-RETIRE's refusal and GEN-ROLLBACK's generation-retaining promotion. That promotion is live at landing, so the generation each cutover pins is already retained.
- Every later pinned generation finds its Python worker code in the checkout, because nothing in Python is deleted before S3-DELETE, no worker-op registration is removed before it, and worker protocol changes are additive.
- 0.9.0 stays restartable at every landed commit and promotable at every checkpoint cut: a landing bumps only gdaemon, between checkpoint cuts no landing changes the schema pin, the gcode or ghook floor or, after TPL, a template, and only a checkpoint cut promotes (D39).

## Rollback and packaging

Families are library crates on gcore inside one gdaemon (D36). GEN-ROLLBACK keeps three generations, each with a manifest (D38). A cutover sets a hold whose token every promotion and restore in it must pass (gobby rollback hold set, then --hold-token on gobby cutover, gobby install and gobby rollback restore), pins the generation installed at that moment, and sets a landing freeze bound to its own task, so land_commit admits only that task's session. gobby cutover also promotes gmcp and gterm when their versions changed. A restore names its members (--bin, gdaemon alone by default, and always the stamped set gcode, gdaemon and ghook for a cut that changed the schema identity) and burns the activated versions, never the restored target's own. Dormancy is code defaults only (D37). From CP-RUNNER-CUT on, every retained generation accepts a hub ahead by expand-only receipts (SCHEMA-WINDOW), so a rollback across an expand step is the binary restore plus the deactivation commit, which reverts the cut's schema inputs with its activation, and loses no write. A rollback across a drop (CP-FINAL-CUT and POST-CLEAN only), or across CP-WAVE3-CUT's attachment relocation once it ran, is a backup restore first, after every live agent seat is ended, with the seats relaunched once the restored daemon is healthy, and it loses every write made after the backup. Every cutover recipe uses only install-local state (its own verified backup, the same schema inputs, its own pin, hold and generations), so A runs that whole cutover on its own install when it adopts a checkpoint, with the tag merged in step 6's place after its own backup and rehearsal (D40).

### D17: Calibration gate thresholds for CP-TEMPLATE-REVIEW and CP-WAVE3-REVIEW.

Default (unresolved): Proceed when the D11 rate (partial+stub)/(done+partial+stub) is at most 5% of owned rows, the final replay pass has zero unexplained compare mismatches with every mismatch class triaged (fixed, known-bad, or an accepted contract change), and differential replay is 100% equal or classified.
