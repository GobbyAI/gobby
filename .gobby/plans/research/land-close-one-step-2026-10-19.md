### Research Questions

- Can landing and closing share one operation without weakening the close gates or allowing a dependent task to start before its blocker closes?
- What do today's landing, landed retest, activation, preview, Gate 13, Lane Manager release and Release Manager GO actually require?
- How much observed land-to-close time belongs to activation, Gate 12 correction, validation and coordination, and what would a one-step change remove beyond existing policy?

- Activation class and close criteria answer different questions. **3. Feasibility and minimum module changes if a later implementation is justified**

A combined waitable operation is feasible for source-only work. It would remain a sequence of durable stages, not one atomic Git/PostgreSQL transaction. The existing asynchronous review queue can carry the long work. Retest and paid review must stay outside MainCheckoutLanding. A short final locked promotion must verify the exact source, current integration tip/tree, policy/approvals, task state and accepted evidence, then promote and finalize closure. No downstream unlock occurs before close commits.

The full prelanding design needs more than calling close_task from land_commit:

| Area | Required change or invariant |
| --- | --- |
| src/gobby/tasks/land_commit.py and MCP _landing.py | Split trial preparation from shared-checkout promotion; retain exact source SHA, base tip, trial commit/tree and idempotency identity. Reacquire MainCheckoutLanding for final recheck/promotion. Preserve freeze, independent-review, overlap, schema-carrier and operator approval checks. |
| close_integration_credit.py, close_checklist.py and candidate/run matching | Add narrow daemon-attested trial evidence. Current LandedCandidateCredit rejects an unlanded descendant. Bind each run to clean tested content and required target/environment inputs; never broaden acceptance to any unlanded worktree. |
| task_repo_paths and close evaluation/finalization | Resolve the trusted trial checkout without losing the original owner's attribution, claim window, registered machine and dirty-path checks. Keep the source candidate and trial integration SHA separate. The task's reviewed patch must not become the entire integration merge or unrelated upstream work. |
| validation.py and _lifecycle_review_gate.py | Include the trial integration context in stable evidence. Current stable keys at validation.py:36-44 include source commits/candidate, attribution and close_receipts, but no trial tree. prepare_task_review hashes task/criteria/summary, diff, test bodies, stable facts and policy: validation.py:75-152. Tests/criteria must be judged in the validated integration context, not just against the original patch. |
| Receipt/fingerprint transition | A prelanding review has no actual landing receipt. Writing that receipt afterward changes stable close_receipts and would stale today's verdict. Model an authenticated promotion transition and separately require its actual receipt before close; do not fabricate a prelanding receipt, silently omit receipt changes, or bypass all fingerprint checks. |
| _lifecycle_close_orchestration.py and close-review storage | Persist and resume the combined operation across queueing, reviewer rejection, daemon interruption and promotion/finalization retries. Preserve FIFO capacity and authenticated verdict submission. The orchestration module is already 993 lines in this snapshot, so added implementation must respect the repository's under-1,000-line ceiling. |
| Installed seat definitions/admission evidence | Preserve reviewer/author/LM/RM responsibilities or make the approved delegation explicit. LM release must be a verifiable admission, not an incidental quoted message. Installed DB definitions are the live configuration. Activation remains mandatory wherever stored criteria or the correctness of a gate fix require it. |

Timing implication: moving the retest and a 4.84-15.61-minute paid review before the ref move can make the displayed land-to-close interval nearly zero. It does not eliminate that test/review time from candidate-to-close or blocker-to-dependent readiness. Only eliminated handoffs, avoided redundant validation, useful overlap and genuinely unnecessary activation waits improve that end-to-end metric. Tip movement can instead add repeated work.

That is not a measured current distribution. It affects live-proof tasks; it is already irrelevant to eligible source-only closes. It cannot justify closing a live-proof blocker early.

### Risks

- **Tip drift:** path-disjoint changes can still affect imports, fixtures, schema, runtime configuration or test discovery. Recompute the trial after a moved tip and invalidate all affected evidence. A tree equality check can preserve content evidence only alongside renewed ancestry, policy, task and approval checks.
- **Review rejection:** retain the task open and correct the candidate before promotion. A changed SHA needs renewed exact-source approval and affected validation. Holding the shared landing lock through tests or paid review would serialize unrelated work and is inappropriate.
- **Git/DB interruption:** current code already recognizes ref-moved/receipt-pending. A combined operation needs replayable landed-but-not-closed recovery; it must neither roll back other shared work nor unlock dependents on an optimistic success response.
- **Live-proof and gate-fix circularity:** a trial source tree cannot change the running daemon's gate implementation or prove installed-binary behavior. Keep such tasks open until required activation/proof is complete. #24522 Hub checkout seam explicitly waited for #24744 Gate 12 recalled pytest RED to close before its fresh preview. An implementation must not claim a gate fix is credited merely because the trial contains it.
- **Authority/evidence weakness:** #24737 gmcp session guard demonstrates that even all deterministic gates and a valid code verdict can coexist with a missing procedural release/retest. A combined API must strengthen the binding of these facts rather than normalize that exception.
- **Measurement gap:** exclusive activation-wait, Gate 12 correction, validation and coordination totals cannot be reconstructed for every task from current receipts and prose. The tables preserve mixed intervals and unmeasured components. Record source/trial/tree, stage request/admit/start/end, target/environment identities, invalidation reasons and review/promotion/close outcomes before claiming a throughput improvement.
- **Decision scope:** this is research, not an implementation plan or authorization. Any later operator choice goes through the Assistant. No one-step change is proposed for immediate implementation.
