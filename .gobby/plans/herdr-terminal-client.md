# Herdr-Derived Terminal Client and Native PTY Runtime

**Plan ID:** herdr-terminal-client

## O1: Overview

`kind: framing`

Build `gclient` — the `gobby-client` TUI derived from the Apache-2.0 herdr codebase — and a backend-neutral daemon `TerminalRuntime` contract with two implementations: the existing tmux stack and a new Herdr-derived native PTY host (`gterm`). `gobby` remains today's Python daemon and Click CLI (`start`, `stop`, `status`, `tasks`, …). Users run `gclient` for the workspace. Gobby's daemon and Postgres stay authoritative for projects, sessions, runs, tasks, worktrees, attention, and lifecycle; the host owns only live PTYs, terminal emulation state, scrollback, and recoverable runtime snapshots.

Research findings that shaped this plan (herdr @ the `v0.8.0` release tag, commit `346411fa`, 2026-08-03 — "the fork point"): herdr has no Rust terminal emulator — its VT engine is vendored libghostty-vt (Ghostty's full Zig source tree, ~18 MB, built with `zig` at compile time via `-Demit-lib-vt`, a build mode of the full tree with no separable upstream artifact). Herdr is already a headless-server/thin-client system with a mature bincode frame protocol (two negotiated encodings, multi-client, detach/reattach, per-terminal attach) — this plan adopts and rebrands that protocol rather than designing a new one. Herdr's Ratatui workspace UI runs server-side; Gobby inverts that seam: `gclient` (crate `gobby-client`) renders a Gobby workspace fed by the daemon (roster, attention) and attaches per-terminal frame streams from the host, importing herdr's generic UI chrome (sidebar, tabs, navigator, status, keybind help, dialogs, scrollbar, widgets — ~13.5k LOC) rewired to Gobby data sources and restyled to the Gobby design system (3.3). This is a **one-time fork, owned outright after import** — no upstream tracking, no mechanical re-pin; individual post-fork upstream fixes may be cherry-picked deliberately with provenance recorded in `UPSTREAM.md` (1.2, 1.5). Roughly a third of herdr's ~200k Rust LOC is imported; its agent detection, plugins (deferred to D1), worktrees, integrations, updater, session persistence, JSON API, and app orchestration are not. Upstream lives at `herdrdev/herdr` after its GitHub org migration.

The shipped web terminal (`.gobby/plans/activity-panel-live-terminal.md`) documents tmux-inherent defects this work eliminates for Gobby-managed terminals: cross-socket identity collisions, smallest-client sizing shrinking simultaneous viewers, duplicated VT query replies from multi-viewer relays, and the 200×50-default post-attach repaint handshake. The native backend is also the recorded path to Windows support (ConPTY) once macOS/Linux parity lands.

## C1: Constraints

`kind: framing`

- **License gate (supersedes the sibling constraint).** `herdr-interface-backend-foundation.md` C1 states "herdr is AGPL-3.0. Ideas only — no code". That constraint is superseded: herdr relicensed to Apache-2.0 in commit `cd5ea1be` (2026-07-22), the relicense is recorded in the **released** `v0.8.0` changelog (2026-08-03), and this plan forks from that tagged release. Remaining accepted, documented risk: upstream ships no NOTICE file, and the AGPL→Apache consent mechanism for ~8 outside contributors is not documented in-repo. Apache-2.0 §4 attribution and modification obligations are honored via deliverable 1.5.
- **Fork-once, own outright.** The import is a one-time fork at `v0.8.0`; there is no upstream tracking and no re-pin procedure. Post-fork upstream fixes are adopted only as deliberate per-commit cherry-picks recorded in `UPSTREAM.md` (1.2 names the initial set; 1.5 owns the log format). The registered reference clone lives at `~/.gobby/clones/herdr`.
- **Topology: the terminal stack must survive the daemon's future.** Today `gobby` is the Python daemon and Click CLI. Evolution (`docs/architecture/evolution.md`, not this epic) replaces that daemon with `gdaemon` (`gobby-daemon`) in `standalone` / `hub` / `node` modes and later renames the `gclient` binary to `gobby`. Migration order is absorb-subsystems → standalone parity → mode split with machine registration and API keys. Consequences pinned here: the Python surfaces this plan adds in P2–P4 are the *node-mode capability set* and are kept thin — the durable contract is the JSON-lines control protocol, the bincode frame protocol, and the backend-neutral WS messages, all of which survive the language migration byte-for-byte (the golden corpus is the enforcement); `gclient` couples to the daemon only through the public HTTP/WS API, never internals; the 2.5 WS message set doubles as the future hub↔node-daemon relay contract for hosted web viewing (D3 owns the relay privacy stance); `gterm` is permanently a separate supervised process — folding PTY ownership into the daemon would forfeit terminal durability across daemon restarts and active/standby lease handoffs, which is the property this plan exists to buy; and `gclient` is permanently a separate interactive process and a separate binary (the VT payload is host-only, so multi-call packaging would bloat every client install). This epic does not rename either binary.
- **`vt-engine` feature gate.** The Ghostty engine (vendored tree, `build.rs` Zig invocation, `src/ghostty/` FFI, and the pane emulation built on it) sits behind a `vt-engine` cargo feature of `gobby-terminal`, enabled by the `gterm` binary and disabled by default. `gobby-client` depends on the light modules only (wire protocol, input encoding, layout, theme) and builds without Zig; protocol-only tests do too.
- **Full-tree vendor.** libghostty-vt is vendored as Ghostty's full source tree at herdr's recorded pin (`c5a21edfcbc2d5b46540ad91b7980aca31f5f1f3`), herdr-style — verbatim `vendor.json`/`patches/` workflow — because `-Demit-lib-vt` is a build mode of the full tree, and pruning would mean owning a curated fork of Ghostty's build graph. Mitigations: code-index and lint exclusions (1.4), nested-license inventory (1.5).
- **Zig is a build-time dependency** (Zig 0.15) only for builds that enable `vt-engine` — the `gterm` host binary and its CI jobs. `gobby-client` and protocol-only test runs never invoke Zig. End users receive prebuilt release binaries; the installer's local-cargo fallback behavior for these crates is defined in 3.6.
- **Naming.** `crates/gterminal` → package `gobby-terminal` → binary `gterm`; `crates/gclient` → package `gobby-client` → binary `gclient`. Users run `gclient` for the TUI. `gobby` stays the Python Click daemon CLI. This epic does not add a `gobby client` wrapper and does not exec the TUI from the Python entry point (3.5). Renaming the `gclient` binary to `gobby` is evolution, not this plan. The `gclient` binary name avoids colliding with the Python `gobby` entry point and with `~/.gobby/logs/gobby-client.log` / `gobby-client-error.log` already used by the daemon restart helper (`src/gobby/servers/routes/admin/_lifecycle.py`). Host logs to `~/.gobby/logs/gterm.log`; TUI logs to `~/.gobby/logs/gclient.log`.
- **Transport.** Host endpoints are Unix domain sockets under `~/.gobby/` with mode 0600 (`gterm-control.sock`, `gterm-frames.sock`). No new TCP port: 60889 and 60891 are already bound (web-dev UI / managed Postgres) and 60890 is the Stage-1 `gdaemon` sidecar / compare-delegation port (`ROADMAP.md`; nothing binds it yet). Windows named-pipe support arrives with the later Windows milestone; the imported `ipc` layer already abstracts both.
- **No attach-capability token system in this epic.** Local sockets are same-user 0600, and frame clients additionally present the existing install-scoped local CLI token (`~/.gobby/local_cli_token`, the same credential gcode/gwiki already use). Web viewers reach native terminals only through the daemon's WS proxy (4.3), where daemon auth already applies. Short-lived per-terminal capabilities are deferred until a remote/web-direct attach surface exists (D2).
- **The two host sockets do not share a credential, and the trust boundary is the local user account.** Frame clients present `~/.gobby/local_cli_token`; the control socket accepts only `~/.gobby/gterm-control.token`, a separate 0600 file the daemon mints on first host spawn and which no client is ever given (3.1). This is stated as what it is: a same-uid process that can read `~/.gobby/` can forge either credential, so nothing here defends against a hostile process running as the user — that is outside the boundary on both macOS and Linux, and no local mechanism moves it. What the split does buy is that possession of a *client's* credential is not possession of write authority: gclient must hold `local_cli_token` to talk to the daemon at all, and under a shared credential that same token would also unlock every mutating verb on the control socket. The frame protocol additionally has no write verb to reach (3.2), so the read-only guarantee does not rest on the credential alone.
- **Daemon authority.** The host never talks to Postgres and holds no durable state beyond optional scrollback snapshots on disk. All lifecycle, attention, task, and session semantics stay in the Python daemon. Host crash → affected native terminals are marked `orphaned`, affected runs become `interrupted`, and Gobby's normal resume flow applies; live PTYs are never reconstructed.
- **No silent backend switching.** An explicitly requested native launch fails clearly when the host is unavailable; it never falls back to tmux silently. tmux remains a first-class backend for externally launched/discovered sessions indefinitely.
- **SRT sandbox semantics preserved.** Managed provider commands are wrapped by SRT once, after construction and before terminal creation, with `allowPty: true` and fail-closed preflight. The native spawn path (4.2) wraps identically before handing the command to the host. Only the daemon and `gclient` (both unsandboxed) dial host sockets; sandboxed agent processes never do.
- **No backward compatibility.** 0.5.0 is unshipped: tmux-specific columns and WS message names are replaced, not aliased.
- **Session lifecycle unions stay lifecycle-only** (per the sibling plan): attention and terminal state are orthogonal dimensions, never new `SessionStatus` values.
- **Schema changes land in the gcore baseline, not numbered SQL files.** `src/gobby/storage/migrations/` is empty and retired: schema authority is Rust `gcore` (`crates/gcore/src/schema/assets.rs`, `BASELINE_VERSION = 375`, applied via `gdaemon schema apply`), pre-0.5.0 changes fold into `crates/gcore/assets/schema/baseline.sql`, and numbered `EmbeddedMigration`s resume only after the release boundary. A schema change here therefore edits `baseline.sql`, refreshes `BASELINE_CHECKSUM` in `assets.rs`, and updates `crates/gcore/assets/schema/catalog.manifest.json` plus the Python identity mirror `src/gobby/storage/schema_expected_identity.json` — the same shape as commit `4a5b8f9e3`. 2.1 follows this mechanism.
- **Rust conventions.** New crates join the workspace per `crates/CLAUDE.md`: scope all cargo commands with `-p`, never relax lints, register in `rust-ci.yml`. The workspace `members` list is `["crates/gcode", "crates/gcore", "crates/gdaemon", "crates/ghook", "crates/gwiki"]` today; 1.2 and 3.3 append the two new crates. `gobby-terminal`/`gobby-client` keep herdr's edition 2021 to minimize import churn (herdr at v0.8.0 is edition 2021 with no MSRV pin) and pin `rust-version = "1.88"`, the workspace floor shared by all five existing crates (edition 2024; mixed editions are supported). `tokio`, `ratatui`, `crossterm`, and `portable-pty` are first *direct* dependencies in this workspace — tokio already appears transitively in `Cargo.lock` via gcore's `postgres` feature — and they are confined to these two crates; `ghook`'s tiny-binary/no-async policy is unaffected.
- **Testing.** Focused runs only: `GOBBY_TEST_PROTECT=1 uv run pytest <paths>` for Python, `cargo nextest run -p <package>` for Rust. PTY-spawning Rust tests run in a serialized nextest group. Never the full pytest suite.

**The state constraint has to admit a terminal that never existed.** Requiring a locator for every non-`pending` row contradicts the spawn-outcome matrix 2.3 owns: a definitive pre-effect failure and a cancellation between row creation and backend spawn both produce an `exited` row for a resource that was never created, so there is no locator to record and inventing a synthetic one would make the partial UNIQUE index collide on the placeholder. `exited` therefore joins `pending` as a state where the locator may be null, and `live`/`orphaned` still require it — those are exactly the states something can be attached to or reaped from. The complementary rule is enforced in code rather than in SQL because "was ever set" is not expressible in a row-local CHECK: `promote_to_live` is the only writer of `locator`/`locator_key`, and nothing ever nulls them, so a row that reached `live` keeps its locator through `exited` and a post-mortem can always name the resource that ran. The acceptance below pins both halves — the permitted null and the forbidden clear.

**`spawn_key` is a property of a spawn, and discovery has no spawn.** An externally discovered pane is observed already running; there was no caller to allocate a pre-effect name, and the row is inserted straight to `live` with a locator by `upsert_external`. A globally `NOT NULL` `spawn_key` would force discovery to fabricate a value that means nothing and that the reaper would then try to resolve against the backend. So the column is nullable and the CHECK ties it to ownership: `gobby`-owned rows must carry one (they were spawned), `external` rows must not (they were found). The UNIQUE index becomes partial to match, so any number of external rows coexist while gobby spawn keys stay unique.

**Every row-local promise is a constraint, not a comment.** Two invariants this section states in prose were previously enforced only by the code paths that happen to obey them, which meant a direct `INSERT` — a migration backfill, a repair script, a test fixture, a future deliverable's shortcut — could write a row the prose calls impossible. A `pending` row carries **no** physical identity at all: `locator`, `locator_key`, and `host_epoch` are null until the promotion CAS fills them, because none of those values exists before the backend effect. An `external` row carries a locator in **every** state, `exited` included: discovery observes an already-running pane, so there is no pre-effect window in which an external row could lack one, and an external row without a locator would describe a resource nobody can name. Both are now `CHECK` constraints, so the row-local cross-product of state, backend, ownership, and identity is closed at the table rather than at its callers, and 2.1.14 tests each illegal shape by direct insert rather than through a manager method that would refuse it anyway.

`locator_key` is the canonical identity of the physical resource, and the partial UNIQUE index above is what makes discovery idempotent under concurrency. Its form is fixed: `tmux:<socket_path>:<server_pid>:<server_start_time>:<pane_id>` and `native:<host_epoch>:<host_terminal_id>`. Native identity never includes a Unix socket path.

`machine_id` is required on every row, filled from `require_machine_id()` at `create_pending` and `upsert_external`. It is placement (where the PTY/tmux lives), the same column `agent_runs` already has. It is not a `user_id`. `session_id` is nullable `ON DELETE SET NULL`, so machine must not be derived through the session. Do not add `user_id`. #19650 has landed (`machines` is in the baseline): rebase this DDL onto that identity work; do not revert `users` / `machines` / `auth_sessions`. If #18879 (workflow-definition split) has landed, rebase onto that baseline the same way: add `terminals` and replace `agent_runs.tmux_session_name`; do not revert the domain tables (`rule_definitions`, `agent_definitions`, …). Both epics edit `baseline.sql` / checksum / catalog; neither owns the other's tables.

**Attach locators are computed, not stored paths.** `attach_locator` for native resolves `gterm-frames.sock` from local `TerminalHostConfig.socket_dir` and refuses when the live host's epoch does not match the row. The roster/REST `AttachLocator` is a request-time handle. A durable `host_socket` in the hub row would attach the wrong machine's host after Stage 3.

**Identity contains only what the owner cannot rename.** An earlier form of this key also carried `session_name` and `window_id`, which is wrong in both directions and breaks under ordinary tmux use. A `rename-session` changes the session name of the very same pane, so the next discovery computes a different key and inserts a *second* row for one physical terminal while the first goes stale; `break-pane` and `move-pane` change the window (and possibly the session) of an unchanged pane the same way; and a grouped session gives one pane two names at once, so two viewers of the same pane could disagree about its identity. `pane_id` (`%12`) is the value tmux itself treats as the pane's handle: it is assigned at creation, survives rename, move, break, and layout changes, and is never reassigned while the server lives. Identity is therefore socket path + server generation + pane id, and nothing else. Session name, window id, and title move into ordinary refreshable columns: they are re-read on every discovery pass and liveness tick, they are what the roster and the UI display, and they are never compared to decide whether two observations are the same terminal. The acceptance mutation-tests each one — rename, move, break-pane, and a grouped alias must all leave the row's identity and its `terminal_id` unchanged while updating the metadata.

The tmux server identity is part of the key because tmux reuses pane ids (`%12`) after a server restart — without it, a recycled pane id would collide with a stale row for a different physical pane. The pid alone is insufficient for the same reason `sessions.terminal_context` already stores `parent_create_time` beside `parent_pid`: the operating system reuses pids, so a tmux server that dies and restarts on the same socket while the daemon is down can be handed its predecessor's pid, and a pid-only key would then treat a brand-new pane as the old physical terminal. The key therefore carries a **server generation**: the tmux server's start time.

**The generation is read from tmux, not from the process table, so it cannot be a hybrid.** Deriving the generation from the OS — `ps -o lstart=` or `/proc/<pid>/stat` field 22, the source the existing `parent_create_time` guard uses — would require two reads of two different subsystems, and the server can die between them: the pid comes from a live tmux, the start time comes from whatever now owns that pid (or from nothing), and the resulting locator describes no server that ever existed. No amount of retry logic fixes a two-source read; it only narrows the window. tmux removes the need entirely, because it renders the generation itself: `#{pid}` is the server pid, `#{start_time}` is the server start time as Unix seconds, and `#{socket_path}` is the socket, all three expanded from one server-state read in one `display-message -p` invocation (verified on tmux 3.7b: `1658|1784592177|/private/tmp/tmux-501/default`). Every producer of a tmux locator therefore obtains socket path, server pid, server start time, and `pane_id` from a **single** `display-message` expansion — 2.5's two discovery producers and 3.4's attach path all obey this — and none may assemble a key from separately sourced parts. A server that dies before the read makes the whole command fail, so there is no partial result to misinterpret, and the acceptances test the same-pid/different-start-time case rather than only a changed pid.

**A stored generation is revalidated at every dereference, not just at discovery.** A correct locator still goes stale: while the daemon is down, a tmux server can exit and a replacement can claim the same socket path and hand out the same `pane_id`, and an attach that targets only socket plus pane id would then bind a stored row to a stranger's pane. So generation is not merely recorded — it is re-read and compared. Because it costs nothing to include, `#{pid}` and `#{start_time}` ride in the same batched expansion as the pane's own state on **every** poll (3.4) and on every liveness tick (2.5), and a mismatch against the stored `locator` is treated exactly as pane death: no frames are delivered, the row is marked `orphaned`, and rediscovery creates a new row rather than reviving this one. The residual is stated rather than hidden, and it is stated as a full tuple: a collision needs the OS to reuse the exact pid for a new tmux server **and** the same socket path **and** the same one-second `start_time` value **and** the same `pane_id`. All four coincide more readily than the pid term alone suggests — a live probe on tmux 3.7b restarted a server twice inside one second and got back the same socket path, the same `start_time`, and the same `%0` — so the pane-id existence check in the same read is *not* a backstop for this case: when the whole tuple matches, the existence check passes, the stale row binds the replacement server's pane, and there is no typed error and no detected mismatch. That outcome is explicitly accepted rather than claimed to be detected. The alternative was weighed and declined: a socket inode plus creation time would discriminate a replacement server, but reading it means a `stat` of the socket path at every dereference — a second subsystem read added to a locator whose whole correctness argument is that it comes from one tmux expansion, which is precisely the hybrid the paragraph above rejects. tmux itself exposes no finer generation than one-second `start_time`, so the honest position is the accepted residual: a same-pid, same-socket, same-second, same-pane restart binds silently, and everything coarser than that tuple is detected.

Two concurrent discoverers of the same pane (SessionStart and the liveness monitor, 2.5) converge on one row via `INSERT ... ON CONFLICT (locator_key) WHERE locator_key IS NOT NULL AND state IN ('pending','live') DO UPDATE`, which is safe to replay; a terminal that has reached `exited`/`orphaned` leaves the partial index, so the same physical locator can be rediscovered later as a new row rather than resurrecting a finished one.

**Pre-effect identity: `spawn_key` (gobby-owned spawns).** A row written before the backend effect cannot carry the locator of a resource that does not exist yet — the native `host_terminal_id` and the tmux window/pane ids are outputs of the spawn — so `locator` and `locator_key` are null while `pending` and are filled atomically by the `pending → live` CAS, guarded by the state-sensitive CHECK above. Nullability alone would still leave a hole: a tmux session created microseconds before the spawn call times out is a live resource that no row can name, so the stale-pending reaper could never find it. `spawn_key` closes that hole by being allocated by the caller *before* the effect and mandated as the backend's creation name. For tmux it is the session name the runtime must pass to `new-session`, deterministically derived as `gobby-<terminal_id>`; for native it is the `terminal_id` itself, which the host stores as opaque metadata from control `spawn` and echoes in `list` (3.1). The reaper therefore resolves any pending row to its possible effect by name on either backend — `has-session -t gobby-<terminal_id>` or a `list` scan — and kills what it finds. Runtimes may not choose their own names, and the UNIQUE index makes reuse of a `spawn_key` a database error rather than a silent collision.

`agent_runs.tmux_session_name` is replaced by `agent_runs.terminal_id UUID REFERENCES terminals(id)` (same baseline edit; no alias — C1). `sessions.terminal_context` **stays** for its non-locator roles (PID-reuse-safe kill via `parent_pid`/`parent_create_time`, handoff identity, `term_program`/`tty`/`cwd`); its tmux-locator keys seed `external`-ownership terminal rows during discovery (2.5).

`src/gobby/storage/terminals.py`: `TerminalManager` with hub-transaction CRUD (psycopg `%s` placeholders), `create_pending(terminal_id, machine_id, backend, ownership, spawn_key, rows, cols, ...)` called at spawn-begin with no locator, `promote_to_live(terminal_id, locator, locator_key, host_epoch)` which is the single CAS that fills the physical identity and flips `pending → live` in one statement, an idempotent `upsert_external(locator_key, machine_id, ...)` for discovery, and reap queries (`list_stale_pending`, `list_orphaned_by_epoch`, `list_live_by_epoch`, `list_live_by_machine`). Creating the row **before** the backend spawn closes today's orphan class (`docs/reviews/agents.md:162`: failed spawns leave tmux sessions no monitor reaps because no run row carries the name).

**The transition surface is an edge allowlist, not a generic setter.** The natural generalization of today's `clear_tmux_session_name` compare-and-clear is a public `transition(terminal_id, expected_state, new_state)`, and it is the wrong shape: a caller that passes `expected_state='exited', new_state='live'` gets a successful CAS and resurrects a finished terminal, which directly contradicts the rediscovery rule above — a locator that reappears must produce a *new* row, never revive the old one. The same setter also lets `orphaned → live` re-adopt a terminal whose host epoch is gone, and lets any state go back to `pending`. Row-local CHECKs cannot catch these, because each individual row is perfectly legal before and after; only the *edge* is illegal. So the CAS primitive is private, a module-level `_ALLOWED_EDGES` frozenset is the whole specification, and the public surface is exactly the five transitions the lifecycle needs: `promote_to_live` (`pending → live`), `fail_pending` (`pending → exited`), `mark_exited` (`live → exited`, `orphaned → exited`), and `mark_orphaned` (`live → orphaned`). `exited` is absorbing and nothing returns to `pending`. Anything outside the set raises rather than writing, so an illegal transition is a programming error caught in tests instead of a silently resurrected row.

**The indeterminate-write latch set lives on the row because the abstain rule outlives the call.** `unresolved_writes` is an empty object in the ordinary case and maps each logical `action_key` to `{at, origin}` when that action's effect cannot be determined (2.4). A single object-valued latch would be lossy: a second independent indeterminate action could overwrite the first and silently re-enable its automatic retry. The map exists here rather than in daemon memory because the consumers that must not resend are periodic, and a daemon restart between an indeterminate write and the next tick must preserve every unresolved action. Clearing is per key rather than time-based — a TTL would re-enable the duplicate it prevents — so positive observation or an operator resolution removes the matching key, while terminal exit clears the map.

`src/gobby/terminals/runtime.py` defines the contract, grown from the three existing seeds (`TerminalSpawnerBase` in `agents/spawners/base.py`, the `ManagedTmux` Protocol in `agents/capture.py`, and `_resolve_tmux_target` in `mcp_proxy/tools/sessions/_terminal_tmux.py` with the facade wrapper in `_terminal.py`):

```python
class TerminalRuntime(Protocol):
    backend: Literal["tmux", "native"]

    async def spawn(self, request: TerminalSpawnRequest) -> TerminalHandle: ...
    async def is_live(self, terminal: Terminal) -> bool: ...
    async def snapshot(self, terminal: Terminal, lines: int = 50) -> SnapshotResult: ...# visible text, detector input
    async def snapshot_full(self, terminal: Terminal) -> SnapshotResult: ...            # scrollback, post-mortem
    async def write_text(self, terminal: Terminal, text: str, submit: bool) -> WriteOutcome: ...
    async def write_key(self, terminal: Terminal, key: NamedKey) -> WriteOutcome: ...   # enter/escape/tab/up/down
    async def write_paste(self, terminal: Terminal, text: str) -> WriteOutcome: ...     # herdr paste_payload
    async def resize(self, terminal: Terminal, rows: int, cols: int) -> None: ...
    async def terminate(self, terminal: Terminal, grace_seconds: float) -> None: ...
    async def attach_locator(self, terminal: Terminal) -> AttachLocator: ...            # request-time handle; native path is computed, never a stored socket
```

`TerminalSpawnRequest` carries the caller-allocated `terminal_id` and `spawn_key` (2.1) plus command/env/cwd/dims/labels; `TerminalHandle` carries that row id plus the backend locator the runtime produced. `SpawnResult` (`agents/spawn_models.py:69`) drops its three tmux fields in favor of `terminal_id` + `AttachLocator`.

**A snapshot that was truncated must say so, all the way down.** Returning `str` throws away the one fact a caller needs to record a faithful artifact: whether it is looking at the whole output or the tail of it. That matters most exactly where it is easiest to lose — capture-before-kill on a long-running agent, whose scrollback is the largest and whose response is the most likely to hit the host's byte ceiling (3.2). Silently storing a short capture as if it were complete is a post-mortem that lies. So the contract returns `SnapshotResult(text: str, truncated: bool, dropped_bytes: int | None, total_bytes: int | None)` and the metadata is carried, not dropped, at every boundary below it: `NativeTerminalRuntime` (4.1) maps the host's `{truncated, dropped_bytes, total_bytes}` straight through, the capture-persistence path in 2.4 stores the flags beside the text so an artifact records its own completeness, and detector inputs ignore the flags but never see a different `text` than they do today.

**The counters are UTF-8 bytes, and a backend that cannot know a value says so.** Two details in that signature decide whether the metadata is trustworthy or merely present. First, the unit: the host bounds its response in *bytes*, so `total_bytes` and `dropped_bytes` count encoded UTF-8 bytes and nothing else. Comparing them against `len(text)` — Python's code-point count — is correct only for ASCII and silently wrong for every box-drawing character, emoji, or CJK glyph a real terminal emits, which is precisely the content most likely to be near the ceiling. Any assertion relating text to counters must therefore encode first (`len(text.encode("utf-8"))`), and truncation must cut on a code-point boundary so `text` is always decodable — a byte-exact cut mid-sequence would make the artifact unreadable to prove it was bounded. Second, the honest unknown: the fields are `int | None` because tmux genuinely cannot answer them. `capture-pane` returns whatever `history-limit` still holds, and lines evicted before the capture ran left no trace — there is no count of them to report, and a `dropped_bytes` of `0` would assert completeness that tmux never verified. So `TmuxTerminalRuntime` reports `truncated=True` with `dropped_bytes=None` whenever the captured history is at the limit (the pane may have lost more), `truncated=False, dropped_bytes=0` only when the history is demonstrably shorter than the limit, and `total_bytes=None` in the at-limit case since the true total is unknowable. `None` means "this backend cannot know", never "nothing was dropped", and consumers render it as unknown rather than as zero. The acceptance in 2.4 pins the persistence half and 4.2 pins an oversized wide-Unicode capture end to end.

**Paste is a write, encoded the way herdr 0.8.0 already does.** `write_paste` takes the clipboard/crossterm paste *text* (not pre-wrapped bytes). The runtime applies herdr's `paste_payload`: if the target's live `MODE_BRACKETED_PASTE` / `#{bracket_paste_flag}` is on, wrap `\x1b[200~{text}\x1b[201~`; otherwise send the raw text. Native encoding happens in the host (it owns VT mode) via control `write` `kind: "paste"`; tmux encoding happens in `TmuxTerminalRuntime`, which reads the pane's `#{bracket_paste_flag}` at write time — the host capture poll (3.4) only runs while a viewer is attached, so a poll-cached flag can be stale or absent — then `send-keys -H`. gclient and the browser never wrap. Cap is herdr's 1 MiB UTF-8 (`MAX_INPUT_PAYLOAD`); oversize is a typed refusal and does not disconnect (herdr #1665, already in the 0.8.0 import). HEAD after `v0.8.0` did not change `send_paste`/`paste_payload` — do not chase post-fork remote image-clipboard or Windows Terminal multiline paste (#670; ConPTY is out of this epic).

**Both backends can lose the answer, so the write outcome is a type and both runtimes produce it.** `write_text`/`write_key`/`write_paste` return `WriteOutcome` — `Delivered` or `IndeterminateWrite` — with genuine failures still raising typed errors, so a caller must decide what an unknown effect means instead of reading a `None` as success. An early form of this plan defined `IndeterminateWrite` as a native-only outcome on the theory that only a dropped control connection can lose a response. That is wrong, and it was disproved against a live tmux server: a `send-keys` whose reply is withheld leaves the client timing out **after** the keys have already been applied to the pane, so the tmux path produces exactly the same ambiguity through a different mechanism. `TmuxTerminalRuntime` therefore returns `IndeterminateWrite` when its `tmux` invocation times out or its client loses the response, and `NativeTerminalRuntime` (4.1) returns it when a control response is lost across a reconnect; neither retries on its own. The boundary that returns it also inserts the logical action into 2.1's `unresolved_writes` map, so the 2.4 rule applies identically whichever backend produced it. Nothing above the contract branches on backend to interpret a write result.

**Dimension bounds.** `src/gobby/terminals/dimensions.py` holds one shared bound set — minimum 1 row and 1 column, maximum 1024 rows, 2048 columns, and 1,000,000 cells (`rows * cols`) — mirroring the Rust constants pinned in 3.2, with the protocol document (3.2) as the single source of truth for the numbers. Every Python ingress validates before persisting a row, allocating a buffer, or forwarding to a backend: `spawn`, `resize`, the REST/WS surfaces (2.5), and the control client (4.1). Zero, negative, non-integer, and product-overflow inputs are rejected with a typed error rather than reaching an ioctl or an allocation, so an authenticated-but-wrong caller cannot make either process allocate unbounded memory.

**Output streaming is deliberately outside this contract.** `TerminalRuntime` covers lifecycle, snapshots, input, resize, and attach-locator resolution. Continuous output streaming stays backend-specific — tmux via its FIFO output reader, native via a daemon-side frame observer (4.2) — because the two transports have genuinely different shapes and a lowest-common-denominator method would hide that. Parity is asserted on the observable `terminal_output` event stream (5.1) instead of on a shared method, and no deliverable may claim streaming "through the runtime contract".

`execute_spawn` is the **sole** creator and transition owner of the pending row, per 2.1: it allocates the id, derives the `spawn_key`, writes the `pending` row with no locator, passes id and `spawn_key` inside `TerminalSpawnRequest`, and performs the single `promote_to_live` CAS from the locator the runtime returned. Every terminal outcome is spelled out so no path can duplicate or strand a row — backend spawn raising leaves the row `pending` for the stale-pending reaper (2.4) and CASes it to `exited` when the failure is definitive; a spawn timeout leaves it `pending` and reapable *by `spawn_key`*, which is the only way a session created just before the timeout can be found at all; cancellation between row creation and backend spawn CASes straight to `exited`; and a successful spawn whose CAS loses (row already moved) terminates the just-created backend terminal rather than leaving an unowned PTY.

**The concrete backend must stop minting names, or `spawn_key` is decoration.** The caller-owned identity contract is only real if it reaches the process that actually creates the resource, and today it does not: `TmuxSpawner._async_spawn` derives its own session name from a timestamp and a random suffix (`base = title or f"{prefix}-{int(time.time())}"`, `suffix = uuid.uuid4().hex[:8]`) and reports it back through `SpawnResult.tmux_session_name`. Left in place, the reaper would resolve `gobby-<terminal_id>` while tmux held a name nobody recorded, which is precisely the orphan class this plan claims to close. So this deliverable edits the spawner: the name-generation block is deleted, `new-session` is invoked with the `spawn_key` carried in `TerminalSpawnRequest`, the sanitization that made arbitrary titles safe becomes a validation of the caller-supplied key (a key that would need rewriting is a caller bug, rejected typed, not silently mangled), and the tmux-specific result fields are replaced by the locator the runtime returns. `title` survives as display metadata written to the terminal row (2.1), decoupled from identity. No `TerminalRuntime` implementation may generate an identity after this deliverable, and the acceptance scans for it.

**SRT wrapping hoists to one chokepoint at the runtime seam.** Today `SandboxLaunch.wrap()` is called from six sites — one per provider branch in `spawn_executor.py` (claude/qwen/grok/codex/droid) plus `resume_executor.py` — so "wrap once, after construction, before terminal creation" is per-branch discipline that every new provider and every new backend must re-remember. Since this deliverable already routes every spawn path through the runtime, the wrap moves with it: the shared step that hands a finished provider command to `runtime.spawn(...)` applies the SRT wrap exactly once, immediately before backend dispatch, and the provider branches keep only their command/env preparation. The `_preflight_srt` probe wrap in `srt_runtime.py` is a probe, not a spawn, and is unchanged. 4.2's native path then inherits the invariant structurally instead of reimplementing it.

**A young pending row is in doubt, not dead.** Absence of a resource proves nothing while its spawn may still be running, so no reaper or reconciler may treat `pending` as `exited` on absence alone. Two conditions must both hold: the row is older than `spawn_in_doubt_seconds` (`TerminalConfig`, 2.2, defaulting to the existing spawn timeout plus a margin), *and* resolving its `spawn_key` against the backend finds nothing. A row younger than that deadline is left alone and revisited. Retry of a spawn reuses the same `terminal_id` and `spawn_key` rather than allocating new ones, so a retry cannot create a second physical terminal or a second row, and a reconciler that runs concurrently with a retry converges on the one row either way. This rule is what 3.1's reconnect reconciliation and 2.4's reaper both consume; neither redefines it.

- **An indeterminate write needs one rule, applied by every caller.** 3.2 withdraws the cross-reconnect exactly-once guarantee for writes: when a response is lost, the boundary reports the effect as *indeterminate* rather than claiming success or failure, because no ledger that dies with the connection can answer the question. Reporting it honestly is necessary but not sufficient — a caller that receives `indeterminate` and treats it as either outcome reintroduces the bug in a new place. Today's surface has only `stage: none|partial`, so there is no branch to fall into: the attention route captures before injection and re-detects only known-partial errors, and the multi-write callers (idle reprompt's prompt-then-Enter, prompt auto-answer, the plan-keystroke sequences above) would continue to their next substep, or increment a retry counter, or resend on the next loop tick — each producing a double-typed prompt in exactly the case where the first one may already have landed.

  So `IndeterminateWrite` becomes a third outcome of the backend-neutral write surface, and there is exactly one rule for it, stated once and adopted verbatim by every consumer: **an indeterminate write is never retried and never advances state; the caller re-observes the terminal and decides from what it sees.** Concretely, a multi-step sequence aborts at the indeterminate step rather than sending the remainder; the attention route leaves the entry open and re-captures instead of clearing it; the idle reprompt and prompt-auto-answer paths leave their retry counters untouched so the next tick re-evaluates from a fresh snapshot rather than from an assumption; the memory watchdog and MCP `send_keys` return the indeterminate result to their caller instead of collapsing it to a boolean. Re-observation is cheap and already implemented — every one of these callers has a snapshot path — which is why abstain-and-re-observe is the whole policy rather than a per-caller matrix of compensations.

**The rule binds later ticks, not just the failing call.** Abstain-and-re-observe is sufficient only if re-observation can answer the question, and for these consumers it cannot: a prompt that was delivered and consumed and a prompt that never arrived can present the *same* snapshot, so an idle reprompt that abstains on tick *n* re-evaluates the identical state on tick *n+1* and sends the same bytes again — the duplicate the rule was written to prevent, arriving one interval later. So the write boundary inserts `{at, origin}` under the logical `action_key` in 2.1's `unresolved_writes` map at the moment it returns `IndeterminateWrite`, and every *automatic* write consults the map: a matching key is suppressed and reported as suppressed rather than sent, while unrelated unresolved actions remain independently protected. Positive observation or an operator resolution removes only the matching key; terminal exit clears the map. An operator write is never suppressed because a human deciding to retype is the resolution. Multi-step sequences use one sequence action key rather than one key per keystroke, so an aborted `Escape`/text/`Enter` wake does not create three entries.

- **`terminal_attach_result` is what makes the lease messages usable.** Every lease message below is scoped by `attachment_id`, and the browser has no way to construct one — the daemon mints it. `terminal_attach` therefore answers with `terminal_attach_result{terminal_id, attachment_id, mode, rows, cols, backend, frame_delivery}` on success and a typed error result carrying the same `terminal_id` on failure, and the frontend keys its per-pane state on the returned `attachment_id`. `terminal_create_result` and `terminal_kill`/`terminal_list` results are likewise defined as backend-neutral shapes rather than being left implicit, so the frontend has one exhaustive union to match on.
- **Writer-lease messages.** The daemon's lease policy needs wire shapes on this surface, or the web viewer cannot implement it. Three messages carry it, all scoped by a connection-local `attachment_id` the daemon mints on `terminal_attach` (one browser tab may hold several attachments, and `terminal_id` alone cannot say which): `terminal_take_control{terminal_id, attachment_id, takeover}` requests the lease; `terminal_control_result{attachment_id, granted, reason}` answers it, where `reason` is a typed refusal (`held`, `terminal_gone`, `host_unavailable`) rather than prose; and the server-initiated `terminal_lease_lost{attachment_id, holder}` event tells a displaced viewer to render read-only. `terminal_attach` gains `mode: "observe"|"control"` (default `observe`) and `frame_delivery: "direct"|"proxy"` (default `proxy`). `direct` mints the `attachment_id` and joins the lease record without opening a daemon frame relay — that is the local `gclient` path, which already reads `gterm-frames.sock`. `proxy` is the browser path: the daemon opens a host frame attach and relays `terminal_output` (4.3). On daemon-WS reconnect, a `direct` client re-registers every live pane and receives a fresh `attachment_id`; old ids are invalid; the pane stays observe/read-only until re-registered and then reacquires control through the normal take-control exchange. `terminal_input`, `terminal_paste`, and `terminal_resize` from a non-holding attachment are refused with the same typed reason instead of being silently discarded.
- **Attachment-local viewport vs lease-gated PTY resize.** 3.2 already splits host-frame `SetViewport` from control `resize`. - **One authority per terminal, and the host is not a party to it.** The lease is a daemon-held record keyed by `terminal_id`, owned by `src/gobby/terminals/leases.py` and created in this deliverable — before any host exists, because the browser surface needs it first. The design decision this pins is *which* process grants control, and there is exactly one answer: the daemon.

  An earlier form of this rule let the host enforce the daemon's decision, by admitting an attachment to a `Control` mode when it presented a daemon-minted lease token. That is one authority on paper and two in practice, because a token is a *replica* of the lease record and every replica needs a consistency protocol: a mint endpoint, a binding to the attachment and host epoch, a TTL and a clock the two processes agree on, a replay rule, revocation on takeover so a displaced holder's token stops working, and a reconciliation pass for a daemon restart that finds a host still honoring a token it no longer has a record of. None of that machinery was specified, and none of it needs to exist, because the token is only there to let a client write *directly* to the host.

  So clients do not write to the host. The host exposes exactly two surfaces (3.2): a **control channel** the daemon alone connects to, authenticated by a control token no client is ever given (3.1, C1), carrying every write the host itself can perform — spawn, input, resize, kill, all of them against host-owned PTYs; and a **frame channel** local clients connect to, which is **observe-only** and has no input verb at all. A tmux-backed terminal's writes never appear on either channel: the host only *observes* tmux panes (3.4), and the daemon writes to them directly through `TmuxTerminalRuntime`, so "the daemon is the only writer" holds across both backends by two different routes. There is nothing to mint, nothing to expire, and nothing to revoke. gclient takes control by asking the daemon over the surface it already uses for roster, spawn, and respond, and its keystrokes travel the same daemon path the browser's already do (3.3) — one extra hop, on a path already proven for the shipped web terminal, in exchange for deleting an entire distributed-consistency problem. The host still serializes the writes it receives, because two daemon-issued writes to one PTY would interleave bytes, but it makes no admission decision and holds no authority state. If the daemon is unreachable, every client is observe-only by construction: frames keep flowing from the host and no write can be issued by anyone. The single-authority acceptance is therefore a source-level fact — the frame protocol has no write verb — rather than a state machine to test.

`gterm host` is the first long-running Rust child in the repo; the daemon owns its lifecycle:

- **This leaf owns the control surface its own supervision consumes.** Health checks, adoption, and reconciliation below are all control-protocol calls, so the leaf that promises them must also implement them — a supervision leaf depending on a later protocol leaf would be a backwards edge. `crates/gterminal/src/host/control.rs` is therefore created here with exactly three things: the newline-delimited-JSON socket listener, the mandatory authentication handshake, and the two read-only verbs `ping` and `list`. The remaining verbs (`spawn`, `kill`, `resize`, `snapshot`, `write`, `subscribe_events`) and the whole frame protocol belong to 3.2, which depends on this leaf. Nothing here spawns a terminal, so the split is clean: 3.1 proves a host exists, answers, and can be inventoried; 3.2 makes it do work.
- **Authentication before the first verb, with a credential the clients never hold.** The control socket is 0600 on a same-user path, and it carries every mutating verb, so the credential it accepts must not be the one every frame client already has. The first request on every control connection must be `hello{protocol_version, control_token}`, answered with `{host_epoch, version, protocol_version}`; any other request on an unauthenticated connection is refused with a typed `unauthenticated` error and the connection is closed, and a token mismatch or unsupported protocol version is refused typed before any terminal state is read. `ping` is an ordinary post-hello verb rather than a credential carrier, because a request that both establishes and uses a connection cannot report rejection ordering cleanly. The control token is `~/.gobby/gterm-control.token`: 32 bytes of `secrets.token_urlsafe`, written 0600 by the daemon before the first host spawn, read by the host at startup, rotated whenever a host is replaced rather than adopted, and handed to no other process — `gclient` never receives it and has no need for it, because it writes through the daemon (3.3). Presenting `local_cli_token` on the control socket is refused exactly like any other wrong token. The frame socket keeps its own `Hello{version, encoding, local_token, ...}` (3.2) validated against `~/.gobby/local_cli_token`; both handshakes appear in the golden corpus with negative cases, including the cross-credential ones. Neither credential defends against a same-uid process that reads `~/.gobby/` (C1 states that boundary plainly); the split exists so that a legitimate client's credential is not by itself write authority.

- **Host (Rust).** `crates/gterminal/src/host/` written fresh against the keep-set (herdr's 10k-line `server/headless.rs` is app-UI-coupled and not imported): a tokio process that owns `PaneRuntime` instances keyed by host-terminal id, binds `~/.gobby/gterm-control.sock` and `~/.gobby/gterm-frames.sock` with 0600 modes and stale-socket reaping (imported `ipc` layer) — serving the control verbs named below, with the frame protocol attached to the frames socket in 3.2 — generates a fresh `host_epoch` UUID per start, writes `~/.gobby/gterm.pid` and logs to `~/.gobby/logs/gterm.log` (env-filtered `tracing`). PTYs survive client disconnects by construction (host owns them). Graceful shutdown drains PTYs with SIGHUP then SIGKILL after a grace period.
- **Supervision (Python).** `src/gobby/terminals/host_manager.py`: spawns `resolve_native_bin("gterm")` with `start_new_session=True` (the detached-child pattern from `servers/routes/admin/_lifecycle.py:130`), health-checks via a control `ping` (which returns `host_epoch` and version), restarts on crash with backoff, and on epoch change marks `native` terminals of the old epoch `orphaned` and their runs `interrupted` (2.1 CAS) so Gobby's normal resume flow applies — live PTYs are never reconstructed (C1). Constructed at the runner composition root; startup health failure degrades native availability without failing the daemon (mirroring `_check_tmux_health`).
- **Adopt before spawn.** Host lifetime is decoupled from daemon lifetime, so daemon startup **adopts** rather than replaces: the manager first dials the existing `gterm-control.sock` and authenticates with the persisted control token (which is why that token is a file rather than a per-spawn secret: the daemon that adopts is usually not the daemon that minted it), issues `ping`, then validates the protocol version against its own floor, the reported PID against `~/.gobby/gterm.pid` (and that the PID is live and is a `gterm` process, guarding PID reuse), and records the returned `host_epoch`. A host passing every check is adopted with its epoch and terminals intact and no orphaning; a replacement is spawned only when no socket answers, the PID identity fails, or the protocol version is incompatible (in which case the stale host is drained first, then its terminals orphaned by the existing epoch-change path). A planned daemon restart (`gobby restart`, the reload path in `servers/routes/admin/_lifecycle.py`) leaves the adopted host running; only an explicit full stop (`gobby stop`) drains it, terminating PTYs with the configured grace. This is what makes the 5.1 and E1 daemon-restart continuity requirements reachable — without it a straightforward manager would replace the host on every restart, change the epoch, and orphan every native terminal.
- **Surviving the daemon's own child reaper.** Adoption is unreachable unless shutdown stops killing the host. `_preserved_agent_terminal_pids` lives in `src/gobby/runner_lifecycle_processes.py` (not `runner_lifecycle_shutdown.py`) and currently builds the survive-restart PID set from *agent runs that have a `tmux_session_name`*. `_run_async_shutdown_cleanup` in `runner_lifecycle_shutdown.py` hands that set to `reap_remaining_child_processes` under `ShutdownIntent.preserve_agents`. A `gterm` host is not an agent run and carries no tmux name, so it is reaped on every restart today. This deliverable makes the preserved set terminal-backed: for `preserve_agents` shutdowns it includes the host PID from `~/.gobby/gterm.pid` (identity-checked as in the adoption bullet) plus its PTY children, and the migrated tmux branch selects on `pending|live` terminal rows instead of the removed field (the reader 2.4 deliberately left here). A full stop (`preserve_agents` false) drains the host through the control protocol with the configured grace and then lets the reaper proceed, so `gobby stop` leaves no stray PTYs.
- **Adoption reconciliation matrix.** Verifying host identity is not enough: the daemon can die between the host-side effect and the database commit, so adoption reconciles both directions. The host's `list` response returns the daemon-supplied `terminal_id` (the host keeps it as opaque metadata from `spawn`), which makes the join possible at all. Every cell is defined: DB `pending` + host has the terminal → CAS to `live` with the reported locator and epoch (this is the crash-after-spawn-before-CAS case that would otherwise leave a live PTY behind a pending row); DB `pending` + host does not, **and the row is past the 2.3 in-doubt deadline** → CAS to `exited` and reap by `spawn_key`; DB `pending` + host does not but the row is *inside* the deadline → left `pending` and revisited on the next sweep, because a spawn issued moments before the disconnect may still be executing and its terminal may not yet appear in `list` (exiting the row here is what would make the eventual successful spawn lose its CAS and get killed, turning a recoverable connection loss into a failed launch); DB `live` + host has it → adopt unchanged; DB `live` + host does not, same epoch → CAS to `exited` and run the normal finalization; any DB row from a different epoch → `orphaned` with its run `interrupted`; and a host terminal whose `terminal_id` is unknown or absent from the database → killed after a bounded grace and logged, because no owner can ever claim it. The destructive unknown-terminal branch is reachable only after both the host `list` and the database inventory read succeed in the same sweep. A database read failure makes the inventory indeterminate, kills nothing, records the typed failure, and retries the entire sweep after backoff. Reconciliation runs on adoption and on every reconnect of the control client (4.1), not only at startup, and it never runs concurrently with a retry of the same `terminal_id`: the spawn caller holds the row and the reconciler skips in-doubt rows, so the two cannot both decide the outcome.
- **Operator visibility.** `TerminalHostConfig`-derived host state is reported read-only through the existing daemon health/status surface (`src/gobby/servers/routes/admin/_health.py`, alongside the degraded-services list that `_get_degraded_services` builds): enabled/running, adopted-or-spawned, `host_epoch`, protocol version, restart count and current backoff, live and `orphaned` terminal counts, and the last startup or health-check error. `gclient` (3.5) surfaces the same diagnostic when the selected or default backend needs the host, so "native launches are failing" is diagnosable without reading `~/.gobby/logs/gterm.log`. This surface never mutates host state.
- **Config.** `src/gobby/config/terminal_host.py`: `TerminalHostConfig` (`enabled`, `socket_dir` default `~/.gobby`, `binary_path` override, `health_interval_seconds`, `shutdown_grace_seconds`), wired into `DaemonConfig` (`app.py`) beside `TmuxConfig`; 3.4 adds the three keys only its poll loop consumes (`tmux_poll_interval_ms`, `tmux_poll_backoff_ceiling_ms`, `max_attached_terminals`) to the same model, which is why that leaf also edits this file. It holds only host-specific settings: the two keys P2 consumers need — `spawn_in_doubt_seconds` and `default_backend` — belong to `TerminalConfig` (2.2), because a config owner cannot sit downstream of its own consumers, and this deliverable *reads* the in-doubt deadline from there rather than redefining it. The host manager is declared and propagated through the same carriers 2.2 established (`runner.py`, `app_context.py`, `runner_init/servers.py`, and `WebSocketServer.configure_terminals` where a WS surface needs it), so health, spawn, and `gclient` read one instance.

### 3.2 Gobby frame and control protocols on the host [category: code] (depends: 3.1)

`kind: deliverable`

Targets:
- `crates/gterminal/src/host/control.rs`
- `crates/gterminal/src/host/frames.rs`
- `crates/gterminal/src/protocol/wire.rs`
- `crates/gterminal/tests/wire_golden.rs`
- `docs/contracts/gterm-protocols.md`

- **Frame protocol (bincode, imported and narrowed to read-only).** The rebranded herdr wire protocol at version 1: `Hello{version, encoding, local_token, cols, rows}` → `Welcome{host_epoch}`; `AttachTerminal{host_terminal_id}`; `SetViewport{rows, cols}`; `Detach`; server → `Frame(FrameData)` | `Terminal(TerminalFrame)` | `Graphics` | `TerminalExited`. Per-terminal attach only (herdr's whole-app frame mode is not exposed). The `local_token` in `Hello` is verified against `~/.gobby/local_cli_token` (same-user defense in depth; C1).

  The narrowing is the point: herdr's `Input`, `InputEvents`, `Resize`, and the `mode`/`takeover` fields of `AttachTerminal` are **not** imported. This channel has no verb that mutates a terminal. `SetViewport` is the one thing that looks like a write and is not — it changes only the grid size this attachment's frames are rendered into, so observers each read at their own size for the focused encoding, and it can never reach `TIOCSWINSZ` (that path exists only on the control channel). This is what eliminates tmux's smallest-client shrinking: a viewer's geometry is a rendering parameter, not a property of the terminal.

- **Two surfaces, and only one of them can write.** The mechanics above are per-connection; the rule binding them is pinned here once so gclient (3.3) and the web proxy (4.3) cannot disagree. The host serves exactly two sockets: the **frame socket**, which local clients connect to and which is read-only as just described, and the **control socket**, which only the daemon connects to and which carries every state-changing verb the host implements (all of them against host-owned PTYs; a tmux pane is written by the daemon itself, never through the host — 3.4). There is no path by which a local client writes to a terminal, resizes one, or acquires anything resembling a lease from the host. The two sockets also accept different credentials — frame clients present `local_cli_token`, the control socket accepts only `gterm-control.token` (3.1, C1) — so a client cannot reach the writing surface by reusing the credential it already needs for the daemon. The read-only property does not depend on that, since the frame enum contains no write verb at all, but the two facts fail independently rather than together.

  This is a deliberate reversal of an earlier design in which the host admitted a `Control` attachment on presentation of a daemon-minted lease token. That design had one authority in name and two in fact, because a token is a replica of the daemon's lease record and a replica demands a consistency protocol — mint, bind, expire, revoke-on-takeover, reconcile-after-restart — every part of which would be new mechanism whose only purpose was to let a client skip a hop. Removing the client write path removes all of it. The host holds no authority state, makes no admission decision, and needs no clock agreement with the daemon; it serializes the writes the daemon sends it because two writes to one PTY would interleave bytes, and that is the whole of its involvement.

  The lease itself lives where 2.5 puts it: a daemon-held record keyed by `terminal_id`. gclient asks the daemon for control, sends keystrokes to the daemon, and renders read-only until the daemon says otherwise; a displaced holder learns of it from the daemon's `terminal_lease_lost` event and must render a visible read-only state (silent input loss is a defect, not a degradation). If the daemon is unreachable, frames keep arriving from the host and nobody can write — observe-only is the failure mode by construction rather than by policy. The cost is one extra hop for local keystrokes, on exactly the path the shipped web terminal already uses.
- **Backpressure and slow consumers.** Frame production must never be gated on the slowest reader, and every hop is bounded — a reader that never reads cannot be promised delivery *and* bounded memory, so the contract is bounded-effort delivery with a typed failure instead of an absolute guarantee. Each attachment gets two bounded queues. The **delta queue** is droppable: on overflow the host discards that attachment's queued frame deltas, marks it desynchronized, and schedules a fresh full keyframe, so a stalled reader costs itself latency rather than costing the writer and healthy observers throughput. The **control queue** is small, bounded, and non-coalescing, carrying `TerminalExited` and typed errors; these are never dropped *silently*, but they are not delivered unconditionally either — if the control queue overflows or a control event exceeds a fixed delivery deadline, the host closes that attachment with a typed error and stops buffering for it. A client that is closed this way relearns state on reconnect (control `list` plus a fresh keyframe), which is why no replay buffer is needed. The delta-lag timeout closes the attachment the same way. This applies identically to gclient attachments and to the daemon's web-proxy attachment (4.3), which is just another frame client; 4.3 additionally bounds the daemon→browser relay.
- **Dimension bounds (protocol source of truth).** `wire.rs` pins the shared bounds this plan validates everywhere: minimum 1 row and 1 column, maximum 1024 rows, 2048 columns, and 1,000,000 cells. `Hello`, `AttachTerminal`, `SetViewport`, and control `spawn`/`resize` are validated against them **before** any grid allocation, snapshot buffer, or `TIOCSWINSZ`, and violations return a typed error. The frame-channel verb in that list is `SetViewport`, never a frame `Resize`: 3.2's narrowing removes `Resize` from the frame enum entirely, so naming it here as a validation site would reintroduce on paper the verb the protocol rejects on the wire. The Python mirror is owned by 2.2; the numbers are documented once here so the two implementations cannot drift silently.
- **Operation identity for non-idempotent verbs.** `write`, `kill`, `resize`, and `spawn` change state, and a response lost to a disconnect is indistinguishable from a request never executed — for `write` specifically, the difference between "nothing typed", "payload typed without Enter", and "payload plus Enter" is the difference between a correct answer and a corrupted agent prompt. Deduplication therefore needs an identity the host can *reason about when it is absent*, which an opaque id cannot provide: with a bounded map of arbitrary ids, a never-seen id and an already-executed-but-evicted id are the same cache miss, so the host would have to either re-execute evicted retries or reject all new work. The identity is instead a **per-connection monotonic `operation_seq`**, assigned by the client, carried on every state-changing request, and paired with a request fingerprint (verb plus payload hash) so a mismatched replay is caught rather than silently confirmed. State-changing requests are serialized per connection and the client issues at most one at a time. The host keeps a `high_seq` watermark, an `evicted_below` watermark, and a bounded map (last 64) of `operation_seq → outcome`. The decision is total under concurrent or out-of-order arrival: `seq == high_seq + 1` is the only new request that executes; `seq > high_seq + 1` is refused `operation_gap` without advancing the watermark, so the missing predecessor may arrive and the refused request may be retried; a retained sequence returns its recorded outcome without re-executing and refuses typed if its fingerprint differs; a sequence at or below the eviction watermark is refused `operation_expired`. The per-connection serialization covers pipelined decoder tasks as well as ordinary client calls, so two handlers cannot both observe the same watermark and execute out of order. Because the ledger is keyed on the connection rather than the terminal, a terminal that exits does not erase the outcome of the `kill` or `spawn` that concerned it, and the daemon can still resolve an in-flight verb after the fact. A reconnect starts a fresh connection with a fresh sequence space, so the ledger's job is exactly-once *within* a connection and it says nothing at all about a retry that crosses a reconnect.

**What the boundary can and cannot promise, stated rather than implied.** A per-connection ledger plus "reconciliation covers the boundary" is only true for verbs whose effect is observable in terminal state, and it is worth being blunt about which ones those are, because the difference decides whether a caller may retry. `spawn` is resolvable: the daemon holds the `terminal_id` and `spawn_key`, and `list` says whether the terminal exists, so the reconciliation matrix (3.1) converges the row without a second spawn. `kill` and `resize` are resolvable and idempotent-by-target: killing a dead terminal and resizing to the size it already has are both no-ops, so a blind retry after reconnect is safe. `write` is **not** resolvable, and no mechanism short of a durable cross-connection ledger would make it so — the bytes are gone into a PTY and nothing in `list` or a snapshot can distinguish "the payload was typed and the program consumed it" from "the payload never arrived" in the general case. So this plan does not pretend otherwise: a `write` whose response is lost across a reconnect is **indeterminate**, the control client must not blind-retry it, and the caller's recovery is to re-read a snapshot and decide from observed terminal state. Declining to promise cross-reconnect exactly-once for `write` is a deliberate choice over building a persistent operation log: a durable ledger keyed by client identity would be real mechanism — storage, retention, cross-restart identity — bought to paper over a case a recapture-and-re-evaluate loop handles correctly.

Because `write` is a control verb, the only client that can ever see this outcome is the daemon, which is what makes it tractable: it surfaces as the `IndeterminateWrite` member of the backend-neutral `WriteOutcome` 2.2 defines, and every consumer above it follows the single abstain-and-re-observe rule 2.4 states. This channel is one of **two** producers, not the only one — a tmux `send-keys` can also apply its effect and lose its answer (2.2) — which is why the outcome type and its latch live in the contract rather than in the native runtime. No local client and no browser tab ever has to reason about it, because neither one issues writes.
- **Control protocol (JSON lines, new, small).** Newline-delimited JSON over `gterm-control.sock` for the daemon (Python speaks JSON, not bincode); herdr's 8.8k-line schema'd API is not imported. The socket, the `hello` handshake, and the read-only `ping`/`list` verbs are created in 3.1, which needs them for supervision; this deliverable adds the working verbs on top. Requests carry `id` for correlation: `spawn{terminal_id, spawn_key, argv, env, cwd, rows, cols}` → `{host_terminal_id}`; `kill{host_terminal_id, grace_ms}`; `resize{...}`; `snapshot{host_terminal_id, mode: "text"|"ansi", lines, max_bytes}` (bounded, see below); `write{host_terminal_id, kind: "text"|"key"|"paste", data, submit}` (the attention-respond primitive with the same literal/paste/named-key semantics as tmux injection; `paste` applies herdr 0.8.0 `paste_payload` from the host's live `MODE_BRACKETED_PASTE`); `subscribe_events` → the **lifecycle-only** event stream (exit, resize, title), each event carrying a per-terminal monotonic `seq` for gap detection — it is deliberately not an output tap, since continuous output belongs to the frame protocol (see 4.2). State-changing requests additionally carry `operation_seq` per the identity rule above.
- **`list` must be able to reconstruct every state the event stream carries.** `subscribe_events` is lossy by design — an attachment can be closed for lag, and a daemon can be down — so any state that only ever arrives as an event is a state that can go permanently stale. Title is the sharp case: a title-only change during a disconnection produces no later event, so there is no `seq` gap to notice, and even a noticed gap cannot be repaired if the snapshot response omits the field. `list` therefore returns, per terminal, `{host_terminal_id, terminal_id, title, rows, cols, pid, last_seq}` — every field the lifecycle stream can change, plus the highest `seq` the host has emitted for that terminal. `terminal_id` is the daemon-supplied id echoed back so adoption can reconcile in both directions (3.1); `last_seq` lets a reconnecting subscriber detect that it missed events at all; and title and dimensions let it repair what it missed without a replay buffer. Reconciliation over `list` runs on startup, on every reconnect, and on the health interval, so the worst-case staleness of any lifecycle-carried field is one interval.
- **Snapshots are byte-bounded.** `snapshot` with `mode: "ansi"` returns scrollback, and scrollback grows without limit while the JSON-lines transport must reject oversized lines to stay memory-safe — a legitimate long history would otherwise either trip the guard (losing capture-before-kill exactly when it matters, at process death) or force an unbounded allocation. The response is therefore capped: `max_bytes` defaults to a fixed ceiling set safely below the transport's line limit, the host truncates from the **oldest** end so the most recent output always survives, and the response carries `{truncated: bool, dropped_bytes, total_bytes}` so the caller records a faithful artifact rather than a silently short one. Deliberately not chosen: a paginated cursor protocol. Capture-before-kill and detector input both want the tail, one bounded response satisfies both, and a cursor would add multi-round-trip state to a path that runs during process teardown.
- **Golden wire corpus.** Three processes in two languages share these two boundaries — the Rust host, the Rust client, and the Python daemon (which speaks JSON control *and*, for the web proxy in 4.3, consumes bincode frames). Rust-internal round-trip tests cannot catch cross-language byte drift, so `crates/gterminal/tests/fixtures/wire_golden/` holds a small committed corpus of canonical encoded messages: `Hello`, `Welcome`, `AttachTerminal`, `SetViewport`, `Detach`, `Frame(FrameData)`, `Terminal(TerminalAnsi)`, `TerminalExited`, and a typed error frame, plus the JSON-lines control requests and responses for every verb above, including `write` `kind: "paste"` with both bracketed-on and bracketed-off payloads. Rust asserts its encoder reproduces the fixtures byte-for-byte and its decoder accepts them; the Python side asserts the same in 4.1 and 4.3. The corpus is fixtures plus focused tests — deliberately not a schema-generation subsystem or an IDL. Changing any wire shape means regenerating the corpus in the same change, which is what makes the version-1 freeze enforceable.
- Both protocols and their versioning/compat rules are documented in `docs/contracts/gterm-protocols.md` (the contract-drift precedent from `docs/contracts/gcode-cli.md`), including the read-only frame channel and daemon-only write rule, the backpressure contract, and the corpus regeneration procedure.

### 3.4 tmux panes observed through the host [category: code] (depends: 3.3, 2.5)

`kind: deliverable`

Targets:
- `crates/gterminal/src/host/embed.rs`
- `crates/gterminal/src/host/frames.rs`
- `crates/gterminal/src/protocol/wire.rs`
- `crates/gterminal/tests/wire_golden.rs`
- `docs/contracts/gterm-protocols.md`
- `crates/gclient/src/tmux_identity.rs`
- `crates/gclient/src/views/mod.rs`
- `src/gobby/servers/routes/terminals.py`
- `src/gobby/terminals/tmux_runtime.py`
- `src/gobby/config/terminal_host.py`

tmux-backed terminals (Gobby-spawned runs still on tmux, and externally discovered sessions) render in gclient through the same host path — one rendering pipeline for every backend (decided over a second daemon-WS rendering path in the client):

- **No tmux client, and no tmux mutation either.** The obvious implementation — an ephemeral grouped session that selects the recorded pane and attaches — is wrong on both counts, and both were reproduced against a live tmux server. Grouped sessions have independent *current windows* but they **share each window object, including its single active pane**, so selecting the recorded `pane_id` inside the group moves the owner's active pane (observed: owner active pane changed from `%0` to `%1`). And every attached client, grouped or not, participates in window sizing for the lifetime of the attachment, so a differently sized viewer recomputes the shared window even if it never asks to resize (observed: a 120x39 owner window became 80x19). No tmux option fixes either, because `window-size` and `aggressive-resize` are window properties a group shares. So the viewer creates no tmux client.

  A second design — `pipe-pane -O` for a live byte stream plus `capture-pane` for an initial keyframe — was then tried and also rejected, because splitting observation across two mechanisms creates defects that no amount of care removes. There is no atomic operation joining the two, and live testing shows the seam both ways: capture-then-pipe drops output written between the two calls, and pipe-then-capture renders it twice. `pipe-pane` is also a *mutation of a shared resource with no ownership token* — `#{pane_pipe}` is a bare boolean, so a check-then-install has an unavoidable race, and an install always closes whatever pipe was already there, meaning a viewer can silently destroy a pipe the pane's owner installed for their own purposes. And `capture-pane -p -e` emits rendered screen text with no cursor position, no mode state, and no alternate-screen flag, so it cannot serve as the checkpoint that a subsequent byte delta is interpreted against; a redraw arriving after the keyframe can land at the wrong cursor. Each of those is fixable in isolation and unfixable together: a sequence-numbered atomic cutover, an ownership protocol tmux does not expose, and a stateful checkpoint protocol would all have to be invented.

- **One observation mechanism: bounded capture polling.** The design therefore uses `capture-pane` for *both* initial and ongoing state, which deletes the cutover, the exclusive resource, and the keyframe-versus-delta contract in one move. While at least one attachment exists, the host polls the pane with a **single batched tmux invocation** that reads the server generation, the pane's full observable state, and the screen together:

  ```
  tmux -S <socket> display-message -p -t <pane_id> \
    '#{pid} #{start_time} #{pane_width} #{pane_height} #{cursor_x} #{cursor_y}
     #{cursor_flag} #{cursor_very_visible} #{alternate_on} #{keypad_cursor_flag}
     #{keypad_flag} #{bracket_paste_flag} #{mouse_standard_flag} #{mouse_button_flag}
     #{mouse_any_flag} #{mouse_all_flag} #{mouse_sgr_flag} #{wrap_flag} #{origin_flag}
     #{insert_flag} #{scroll_region_upper} #{scroll_region_lower} #{pane_in_mode}
     #{cursor_shape} #{cursor_blinking} #{cursor_colour} #{mouse_utf8_flag}
     #{pane_dead} #{pane_title}' \
    \; capture-pane -p -e -t <pane_id>
  ```

  Every value in a poll comes from one server-state read, so geometry can never describe a different screen than the one returned beside it — a claim the round-4 review reproduced on tmux 3.7b, racing 3,000 batched polls against alternating resizes without a single disagreement between the reported dimensions and the captured screen. The host renders the captured text into a pane-sized grid, diffs it against the previous poll, and emits ordinary `FrameData` cell deltas — the frame protocol is unchanged, and the deltas are *computed by the host from complete observations* rather than reconstructed from a byte stream, which is a better fit for the existing cell-diff encoding than raw bytes would have been. The tmux footprint is **zero** — no client, no pipe, no option, no selection change, nothing to restore on detach, and nothing an owner can observe except the read-only commands in their server's log.

  The cost is stated rather than hidden: a viewer sees the pane at poll granularity, so output that appears and is overwritten inside one interval is never rendered, and scrollback beyond the visible pane is not streamed (a bounded history window is captured once on attach for context). For a read-mostly viewer of a pane another program owns, that is the right trade — the alternative was byte fidelity purchased with a destructive mutation and a lossy seam. Gobby-owned tmux terminals are unaffected by the trade in practice because they are migrating to the native backend anyway (P4), and external panes are exactly the case where non-interference matters more than frame-perfect fidelity.

- **The screen is not the whole state, and the missing bits are the ones that change invisibly.** An earlier form of this batch read only dimensions, cursor position, `pane_dead`, `alternate_on`, and the title, on the assumption that `capture-pane -e` carries everything else. It does not, and the gap is not academic: the round-4 review hid the cursor with DECTCEM in a live pane and observed `#{cursor_flag}` flip while the captured bytes and every field in that batch stayed byte-identical. A renderer diffing consecutive observations would therefore draw a cursor the application had turned off, indefinitely, with nothing to notice. The same class covers the input modes — application-cursor-keys, application-keypad, bracketed paste, and the mouse reporting modes — which change no cell either, and which the daemon needs in order to encode a keystroke correctly: an arrow key is `ESC [ A` or `ESC O A` depending on a bit that lives nowhere in the captured screen.

  The fix costs one longer format string, because tmux exposes all of it. The batch above therefore carries the cursor's visibility, very-visible state, shape, blink state, and colour, the alternate-screen flag, the keypad and cursor-key modes, bracketed paste, all six mouse-mode flags including the UTF-8 variant, and the wrap/origin/insert flags plus the scroll region — every per-pane state variable tmux tracks. These map into the host's frame and render state alongside the cells, so a mode change with no cell change still produces a frame; and the daemon reads the same modes when encoding input for that terminal, so an arrow key or a paste is encoded against the target's actual state rather than a default. `#{pane_in_mode}` is included for a reason the reviewer did not raise: when a pane is in tmux's own copy mode, `capture-pane` returns the copy-mode view rather than the application's screen and keystrokes are consumed by tmux, so an observer that ignored it would render a scrollback pager as if it were the program and report input as delivered when tmux ate it. A pane in copy mode is surfaced as a distinct observable state rather than rendered as ordinary output.

  **The field list is closed against tmux's own inventory, not against a guess at what matters.** The first correction to this batch added the flags one review named and stopped there, which left the same class of defect one step further out: a later probe changed `#{cursor_shape}` (DECSCUSR), `#{cursor_colour}` (OSC 12), `#{cursor_blinking}`, and `#{mouse_utf8_flag}` while `capture-pane -p -e` returned byte-identical output and every declared field held still — a cursor drawn as a block where the application asked for a bar, in a colour the application changed, with no observation that could ever notice. All four expand on tmux 3.7b (verified: `default|0|none|0`) and all four are now in the batch. The rule that replaces the guessing is stated so the implementer can re-derive it: the format list above is closed by enumerating tmux's per-pane state variables and, for each one, either reading it in this batch or writing down why the cells already carry it. `#{pane_title}` is read here; window- and session-scope variables are not, because they are 2.1 metadata rather than pane state; and the acceptance for this is a mode-and-appearance test whose cells never change, so a field silently dropped from the batch fails it.

- **A failed command is not a dead pane.** Mapping every non-zero `tmux` exit to `TerminalExited` conflates "the pane is gone" with "we could not look at it", and the second is far more common: a fork failure under memory pressure, a descriptor exhaustion, an exec timeout on a loaded machine, or a socket that briefly refuses connections all produce a failed invocation while the pane sits there perfectly alive. Treating those as death is unrecoverable in the worst way — it tears down attachments, marks the row, and the pane it just declared dead keeps running unobserved. So the poll classifies its outcome instead of testing it for zero. **Confirmed absence** is `#{pane_dead}` set, or tmux reporting the target or the server missing (`can't find pane`, `no server running on <socket>`), or the generation in the same read not matching the stored locator; only these emit `TerminalExited`, tear down attachments, and mark the row. **Transient failure** is everything else — spawn failure, timeout, permission, descriptor exhaustion, an unparseable response — and it is retried on an exponential backoff from the poll interval up to a bounded ceiling, with the attachment held open and the last good frame left on screen behind a typed "stale" indicator so a viewer is never shown fabricated liveness. If transient failures persist past the ceiling the terminal is marked `orphaned`, not `exited`: unknown is its own state, and the daemon's reconciliation (3.1) resolves it against a fresh discovery pass rather than the host guessing. A daemon that is unreachable changes nothing about this — the host keeps polling and keeps frames flowing, and the row is reconciled when the daemon returns.

- **The poll loop has an owner, a floor, and a stated bound.** Calling the interval "configurable" without saying who owns it leaves a timer-driven external-process loop with no operational contract, so it is pinned: `TerminalHostConfig` (3.1) owns `tmux_poll_interval_ms`, defaulting to 150ms with a validated floor of 50ms, and `tmux_poll_backoff_ceiling_ms`, defaulting to 5s. The interval is a host key rather than a shared `TerminalConfig` key because only the host runs the loop. The load bound follows from two properties already in this design rather than from a new limiter: an observer exists **only** while at least one attachment exists, and all attachments to one `locator_key` share a single observer. Worst-case process rate is therefore `attached_tmux_panes / interval` — bounded by what a human has open, not by how many terminals exist or how many viewers watch each one — and a hundred discovered external sessions with none attached cost nothing at all. That expression is a *rate*, though, and a rate is not a bound: it divides by the interval but its numerator — the count of distinct attached `locator_key`s — has no maximum anywhere in this design, and locator sharing only collapses multiple viewers of the *same* pane. A scripted client, a runaway workspace layout, or a project with hundreds of discovered external panes can attach as many distinct panes as it likes, and "bounded by what a human has open" is an assumption about the caller rather than a property of the host. So `TerminalHostConfig` also owns `max_attached_terminals`, defaulting to 64: attaching past it is refused with a typed capacity error naming the limit, the refusal is a frame-protocol shape in the golden corpus, and existing attachments are never disturbed to make room. This is the one place a cap is added, and it is one integer plus one error — strictly less mechanism than the concurrent-poll scheduler that was considered and still declined, because with the numerator bounded the worst-case process rate `max_attached_terminals / interval` is a finite number the operator can compute (at the defaults, 64 panes at 150ms, roughly 427 tmux invocations per second in the pathological case, against 6.7 for a plausible one). A capacity refusal is visible and diagnosable; a pane that silently stops updating is what the earlier decline was trying to avoid, and a typed refusal at attach time is not that.

- **Geometry comes from the poll, so it cannot be stale.** The emulator is sized to the pane, not to the viewer, from the `pane_width`/`pane_height` in the same batch as the screen it renders — an owner-driven resize is therefore observed atomically with its first resized screen and emitted as an ordinary resize event ahead of the frame it applies to, and there is no window in which cells are applied under previous dimensions. On confirmed pane death the host emits `TerminalExited`, tears down every attachment for that terminal, and removes the registry entry — the same teardown path a native PTY exit takes, so no attachment can outlive the pane; the daemon releases its own lease record when it sees the exit, since the lease was never host state (3.2). Nothing about viewer geometry reaches tmux: the frame channel has no PTY-resize verb at all (3.2), so a viewer whose pane differs from the owner's geometry letterboxes or scrolls locally in gclient and re-letterboxes when the owner resizes. Resizing a `gobby`-owned tmux terminal is a daemon operation through `TmuxTerminalRuntime`, not a host one.

- **Input for a tmux pane never touches the host.** Writes are daemon-only (3.2), and for a tmux-backed terminal the daemon already owns an exact write path: `TmuxTerminalRuntime` issues `send-keys -t <pane_id> -H`, which delivers arbitrary bytes — control sequences included — to precisely that pane, encoded against the mode flags the poll reports. So this deliverable adds no write path of any kind: the host observes, the daemon writes, and gclient's keystrokes travel the same daemon route the browser's already do. That also means the observer needs no notion of a writer, a holder, or a lease, and pane death has no lease-side cleanup to perform here.

- **Identity is the pane, the wire says so, and every poll checks it.** Attach targets carry the 2.1 physical identity — socket path, tmux server pid, server start time, and `pane_id` — never a session or window name, so a rename or a `break-pane` between attaches resolves the same terminal. The generation is not merely carried, it is verified: `#{pid}` and `#{start_time}` ride in every poll batch (they cost nothing to add to a format string that is already being expanded), and a mismatch against the attach target's stored generation is treated as confirmed absence. That closes the case where a tmux server died while the daemon was down and a replacement claimed the same socket path and handed out the same `pane_id` — without the check, the very first poll would bind a stored terminal to a stranger's pane and stream it to a viewer as if it were the original. The host re-reads `#{pane_title}` (and, on the daemon side, session and window names) as refreshable metadata from the poll, updating the row without touching identity.
- **The observer is created inside `Attach`, not before it.** A separate `embed` verb returning a `host_terminal_id` for a later frame attach cannot be made safe: initialize the refcount at creation and a caller that dies before attaching leaks the observer forever; initialize it at attach and a zero-ref teardown can reap it before the caller ever uses the id it was handed. So there is no separate verb. `AttachTerminal{terminal_id, locator}` on the frame socket performs create-or-join **inside the same critical section that registers the attachment**, under a per-`locator_key` creation lock: the registry entry and its first attachment commit together, or neither does. The response reports `created` so callers can distinguish first attach from join. Attachments are refcounted and polling stops **immediately when the last one detaches** — deliberately no linger window, because a linger timer plus reattach is exactly what would need cancellable linger generations to stay correct, and restarting a poll loop costs one tmux invocation. If the frame handshake fails partway, the same critical section rolls the creation back. Observers are viewers, not owners: daemon lifecycle authority over the underlying tmux session is untouched (`TmuxTerminalRuntime` remains the control plane for capture/inject/kill), and host shutdown or crash leaves the pane in exactly the state it was in, because nothing was ever mutated.
- **This leaf changes wire shapes, so it owns the corpus with them.** `AttachTerminal` gains the pane-identity block, its response gains `created`, the pane's mode-flag state joins the frame payload, and the recursive-view refusal, the capacity refusal, and the copy-mode and stale-observation states are new typed shapes — all of which are frame-protocol shapes that three processes decode. Adding them without regenerating `crates/gterminal/tests/fixtures/wire_golden/` would leave the corpus asserting a protocol the host no longer speaks, and the Python frame client (4.1) pins itself against that same corpus, so stale fixtures would let Rust and Python drift silently in exactly the way the corpus exists to prevent. So `crates/gterminal/src/protocol/wire.rs`, the golden corpus, and `docs/contracts/gterm-protocols.md` are updated in this deliverable, byte-exactly and in the same change, per the version-1 freeze rule 3.2 sets. This is also why the deliverable depends on 3.3 rather than only 3.2: the client-side invoker for this path lives in gclient's terminal views, and a leaf that edits `crates/gclient/src/views/` cannot run before the crate exists.
- **Recursive-view guard, from the client's identity.** Rendering a pane inside itself is a feedback loop — the poll observes the pane's screen, gclient draws it back into that pane, and the next poll observes the drawing — so it must be refused. It cannot be detected from the host's environment: `gterm` is spawned by the daemon and inherits the *daemon's* `$TMUX`, which says nothing about where the client is running, and the common case (daemon outside tmux, gclient inside the target session) is invisible that way. gclient therefore reports its own identity: it parses `$TMUX` for the socket path and server pid, reads `tmux display-message -p '#{pane_id}'` plus the server start time, and sends that block in `Hello` as authenticated attach metadata (`crates/gclient/src/tmux_identity.rs`). The host compares the client-supplied identity against the target `locator_key` before creating or joining an observer and refuses typed on a match. A client running outside tmux sends no block and is never refused.

### 4.1 NativeTerminalRuntime over the host control API [category: code] (depends: 2.2, 3.2, 3.4)

`kind: deliverable`

Targets:
- `src/gobby/terminals/native_runtime.py`
- `src/gobby/terminals/host_client.py`
- `src/gobby/terminals/frame_client.py`
- `src/gobby/terminals/__init__.py`
- `src/gobby/runner.py::*` — scope-reason: native runtime and frame-client composition wiring per the body
- `src/gobby/app_context.py::*` — scope-reason: native runtime and frame-client composition wiring per the body
- `src/gobby/runner_init/servers.py::*` — scope-reason: native runtime and frame-client composition wiring per the body
- `src/gobby/runner_init/orchestration.py::*` — scope-reason: native runtime and frame-client composition wiring per the body

`src/gobby/terminals/host_client.py`: an asyncio JSON-lines client for `gterm-control.sock` (request correlation, timeouts, typed errors `HostUnavailableError`/`HostEpochChangedError`/`HostCommandError`, reconnect with epoch verification). `src/gobby/terminals/native_runtime.py`: `NativeTerminalRuntime` implementing the full 2.2 contract over it — `spawn` takes the caller-allocated `terminal_id` from the request, issues control `spawn` with it, and **returns** the `host_epoch` + `host_terminal_id` locator for the caller to CAS (`execute_spawn` owns row creation and every transition, per 2.1 and 2.3; the runtime writes no rows); `snapshot`/`snapshot_full` map to control `snapshot` (text/ansi); `write_text`/`write_key`/`write_paste` map to control `write` preserving the injection semantics (literal + submit-Enter, named keys without Enter, herdr 0.8.0 `paste_payload` for `kind: "paste"`) and the `stage: none|partial` failure classification for the attention respond contract; `terminate` maps to `kill` with grace; `is_live` cross-checks control `list` against the stored epoch; `attach_locator` returns the frame-socket locator. Registered in the runtime registry beside tmux — this deliverable is where the registry first resolves both backends, since 2.2 registers tmux alone. An explicitly requested native spawn with the host down raises `HostUnavailableError` — no tmux fallback (C1).

Two protocol obligations from 3.2 land in this client, and the first one has to match the host's actual guarantee rather than a stronger one. Non-idempotent requests (`write`, `kill`, `resize`, `spawn`) carry the per-connection monotonic `operation_seq` the host's ledger is keyed on, plus the request fingerprint, so a retry *on the same connection* returns the recorded outcome instead of executing twice, and `operation_gap`/`operation_expired` refusals surface as typed errors the caller must handle rather than silent retries. Across a reconnect the sequence space is new and the ledger is gone, so this client obeys the per-verb boundary rule 3.2 pins: `spawn` is left to reconciliation, `kill` and `resize` may be retried because they are idempotent against their target's state, and a `write` whose response was lost is reported **indeterminate** and never blind-retried. This runtime is one of the two producers of the outcome type 2.2 defines: it returns `IndeterminateWrite` beside `Delivered` and typed failure, so no caller can accidentally read it as either one, and every consumer applies the single abstain-and-re-observe rule 2.4 states. The tmux runtime is the other producer; this control client is the native producer and both write into the shared unresolved-action map. An earlier draft of this deliverable promised a stable `operation_id` reused across reconnects; that promise is withdrawn, because a per-connection ledger cannot honor it and only a durable cross-restart operation log could. And every reconnect re-runs the 3.1 adoption reconciliation over control `list` — verifying the epoch, converging `pending` rows, finalizing rows the host no longer has, and reporting host-only terminals — because a reconnect is indistinguishable from a restart from the row's point of view.

`snapshot`/`snapshot_full` return the 2.2 `SnapshotResult`, not a string: the host's `{truncated, dropped_bytes, total_bytes}` fields map straight through so a truncated capture is recorded as truncated all the way into persistence (2.4). Dropping them here would make the host's byte-bounding honest and the daemon's record of it silent, which is the worse of the two failures.

The control client is the first Python consumer of a wire format defined in Rust, so it is held to the golden corpus committed in 3.2: `host_client.py` must decode every canonical control response in the corpus and its own encoded requests must match the corpus bytes, proving the two implementations agree without a running host in the loop.

**The Python frame client is created here, not by its second consumer.** Two later deliverables need to read bincode frames from Python — 4.2 relays a native run's output into the existing `terminal_output` broadcast, and 4.3 proxies frames to the browser — so the adapter belongs to their common predecessor rather than to whichever happens to be written first. `src/gobby/terminals/frame_client.py` is that adapter: an asyncio bincode frame client for `gterm-frames.sock` implementing `Hello`/`Welcome`, `AttachTerminal`, `SetViewport`, `Detach`, and decoding of `Frame`, `Terminal(TerminalAnsi)`, `Graphics`, and `TerminalExited`, under the same bounded-queue contract every frame client obeys (3.2). Its caller supplies the `host_epoch` stored with the terminal locator; after `Welcome{host_epoch}` the client compares the returned epoch before sending `AttachTerminal`, and a mismatch closes the connection with typed `HostEpochChangedError` so a locator from a replaced host never attaches by recycled host-terminal id. It is a reader: writes go on the control client, even though both clients live in the same process, so the daemon's own code cannot accidentally establish the client write path 3.2 removed. It is pinned against the golden corpus in the same way the control client is — byte-exact encoding, fragmented-read reassembly, oversized and version-mismatched rejection — so 4.2 and 4.3 consume one verified decoder and cannot drift from each other or from Rust.

### 4.3 Web terminal parity through the host for both backends [category: code] (depends: 4.1, 2.5, 3.4)

`kind: deliverable`

Targets:
- `src/gobby/servers/websocket/tmux.py::*` — scope-reason: web-proxy migration to the shared frame client and PTY-bridge retirement

- `web/src/components/activity/terminal/TerminalView.tsx::*` — scope-reason: web-proxy migration to the shared frame client and PTY-bridge retirement

The web terminal views terminals through the daemon as proxy (no browser→host connection): `terminal_attach` makes the daemon open a frame-protocol attach to the host through the shared frame client (4.1) negotiating the `TerminalAnsi` encoding, and relays frames as the existing `terminal_output` events; `terminal_attach` from the browser uses `frame_delivery: "proxy"`; `terminal_input`/`terminal_paste`/`terminal_resize` are checked against the daemon's lease record and then dispatched **through the `TerminalRuntime` for that row's backend** — never on the frame attachment, which has no write verb (3.2). `terminal_set_viewport` is not lease-gated and is forwarded only as that tab's host-frame `SetViewport`. The dispatch is per-backend because the two backends have different write paths and the host has none for tmux: a `native` terminal's input and resize go to the host on the control channel, while a `tmux` terminal's go to `TmuxTerminalRuntime`'s daemon-side `send-keys -t <pane_id> -H` and `resize-pane`, exactly as 3.4 requires — the host observes tmux panes and never writes to them. Both paths return the 2.2 `WriteOutcome`, so an indeterminate browser keystroke is reported to the tab rather than assumed delivered. The wterm/ghostty renderer consumes the ANSI stream unchanged (same VT family end-to-end). Per-connection cleanup detaches the daemon's host attachment exactly as PTY bridges are cleaned up today.

**The tmux bridge is retired for this surface, so one terminal has one transport.** 2.5 already made the daemon lease the single authority, which stopped a web tab and a gclient pane from both believing they had control. What it could not fix yet is the *transport*: `TmuxPTYBridge` runs its own `tmux` client per browser connection, which is exactly the shape 3.4 proved unsafe — a second client participates in window sizing and can move the owner's selection. With 3.4's capture-poll observer available, the browser's tmux attachments route through the same host path as gclient's: `TmuxPTYBridge` is deleted along with its export, and `src/gobby/servers/websocket/tmux.py` resolves every attach — tmux and native alike — to a host attachment. The result is one observer per physical pane shared by every viewer, one lease record, and one external-geometry policy, with a browser resize on an `external` terminal refused by the daemon and never reaching tmux, identically to gclient. This is the leaf where the cross-surface single-authority claim becomes true for tmux, which is why it depends on 3.4.

**Deleting a class means deleting the tests that construct it.** `TmuxPTYBridge` is referenced in fourteen places in `tests/agents/test_tmux.py` — a substantial direct suite covering the bridge's attach, resize, input, and cleanup behavior — plus its export in `src/gobby/agents/tmux/__init__.py` and its two construction sites in `websocket/tmux.py`. A retirement that removed the class and left that suite behind would not be a partially-done refactor; it would be an import error on collection. Each bridge test is therefore either **re-expressed** against the frame-client path when it asserts behavior the new transport must still exhibit (a browser attach renders the pane, a disconnect releases everything, input reaches the pane) or **deleted** when it asserts bridge-internal mechanics that no longer exist (its per-connection tmux client, the session-option manipulation 2.5 already removed for external panes). The acceptance requires zero references to the symbol anywhere in `src` or `tests`.

Two policies bind this surface specifically, because it is the second surface that can hold the daemon's lease:

- **Read-only by default, over the 2.5 lease messages.** A web `terminal_attach` grants no write rights; the daemon moves its lease record to that attachment only when the browser sends `terminal_take_control`, answering with `terminal_control_result`, and a displaced holder — a gclient pane, another tab — receives `terminal_lease_lost` and renders read-only, so a takeover is visible instead of silently dropping typed input. `terminal_input`/`terminal_paste`/`terminal_resize` from an attachment that does not hold the lease are refused with a typed reason rather than discarded. Every one of those decisions is made by the daemon against one record; the host is never consulted, which is what keeps a focused gclient pane and an open web tab from ping-ponging authority, and it is why the wire shapes had to exist in 2.5 rather than being implied by policy.
- **Backpressure at both hops.** The daemon's host attachment is an ordinary frame client under the 3.2 bounded-queue contract, and the daemon→browser relay is bounded the same way: a per-connection outbound queue plus a send timeout, where overflow or timeout closes that tab's terminal stream with a typed lag error instead of buffering without limit or back-pressuring the host. After a host-side delta drop the daemon relays the resynchronization keyframe; after a browser-side close the tab reconnects and relearns state. A slow or wedged browser therefore degrades only its own tab. Frames the daemon relays are decoded with the golden-corpus-verified frame decoder, pinning the Python frame path against Rust byte drift.

**Acceptance:**

- 4.3.1 - The web terminal attaches (`frame_delivery: "proxy"`), streams, types into, pastes into, resizes, set-viewports, and detaches from a native terminal via the daemon proxy with no frontend renderer changes beyond backend-neutral plumbing. test: `tests/servers/test_native_web_proxy.py::test_web_attach_native_terminal`.
