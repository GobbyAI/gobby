# Context-Mode Borrowings: Output Offload Gate, Tiered Handoffs, Rule Framing, URL TTL Cache

**Plan ID:** context-mode-borrowings

## Overview
`kind: framing`

Adopt four mechanisms inspired by [mksglu/context-mode](https://github.com/mksglu/context-mode) that close real gaps in Gobby: (1) the MCP proxy returns tool results verbatim with zero size handling — add a large-output offload gate that stores + BM25-indexes oversized results and returns a bounded envelope with retrieval tools; (2) the injected handoff summary is truncated by a flat head-cut that can destroy the `## Next Steps` section — replace with deterministic tier-budgeted allocation, and add first-class unresolved-error state that survives compaction; (3) rule deny messages lead with "Gobby blocked", which models empirically misread as security gates (context-mode ADR-0003) — reframe redirects action-first; (4) gwiki URL ingest always re-fetches — add a TTL freshness check with a cheap cache-hit response.

## Constraints
`kind: framing`

- No backward compatibility: 0.5.0 is unshipped; no shims, no legacy fallbacks.
- Non-test Python/Rust source files stay under 1,000 lines — extract new modules rather than growing existing ones. Files already over the cap before this plan are pre-existing debt: this plan's edits to them must land in extracted modules (never growing the over-cap file, which must strictly shrink or stay untouched), and their remaining decomposition is explicitly out of scope — deferred to open refactor tasks that the implementing agent finds or creates at implementation time.
- Do NOT borrow from context-mode: SQLite FTS5 (Gobby's ParadeDB BM25 + Qdrant + FalkorDB RRF stack is strictly stronger), the 12-runtime sandbox executor (proxy gate covers the MCP half; CLIs have native exec), or a row-per-event session log (transcript-as-log with on-demand derivation is the sounder design).
- Postgres access uses the hub transaction boundary with psycopg `%s` placeholders.
- Any edit under `src/gobby/install/shared/` requires regenerating `src/gobby/install/bundled_content_manifest.json` via: `uv run python -c "from pathlib import Path; from gobby.install.manifest import write_bundled_content_manifest; write_bundled_content_manifest(Path('src/gobby/install'))"`.
- Rust changes are not live until rebuilt AND reinstalled to `~/.gobby/bin/` (`crates/CLAUDE.md`).
- Never run the full pytest suite; focused tests only, prefixed `GOBBY_TEST_PROTECT=1`.

### 2.1 Add section-aware budget allocation to handoff injection [category: code]
`kind: deliverable`

Targets: `src/gobby/llm/sdk_utils.py`, `src/gobby/hooks/event_handlers/_session_start/handoff.py`

Replace the flat head-cut in `_bound_handoff_summary` (`src/gobby/hooks/event_handlers/_session_start/handoff.py:154-176`, currently delegating to `head_with_breadcrumb` in `src/gobby/llm/sdk_utils.py:49-88` against `HANDOFF_SUMMARY_INJECT_BUDGET = 6_500`) with deterministic section-aware budgeting. No LLM call at injection time.

In `sdk_utils.py` add generic helpers:

```python
def split_markdown_sections(text: str) -> list[MarkdownSection]:
    """Split on ^## headings; returns preamble (pre-first-##) plus one entry
    per section with casefolded title and original order index. Fence-aware:
    lines inside fenced code blocks (``` or ~~~, simple open/close tracking)
    are never headings and never count toward the section-count fallback."""

def allocate_section_budget(
    sections: list[MarkdownSection],
    priorities: Mapping[str, int],
    budget: int,
    *,
    min_section_chars: int = 200,
    unknown_priority: int = 60,
) -> BudgetResult:  # kept sections (possibly trimmed), omitted titles
```

Extract the paragraph-boundary cut logic from `head_with_breadcrumb` into a shared `_clean_cut()` used by both paths. Algorithm: if `len(summary) <= budget` return unchanged. Otherwise:

1. **Breadcrumb budgeted first, and bounded**: compute `available = budget - len(worst_case_breadcrumb)`, where the worst case is the base breadcrumb plus an omission line listing EVERY section title that can be trimmed or dropped — mandatory sections included, since a trimmed `Next Steps` or `Current State` is listed too — each title truncated to 40 chars and the list capped at 10 entries with a `+N more` tail, so the worst case is a small constant (~600 chars) that can never approach the 6,500 budget regardless of pathological headings. After allocation, rebuild the breadcrumb with the actual (equal-or-shorter) omission list; leftover characters go unused. Deterministic, no iteration.
2. **Mandatory headings and trim markers reserved before any body allocation**: reserve the mandatory sections' heading lines plus one `[section trimmed]` marker each up front, then allocate the FULL bodies of `Next Steps` and `Current State` before any optional content — optional sections can never consume budget the mandatory sections need. Only when their combined full bodies exceed the remainder: split it between the two proportionally to body lengths, with each guaranteed at least `min(len(body), min_section_chars)` so a skewed split cannot starve either below its heading + minimum; trim each at a paragraph boundary, drop every other section, and stop — both mandatory sections always appear.
3. **Greedy first-fit for the rest**: allocate the remaining budget in priority order; a section that fits whole is kept; the first that does not fit is head-trimmed at a paragraph/newline boundary with a `[section trimmed]` marker if the remainder is ≥ `min_section_chars`, else dropped; all lower-priority sections are dropped.
4. Reassemble kept sections in original document order.

Exactly one mandatory section present: treat it as a mandatory set of one (full guarantee applies to it; the missing one is simply absent). The `head_with_breadcrumb` fallback applies only when BOTH mandatory titles are unrecognized or there are no `##` headings. There is NO section-count fallback: allocation is linear in the section count and the breadcrumb omission list is already bounded (step 1), so a large heading census degrades nothing — 31 legitimate sections with mandatory content near the tail must keep the mandatory guarantee, never fall back to a head-cut.

**Duplicate headings and fenced pseudo-headings**: the FIRST occurrence of a mandatory title owns the mandatory guarantee; later duplicates are ordinary sections at unknown priority (60) in document order. A `## Next Steps` inside a code fence is body content of its containing section — it neither claims the mandatory guarantee nor starts a section.

The handoff-specific priority table lives in `handoff.py` next to its only caller:

```python
_SECTION_PRIORITIES = {
    "next steps": 10,
    "current state": 20,
    # preamble: 25 (handled positionally)
    "unresolved errors": 30,   # reserved for 2.3
    "key technical decisions": 40,
    "problems encountered": 50,
    "what didn't work": 55,
    # unknown headings: 60
    "files changed": 70,
    "what was accomplished": 80,
}
```

Breadcrumb: keep existing wording; when sections were trimmed or dropped, append one line `Omitted sections: X, Y — full summary via get_handoff_context.` (titles truncated, list capped per step 1). The breadcrumb always counts inside the 6,500 budget. `_bound_handoff_summary` keeps its current signature.

 "first_at": str, "last_at": str, "count": int}    # canonical ISO timestamps; saturating count
```

`target_key` is never None: it is the extracted target (file path / command excerpt) or, when none is extractable, a stable argument fingerprint `args:<first 8 hex of sha256 over canonically-sorted normalized arguments>`. This kills wildcard resolution — success of `close_task(B)` can never resolve a failure of `close_task(A)`.

**Every variable-width field is bounded at write time — the session variable is size-bounded, not just count-bounded**: `tool` enters through caller-controlled wrapper strings (P3 itself establishes wrapper names are unbounded) and file `target_key`s carry paths of arbitrary length. Bound them with ONE shared deterministic renderer that 3.3 also imports for envelope names — `render_bounded_identity` in `tool_error_tracker.py`, governed by a single total-length authority, module constant `MAX_IDENTITY_COMPONENT_CHARS = 130`: a component of ≤130 chars passes through unchanged; a longer one renders to EXACTLY 130 chars — a retained prefix of `MAX_IDENTITY_COMPONENT_CHARS - len("…#") - 8 = 120` chars, then `…#` plus the first 8 hex of sha256 over the full original value. The prefix length is DERIVED from the constant, never stated independently — the earlier draft's off-by-one (a 120-char retained prefix plus `…#` plus 8 hex is 130 chars against a declared 129 cap) is exactly the bug this derivation kills. Rendering is idempotent (the 130-char output re-renders unchanged), and writer (upsert), resolver, and read normalizer all route through this one helper — applied before upsert AND before resolution matching, so the same transformation on both sides keeps matching exact while the full-value digest keeps two long identities sharing a truncated prefix distinct. `error` stays ≤300 chars. Worst-case record arithmetic: `tool` ≤130 chars, `target_key` ≤130 (the COMPLETE composed key — readable portion plus its `+N` and `#`-digest suffixes — passes through `render_bounded_identity` as its one final transform, so the stored form shares the same 130-char authority as `tool`; composition order in `extract_target_key` below), `error` ≤300, two canonical seconds-precision ISO timestamps (≤32 chars each — the fixed emitter form the normalizer enforces below), `count` rendered at most 6 digits (the `MAX_TOOL_ERROR_COUNT` saturation cap below), plus key/formatting overhead — under 700 chars per record; 10 records plus the `Unresolved Tool Errors:` header render under ~7,500 chars, a hard bound far below `TRANSCRIPT_FALLBACK_MAX_CHARS` (24,000) that 2.3's reserve arithmetic depends on.

**Every stored field is structure-safe as well as bounded — sanitized BEFORE the length bound, identically on upsert and resolve sides**: `tool`, `target_key`, and `error` pass through one deterministic `sanitize_record_text` step that collapses CR/LF and all other control characters to single spaces (the stored value is always one line) and backslash-escapes a leading markdown-structural token (`#`, backtick-fence, tilde-fence). Caller-controlled error text and command excerpts are routinely multiline and can embed lines like `## Next Steps` or fence delimiters; rendered into a generated summary, such a line would fabricate an EARLIER mandatory heading and steal 2.1's first-occurrence guarantee from the genuine section — 2.3 renders these fields and its summary template copies them into an output section. Sanitizing at write time makes every downstream consumer safe by construction; because it precedes the truncate+digest bound on both the upsert and the resolve path, matching stays exact.

**Write-time guarantees require exclusive write ownership — `open_tool_errors` is reserved against external setters, and every read normalizes**: the tracker is NOT the only writer today. The public variable surface (`set_variable` in the workflows tool module and its top-level alias) accepts arbitrary session-variable names with list/dict values and delegates to the generic `SessionVariableManager.set_variable` — an external caller could overwrite `open_tool_errors` with multiline heading/fence content, unbounded fields, malformed records, or an arbitrarily large list, bypassing every bound above. Two-layer fix. (1) **Reservation**: add `open_tool_errors` to `RESERVED_WORKFLOW_VARIABLES` (`src/gobby/workflows/reserved_variables.py`) — the public setter already rejects reserved names via `is_reserved_workflow_variable` before any write (plain and workflow-scoped forms alike), so this is one frozenset entry with no setter-module change; the tracker's dedicated `upsert_open_tool_error`/`resolve_open_tool_errors` methods are trusted runtime writers and unaffected, and reads via `get_variable` stay open. (2) **Canonical read normalization, defense in depth**: one `normalize_open_tool_error_records(raw) -> list[dict]` in `tool_error_tracker.py`, applied wherever stored state is consumed — inside the tracker's upsert/resolve transactions when they read existing state, and in 2.3's `load_open_tool_errors`. A non-list value yields `[]`; per record: non-dict shape or missing identity/timestamp keys → dropped; `tool`/`target_key`/`error` → `sanitize_record_text` plus hard caps at the write-time worst-case bounds (tool ≤130 and target_key ≤130, EACH via the same `render_bounded_identity` helper applied to the whole stored value under the one `MAX_IDENTITY_COMPONENT_CHARS` authority, error ≤300 — the write bounds ARE the normalizer caps and both sides render through the one helper, so tracker-written records — already ≤130 and fixed points of the idempotent render — pass through byte-identical and matching stays exact); `count` → coerced to an int and clamped into `[1, MAX_TOOL_ERROR_COUNT]` (module constant `999_999` in `tool_error_tracker.py`, non-numeric → 1) — the same fixed cap the tracker's saturating increment enforces, so a stored count renders at most 6 digits and a directly seeded multi-kilobyte positive int (Python ints are arbitrary-precision and any positive value passes a positivity check) can never carry stored or rendered bytes; unparsable ISO timestamps → record dropped, and parseability alone is NOT acceptance — every accepted timestamp is normalized into ONE canonical comparable time domain (aware UTC) before anything compares or emits it: an offset-naive parseable timestamp drops its record under the same policy as an unparsable one (the tracker, the sole trusted writer, always emits aware UTC, so a naive value proves foreign origin and names no unambiguous instant — assigning it a zone would be a guess the normalizer never makes), and an aware timestamp at ANY offset converts through `astimezone(timezone.utc)` then re-emits via the one canonical emitter `isoformat(timespec="seconds")` — `datetime.fromisoformat` accepts arbitrarily long parseable fractional-second strings, so parse-only validation would pass a multi-kilobyte timestamp verbatim, and parseability does not even guarantee mutual comparability (a naive/aware datetime comparison raises `TypeError`, while string ordering across differing offsets is not chronological — either failure mode would break the newest-record selection below); the tracker writes timestamps with that same aware-UTC seconds-precision emitter, keeping tracker-written records byte-identical through normalization (the UTC conversion is a no-op on them); the list is capped to 10, newest kept by comparing the NORMALIZED aware-UTC `last_at` datetimes — mutually comparable by construction, never raw strings or pre-normalization values. Rows seeded before the reservation existed, or by any writer bug, can therefore never surface unbounded or structure-breaking content downstream.

- `extract_target_key(data, arguments) -> str` — injective up to hash collision AND resolution-compatible. File tools: the key basis is the FULL sorted canonical path list — rendered as `canonical_file_paths[0]` (or the single path) plus `+N` when more, suffixed `#<first 8 hex of sha256 over the full sorted path list>`. Execute tools: the first 80 chars of the command, suffixed `#<same digest over the FULL command string>`. Otherwise the argument fingerprint `args:<digest over canonically-sorted normalized arguments>` (never None). The digest basis is the complete extracted target (all paths / whole command), NOT all arguments — so a later success against the same target still resolves the record (an `Edit(A)` retry with different content resolves `Edit(A)`), while two commands sharing an 80-char prefix, or two multi-file events sharing `paths[0]` with different path sets, can never collide. Composition order is fixed: compose the readable raw key WITH its target-digest suffix first, then apply `render_bounded_identity` to the ENTIRE composed key as the single final transform — the returned `target_key` is ≤130 chars and is the exact stored, matched, and normalized form at all three boundaries (write, resolve, read-normalize). When the composed key exceeds 130 chars, the render keeps the derived 120-char prefix and appends `…#` plus 8 hex over the FULL composed key; the embedded target digest participates in that outer digest, so distinctness survives truncation, and recomposing the same target reproduces the identical composed key and hence the identical stored form.
- `track_tool_outcome(sv_mgr, session_id, event)` — on failure: upsert (repeat failure of same `(tool, target_key)` updates in place: `count += 1` saturating at `MAX_TOOL_ERROR_COUNT`, refresh `error`/`last_at`); on success: resolve matching records. Policy denials are excluded structurally by the ownership contract below — NEVER by message-prefix matching, which would couple this to P1's message format.
- `track_proxy_outcome(sv_mgr, session_id, caller_identity, final_identity, result, outcome_class)` — the proxy-native entry point used by the finalization wrapper below. It takes TWO identities, each a `(server_name, tool_name, arguments)` triple keyed as `"{server_name}/{tool_name}"` with the same target-key extraction: the CALLER identity (what the wrapper received — before-tool rules cannot change it) and the FINAL dispatch identity (what actually dispatched — rules may rewrite any of server, tool, and arguments via `modified_input`, `result_handling.py:279-292`, so the two can differ on a successful retry). `failed_pre_dispatch` upserts keyed by the caller identity; `executed` results are classified via `classify_raw_tool_result` (this leaf adds that raw-result entry point to the canonical classifier authority in `src/gobby/hooks/tool_outcomes.py` — it accepts plain dicts, strings, and `CallToolResult` objects including enriched error dicts and nested failures; 3.3 reuses it for offload gating), with record `error` text drawn from `extract_error_snippet`, and are tracked keyed by the final identity per the ownership contract's class handling below.

**Single-owner-per-transport contract (kills double-counting AND deny-echo recording with zero marker machinery)**: one logical tool outcome can surface twice — once at the proxy and again as the CLI's PostToolUse echo of the same wrapper call — and tracking both would increment `open_tool_errors.count` twice per failure. Ownership is split by transport, each outcome tracked exactly once:

- **The proxy finalization wrapper owns ALL proxy-entry outcomes, classified structurally at each return site.** The after-tool site alone cannot: `call_tool` (`src/gobby/mcp_proxy/services/tool_execution.py:169-334`) has failure returns BEFORE `_execute_tool_dispatch`, and `apply_after_tool_workflow` (`src/gobby/mcp_proxy/services/result_handling.py:295-347`) early-returns when the workflow handler is absent or evaluation raises. Restructure instead: the current `call_tool` body becomes `_call_tool_impl`, returning a small internal outcome struct — `(result, outcome_class, effective_session_id, final server/tool/arguments)` with `outcome_class ∈ {policy_denied, invalid_call, failed_pre_dispatch, executed}` assigned structurally at each return site — and the proxy-namespace recursion re-enters `_call_tool_impl` so finalization runs exactly once per external call. Return-site map: the caller argument-preparation failure and the schema-validation failure (both `build_invalid_arguments_response`), the unresolved-namespace `SERVER_NOT_FOUND` return, and the direct named-server membership preflight rejection → `invalid_call`; the session tool-filter block → `policy_denied`; dispatched results → `executed`. The membership preflight is new mechanism this leaf adds because class totality demands it: today a direct unknown server name sails PAST schema pre-validation (the failed schema fetch is caught and validation skipped, fail-open — `tool_execution.py:286-292`), reaches `_execute_tool`, and returns as a dispatched `SERVER_NOT_FOUND` error result (`tool_execution.py:373-425` via the message classifier) — which the map above would class `executed` and upsert under an identity no corrected call can ever resolve. So `_call_tool_impl` rejects the caller-supplied server name immediately after the proxy-namespace branch, with the same structured `SERVER_NOT_FOUND` shape (reusing `_get_server_suggestion`), when the name resolves to no dispatchable server. Membership mirrors dispatch's own branch structure (`tool_execution.py:383`), making the preflight verdict equivalent to dispatch resolvability by construction: when `_internal_manager` is present and `_internal_manager.is_internal(server_name)` holds — the reserved `gobby-` prefix ROUTER (`tools/internal.py:444`), a pure prefix test, deliberately NOT treated as membership — membership means `_internal_manager.get_registry(server_name) is not None` (`tools/internal.py:458`, the actual registry lookup); on the other branch membership means `MCPClientManager.has_server` (`src/gobby/mcp_proxy/manager.py:137`). Both predicates exist today — no new inventory machinery — and the check stays structural at a structural return site, no message or error-code matching. The branch-mirroring is load-bearing twice over: an unknown internal-prefix name (`gobby-does-not-exist`) passes the prefix router but has no registry — dispatch would raise `Internal server '<name>' not found` (`tool_execution.py:395-399`) into the catch-all as a dispatched executed-class result under an unresolvable identity — and an external server pathologically configured under the reserved `gobby-` prefix is rejected too, because dispatch routes every `gobby-*` name to the internal branch and would fail it regardless of external registration. Placement before before-tool enforcement is deliberate — an unknown caller-supplied name is a deterministic input rejection exactly like the namespace miss beside it, and rules never see namespace-miss calls today either. Two documented residuals stay `executed`-class with sound-or-accepted resolution: a server removed between preflight and dispatch fails at dispatch keyed by the final identity, and re-adding the server then retrying repeats that identity and resolves the record; a before-tool rule that rewrites dispatch to an unknown server fails at dispatch keyed by the rewritten final identity, and fixing the rule then retrying dispatches under a different final identity, leaving the stale record to cap eviction — the same accepted residual as an edited-command correction (`count`/`last_at` signal staleness). The before-tool return is NOT one class: `apply_before_tool_enforcement` (`result_handling.py:165-292`) today collapses four distinct failures into one `workflow_error` shape, so it gains an explicit outcome discriminant — a fifth tuple element `before_outcome ∈ {policy_denied, failed_pre_dispatch}` assigned at each of its return sites: the actual deny decision (`response.decision != "allow"`) → `policy_denied`; failed Codex reconciliation, raised workflow evaluation, and invalid RULE-rewritten arguments → `failed_pre_dispatch` (operational failures — the rewrite came from a rule, not the caller, so a retry with unchanged arguments legitimately resolves them). `_call_tool_impl` propagates that discriminant into its outcome struct. The public `call_tool` is the single finalization path: it calls the impl and invokes `track_proxy_outcome` with both identities — its OWN parameters are the caller identity; the outcome struct carries the final dispatch identity — via `await asyncio.to_thread(track_proxy_outcome, ...)`, wrapped in try/except that logs at debug, then returns the result. The executor bridge is mandatory, not stylistic: `track_proxy_outcome` drives the tracker's synchronous `transaction_immediate` read-modify-write, the public `call_tool` is async, and every other blocking operation on that path already crosses `asyncio.to_thread` — a direct invocation would block the daemon event loop on every session-resolved proxied call under DB latency. `handle_after_tool` needs no bridge: it is a synchronous hook handler, so `track_tool_outcome` already runs on its caller's worker thread, off the event loop. Class handling: `policy_denied` and `invalid_call` → never tracked; `failed_pre_dispatch` → upsert keyed by the CALLER identity (the failure predates any rule rewrite, and the caller's retry repeats exactly that identity even when the rules then rewrite the dispatch); `executed` success → resolve BOTH the caller-identity key (closing any standing pre-dispatch record) and the final-identity key (closing any standing executed record), collapsed to one resolve when the identities coincide; `executed` failure → upsert keyed by the final identity, and ALSO resolve the caller-identity key ONLY when the two keys differ — reaching dispatch at all proves the pre-dispatch stages cleared, so a rewritten retry closes its pre-dispatch record even when the dispatched call then fails, while the only-when-different guard keeps a same-identity repeat failure updating its record in place (`count += 1`) instead of resolve-then-upsert resetting it. Tracking is fully independent of after-tool workflow availability — `apply_after_tool_workflow` hosts no tracking at all.
- **`invalid_call` is an explicit, tested exclusion grounded in resolution soundness, not a gap**: deterministic caller-input rejections (malformed arguments, an unknown server name — the unresolved proxy-namespace return and the direct membership preflight rejection on either branch, unknown internal-prefix or unconfigured external, alike — and schema-validation failure) are keyed by a fingerprint of the very arguments that caused the failure — a corrected call NECESSARILY carries different arguments, can never match the record, and the record would stay open forever (surviving into handoffs until cap eviction) while telling the reader nothing the in-turn structured error did not. So they are never recorded. The tracked classes have sound exact-match resolution by construction: a `failed_pre_dispatch` failure is operational and keyed by the CALLER identity, which no before-tool rule rewrite can alter — the retry repeats that identity, and any completed dispatch of it (executed success or failure) resolves the record, so the rules rewriting the server, tool, or arguments on the successful retry cannot strand it; an `executed` failure keys by extracted target (file paths / command) or by the argument fingerprint, where the arguments ARE the stable target identity (a `close_task(A)` retry after fixing the blocker repeats the same arguments). Accepted residual, documented and tested: an `executed` failure whose correction changes the arguments (an edited command) leaves the original record standing until cap eviction — `count`/`last_at` signal staleness and the cap bounds the noise.
- **`handle_after_tool` (`src/gobby/hooks/event_handlers/_tool.py:158`) owns native CLI tools only** and SKIPS wrapper echoes via `is_wrapper_echo_event`: every CLI after-event for the wrapper tool is an echo of a call the proxy already finalized, so tracking it would always be a duplicate. Add one guarded call to `track_tool_outcome` covering both the failure and success paths, gated on `not is_wrapper_echo_event(event)`, wrapped in try/except that logs at debug — error tracking must never break tool handling.
- **Policy denials are structurally excluded by return site, never by result shape**: the before-tool deny decision (`response.decision != "allow"`, carried by the `before_outcome` discriminant) and the session tool-filter block are the only two `policy_denied` sites — a denied call never reaches dispatch and the wrapper never tracks that class; its CLI PostToolUse echo (an apparent tool failure carrying only deny prose) is wrapper-shaped and skipped. CLI-side PreToolUse denials never execute the tool and produce NO after event. No deny marker, no correlation window, no message or error-code matching — the previous `recent_rule_denials` design is superseded by this ownership split.
- **The public wrappers above the service add no tracked outcomes — their local failures are all excluded classes, by inventory** (no wrapper file is modified by this leaf; §3.4's threading-site inventory lists both wrapper locations): the FastMCP wrapper `GobbyDaemonTools.call_tool` returns locally before delegating on canonicalization failure, missing `server_name`/`tool_name`, `project_id` with no database, unresolvable `project_id`, and unresolvable `session_id`; the stdio wrapper `call_tool` returns locally on canonicalization failure, missing routing fields, and the stale-wrapper check, and a failed daemon preflight surfaces before the daemon proxy runs. The input-shaped failures in each list (canonicalization, missing routing, unresolvable project) are `invalid_call`-class deterministic rejections — untracked by the soundness rationale above; unresolvable session falls under the unresolvable-session exclusion; and a failed preflight means the daemon is unreachable, so the no-ownership-gap argument below applies. The unconditional wrapper-echo skip therefore stays sound with ZERO wrapper-side tracking code: every CLI echo of a wrapper call corresponds to an outcome either finalized by `ToolProxyService.call_tool` or belonging to an explicitly excluded class — no failure class has the skipped echo as its only observer. - **Unresolvable-session outcomes are an explicit, tested exclusion, not a gap**: records live in a session's `open_tool_errors` variable, so tracking requires a resolved session — the invalid-session-reference return and calls with no resolvable session context are untracked by definition (there is no session state to attach to), and their wrapper echoes are still skipped.
- **No ownership gap**: a transport failure that prevents the proxy from processing a wrapper call (daemon unreachable) also prevents the CLI's hook event from reaching the daemon — `ghook` posts to the same process — so no failure class is observable only via the skipped echo.

### 3.3 Implement the offload gate service [category: code] (depends: 3.2, 2.2)
`kind: deliverable`

Targets: `src/gobby/mcp_proxy/services/result_offload.py` (new), `src/gobby/mcp_proxy/server.py`

`ToolResultOffloader(store, db, config, project_id_getter)` with one public method `async maybe_offload(*, server_name, tool_name, result, session_id, intent) -> Any` (sync work via `asyncio.to_thread`):

Error detection reuses the existing canonical authority — `src/gobby/hooks/tool_outcomes.py` (`normalize_tool_outcome`, line 282, with nested-container signal collection) owns tool-result classification, and 2.2 supplies the raw-result entry point `classify_raw_tool_result(result) -> ToolOutcome` there (accepts plain dicts, strings, and `CallToolResult` objects — `normalize_tool_outcome` takes event mappings; hence the depends on 2.2). Do NOT create a parallel classifier. Use it from the offloader AND the error-to-`CallToolResult(isError=True)` conversion in the daemon tools front door (`src/gobby/mcp_proxy/server.py:167`, whose live sniff treats ANY dict containing `error` without `success` as failure — broader than a lone `error` key; enriched error dicts like `{error, hint, schema}` must not be offloaded into apparent successes).

1. Pass through untouched when: disabled; `fnmatch(f"{server_name}/{tool_name}", pat)` matches an exempt pattern; `classify_raw_tool_result` reports failure (including `CallToolResult.isError` and nested failures); or external content includes non-text items (images/blobs — base64 cannot be previewed or BM25-searched).
2. Serialize — TOTAL over every reachable successful result shape (`InternalToolRegistry.call` returns whatever the handler returns and `normalize_internal_success_result` passes every non-dict through unchanged, so top-level lists, tuples, and bare JSON scalars are reachable successful wrapper results) — in TWO explicit stages so no branch can leave unserialized structure at the measurement or storage boundary. Stage 1, unwrap: a `CallToolResult` reduces to its payload — `structuredContent` when present (mapping-valued in the live external-success shape: `src/gobby/integrations/mcp_result.py:27-29`, `tests/sync/test_mcp_result.py:10-13`), else the joined text parts (a str); every other result is its own payload. Stage 2, serialize the payload under ONE rule regardless of provenance: payload str as-is (`content_kind="text"`, unquoted); EVERY other payload — dict/mapping (an unwrapped `structuredContent` included), list/tuple, and JSON scalars alike — → `json.dumps(indent=2, default=str)` (`content_kind="json"`). The threshold comparison, `max_stored_chars` bound, chunking, and envelope budgeting all operate on that serialized TEXT — a mapping-valued `structuredContent` must never reach the `len` measurement or `ToolResultStore.save` as a dict (`len` of a dict counts keys, silently defeating the threshold). No successful shape falls outside these branches: only a `json.dumps` raise (e.g. circular references) is a genuine serialization failure eligible for verbatim passthrough. If `len <= threshold_chars`, return the original result.
3. Store (bounded at `max_stored_chars`) and build the envelope — a raw payload dict with NO `success`/`error` keys so the shared classifier treats it as success:

```json
{
  "offloaded": true,
  "result_id": "…",
  "server_name": "…", "tool_name": "…",
  "content_kind": "json",
  "total_chars": 187432, "stored_chars": 187432,
  "structure": {"type": "object", "keys": {"docs": "list[142]", "meta": "object"}},
  "preview": "…first preview_chars…",
  "matches": [{"ordinal": 17, "start_offset": 34120, "end_offset": 36080, "score": 8.1, "content": "…"}],
  "retrieval_available": true,
  "guidance": "Output exceeded {threshold_chars} chars and is retrievable for {retention_days} days. Search it: call_tool('gobby-results','search_tool_result',{'result_id':…,'query':…}). Page raw content: get_tool_result. Tip: pass intent='<what you need>' on call_tool to get matched sections directly."
}
```

`guidance` renders the CONFIGURED `threshold_chars` and `retention_days` values — never hard-coded literals — and phrases the contract as "retrievable for N days" (retention is enforced at read; expired rows are physically pruned opportunistically on the next `save`, so retrievability, not on-disk lifetime, is the guarantee).

`matches` is present only when `intent` was provided (BM25 query against the just-stored chunks, limit `intent_match_limit`). **The intent search is advisory and can never fail the call**: pg_search parse errors AND every other backend failure — `BM25SearchBackend.search` (`keyword.py:150-177`) re-raises all non-parse exceptions — are caught at this search call: log a warning and return the normal persisted envelope with `matches` omitted, `retrieval_available: true`, and the `result_id` intact. A post-store search failure is never replaced by the persistence-failure fallback (the result IS stored and retrievable) and never escapes `maybe_offload` to turn a successful tool call into a wrapper failure. `structure` summarizes top-level keys and list lengths for JSON payloads; a top-level list reports `{"type": "list", "length": N}`.

**Intent is bounded before it touches the sanitizer or BM25**: `intent` is caller-controlled free text threaded from every conversational entry point with no schema cap. The offloader truncates it to `MAX_PG_SEARCH_QUERY_CHARS` (the fixed module constant from 3.2) BEFORE `sanitize_pg_search_query` runs — the cap bounds the O(n) sanitizer pass too, so a multi-megabyte intent never costs more than the constant. Intent is advisory metadata, so over-length never fails the call; an intent that is empty, whitespace-only, or sanitizes to empty (all punctuation) is treated as absent — preview-only envelope, no BM25 query executed.

**Envelope size invariant**: the serialized envelope never exceeds `max_envelope_chars` (default 8,000 — below `threshold_chars` by construction; validate this relation in config). The invariant is enforced on the FINAL result at the entrypoints, so the budgeter's working target is `max_envelope_chars - _WRAPPER_MUTATION_RESERVE` (module constant, 512): after the proxy returns, EVERY conversational entrypoint transforms the successful result before the caller sees it, and one path stacks two transformations. The FastMCP wrapper `GobbyDaemonTools.call_tool` (`server.py:305-315`) merges a capped-wait `_mcp_metadata` dict in place. The HTTP routes pass results through `_process_tool_proxy_result` → `_success_response_payload` (`execution.py:252-311/:44-59`, a §3.4 threading target), and because the envelope deliberately carries NO `success` key it is ALWAYS wrapped there under `{"success": true, "result": <envelope>, "response_time_ms": …}`. The stdio path COMPOSES: the stdio proxy receives that HTTP-wrapped payload and the stdio wrapper (`stdio_tools.py:216-220`) then adds three top-level timeout keys on top of it. The reserve is therefore sized for the worst CUMULATIVE chain, not the worst single site: the HTTP success wrapper adds ~60 chars of keys, nesting, and a bounded float; the stdio timeout keys add ~110 (three keys, two bounded numerics, one bool); their composition stays under 200, and the FastMCP `_mcp_metadata` merge alone stays near 200 — every final form fits within 512 with headroom. 3.4's acceptance asserts the final serialized size at each entrypoint, including the composed HTTP+stdio chain. Budget within the working target: fixed fields + guidance first, then `structure` (cap at 20 top-level keys, `"…"` marker beyond), then `preview` (up to `preview_chars`), then `matches` — each match snippet trimmed to fit the remaining budget, dropping trailing matches rather than exceeding the cap. Assert the invariant in tests with adversarial inputs (huge keys, 5 full-size matches).

**No unbounded "fixed" fields**: `server_name` and `tool_name` enter through unbounded caller strings (the public wrapper accepts arbitrary text — `GobbyDaemonTools.call_tool`, `server.py:167`), so they participate in the budget like everything else: render each through 2.2's shared `render_bounded_identity` helper (the single `MAX_IDENTITY_COMPONENT_CHARS = 130` total-length authority; truncated forms carry `…#` plus an 8-hex digest) so the identity stays distinguishable and the bound is exact. With that bound plus the two-sided config bounds from 3.1 (guidance renders `threshold_chars`/`retention_days` with bounded digit counts), the fixed-fields + guidance worst case is a small constant below the `ge=2_000` floor — the arithmetic that makes the floor claim true. The same bounded rendering applies to the persistence-failure fallback envelope.

**Bounded storage, reported honestly**: content beyond `max_stored_chars` is not stored; the envelope reports `stored_chars < total_chars` and the guidance states the tail is not retrievable (the source system still holds the original). Verbatim passthrough of multi-megabyte results is explicitly rejected — it is the failure this feature exists to prevent.

**Bounded fallback on persistence errors — never verbatim fail-open**: when serialization succeeds but save/index persistence fails (Postgres down, insert error), log a warning and return a bounded inline fallback envelope built by the SAME envelope budgeter — `structure`, `preview`, `total_chars`, `retrieval_available: false`, no `result_id`, and guidance stating the omitted tail cannot be retrieved. A Postgres outage must not bypass the context-size protection this phase exists to provide. Verbatim passthrough remains only for tool failures, non-text content, and genuine serialization failures (without serialized text there is nothing to budget).

### 4.1 Add TTL freshness check and cached bucket to URL ingest [category: code]
`kind: deliverable`

Targets: `crates/gwiki/src/ingest/url.rs`, `crates/gwiki/src/ingest/mod.rs`, `crates/gwiki/src/support/time.rs`, `crates/gwiki/src/sources/types.rs`, `crates/gwiki/src/sources/manifest.rs`, `crates/gwiki/src/collect.rs`, `crates/gwiki/src/collect/tests.rs` (new), `crates/gwiki/src/commands/refresh/candidate.rs`, `crates/gwiki/src/commands/refresh/tests.rs`, `crates/gwiki/src/ingest/url/tests.rs`, `crates/gwiki/src/health.rs`, `crates/gwiki/src/health/tests.rs` (new), `crates/gwiki/src/upkeep.rs`, `crates/gwiki/src/upkeep/tests.rs` (new), `crates/gwiki/src/citations.rs`, `crates/gwiki/src/commands/citation_quality.rs`, `crates/gwiki/src/commands/compile.rs`, `crates/gwiki/src/commands/refresh/selection.rs`, `crates/gwiki/src/commands/sources.rs`, `crates/gwiki/src/compile/select.rs`, `crates/gwiki/src/paths.rs`, `crates/gwiki/src/recap.rs`, `crates/gwiki/src/transcribe.rs`, `crates/gwiki/src/video/tests.rs`, `crates/gwiki/src/vision.rs`, `crates/gwiki/src/sources/tests.rs`, `crates/gwiki/src/ingest/video/tests/frame_assets.rs`

TTL is a per-request parameter, never stored — freshness is caller policy. In `ingest_urls_with_fetcher` (`crates/gwiki/src/ingest/url.rs:186`), read the source manifest once per batch (the vault JSON index with fs4 locking — `crates/gwiki/src/sources/manifest.rs:115`; `SourceRecord.fetched_at` already exists in `unix-ms:{millis}` format, `crates/gwiki/src/support/time.rs:3`).

**Fetch provenance is required for a cache hit**: `collect_inbox` (`crates/gwiki/src/collect.rs:45`) registers unfetched URL stubs with a fresh `fetched_at`, the same `SourceKind::Url`, and the same canonical location as real ingestion — a freshness-only predicate would mistake a stub for fetched content and skip the FIRST network fetch. Add a provenance field to `SourceRecord` (`crates/gwiki/src/sources/types.rs`), e.g. `fetch_provenance: fetched | stub`: real URL ingestion writes `fetched`, collect writes `stub`. Add a freshness field `last_verified_at` (`unix-ms`) alongside it, initialized to the capture `fetched_at` at registration. `fetched_at` stays the IMMUTABLE capture time — `ingest_snapshot_without_index` (`crates/gwiki/src/ingest/url.rs:83-122`) assigns `snapshot.fetched_at = record.fetched_at` precisely so an unchanged re-ingest reproduces byte-identical raw content (#17644), so advancing `fetched_at` for freshness would break raw-write idempotency; `last_verified_at` is the separate freshness authority that later verifications advance. No migration shims (0.5.0 unshipped); records without these fields are treated as `stub` with `last_verified_at` defaulting to `fetched_at`.

A URL is a cache hit ONLY when ALL hold: `max_age_hours > 0` (zero disables caching outright — with `age <= ttl` alone, a record fetched in the same millisecond would be a hit at TTL 0), `canonical_location == canonicalize_location(requested_url)` (`crates/gwiki/src/sources/render.rs:47`), `fetch_provenance == fetched`, freshness holds under checked arithmetic against `last_verified_at`, AND **cache integrity holds**. Eligibility is provenance-based, NOT kind-based: `source_kind_for_url_response` (`crates/gwiki/src/ingest/url/render.rs:92-104`) classifies fetched non-HTML payloads as `Pdf`/`Image`/`Audio`/`Video`/`Text`/`File` — never `Url` — so a `kind == Url` gate would permanently exclude every non-HTML `ingest-url` success from caching, defeating P4's command-wide goal. `fetched` provenance plus the canonical-location match fully identifies URL-fetched records regardless of media kind (no non-URL pipeline ever writes `fetched`), mirroring refresh's own location-based `is_url_source` (`crates/gwiki/src/commands/refresh/selection.rs:231`); kind's only cache role is selecting the integrity artifact set below. When several manifest entries share a canonical location (content-addressed ids let a stub and one or more fetched versions coexist), the candidate is the `fetched`-provenance entry with the newest `last_verified_at`; stub entries are never candidates. A hit skips fetch AND indexing for that URL. Accepted caveat: requested-vs-final-URL redirects miss the cache — same miss class as today's content-hash dedup.

**Cache integrity + checked arithmetic**: manifest metadata alone is not trusted — before declaring a hit, verify EVERY on-disk artifact the record's URL ingest branch owns. The HTML branch (`ingest_snapshot_without_index`, `crates/gwiki/src/ingest/url.rs:83-122`, `kind == Url`) owns exactly `raw/<id>.md` via `write_raw_markdown`; the non-HTML branch (`ingest_non_html_snapshot_without_index`, `url.rs:124-160`, every other fetched kind) owns `raw/<id>.md` PLUS an asset `raw/assets/<id>.<ext>` written unconditionally by `write_asset` (`url.rs:141`) — its raw markdown stores only a `source_asset` reference plus degradation prose, so a raw-only check would declare a hit on a record whose actual payload is gone. NO URL ingest branch writes a derived note — `index_after_ingest` (`crates/gwiki/src/ingest/mod.rs:146-190`) creates nothing, indexing `raw/INDEX.md` plus whatever `knowledge/sources/*.md` notes OTHER pipelines (document/session derivation) already put on disk — so a chunk- or index-backed integrity predicate is undefinable over the URL success path (a first URL ingest into an empty vault owns zero indexed chunks forever), and index state is irrelevant to what a hit skips anyway. Raw predicate: `vault_root.join(raw_source_path(&record.id)?).is_file()` — `raw_source_path` returns the VAULT-RELATIVE `raw/<id>.md`, so a bare `exists()` on its return value would resolve against the process working directory and turn every out-of-vault invocation into a permanent cache miss. Asset predicate (non-`Url` kinds only): the asset extension derives from the ingest-time file name (`asset_path`, `crates/gwiki/src/ingest/mod.rs:557-562`) and is NOT reconstructible from the record, so scan `vault_root.join("raw/assets")` for a file whose stem equals `record.id` — content-addressed ids make the stem unique. Any required artifact missing → treat as a miss and refetch (self-healing, no error); partial self-heal is safe because `write_immutable` (`ingest/mod.rs:370-409`) validates byte-identical existing files instead of clobbering — an unchanged refetch re-derives identical bytes for the surviving artifact and writes only the missing one, while changed content registers a NEW content-addressed id with fresh paths. Freshness math: `ttl_ms = max_age_hours.saturating_mul(3_600_000)`; `age = now_ms.checked_sub(parse_unix_ms(last_verified_at))` — a `None` (future timestamp, corrupt manifest) is a miss, never a panic or wraparound hit.

**Refresh keeps freshness honest**: `gwiki refresh`'s unchanged-content path (`crates/gwiki/src/commands/refresh/candidate.rs` — pushes `RefreshResult` and returns without touching the record) must advance the manifest `last_verified_at` (and promote `fetch_provenance` to `fetched`) on every SUCCESSFUL refresh, including unchanged content — a freshly verified URL is fresh, not expired. Failed refreshes leave the record untouched. The deterministic seam for proving this is the PRIVATE injected-fetch helper `execute_with_fetcher` (`refresh/mod.rs:42-52`) — in Rust only its child modules can call it, so the refresh-side freshness test lives in `crates/gwiki/src/commands/refresh/tests.rs` alongside the existing injected-refresh tests (4.1.5); the URL-cache-only cases stay in the ingest-url test module, which cannot reach that seam.

**Unchanged `ingest-url` refetch advances freshness too — atomic post-success touch/promotion**: today `SourceManifest::register_parts_with_content_hash` (`crates/gwiki/src/sources/manifest.rs:115-147`) returns an existing canonical-location/content-hash match UNCHANGED, so an expired URL whose content has not changed would stay expired forever and refetch on every ingest, and a pre-field record (defaulted `stub`) would never become cacheable. When a successful fetch dedups to an existing record, atomically — inside the same `with_manifest_lock` critical section — advance that record's `last_verified_at` to the new snapshot's fetch time, promote `fetch_provenance` to `fetched` (monotonic: a `fetched` record is never demoted; this is also how a pre-field record promotes on its first unchanged refetch), persist the manifest, and return the UPDATED record. `fetched_at` is not modified (raw-write idempotency above), so the raw file stays byte-identical and the stable content-addressed source id is preserved.
