# Hourly reconcile apply

Plan artifact: `.gobby/plans/task-23584.md`

**Plan ID:** task-23584

## Overview
`kind: framing`

Task #23584 holds deferred item D1.1 of the approved plan
`.gobby/plans/code-index-vector-reconciliation.md`: "The hourly prune runs reconcile
for each project. It applies only orphan deletion and flag reset, with a receipt under
the daemon's private state directory, and reports counts in the prune result."

This plan delivers that item in the native hourly prune. It adds one unattended entry
to the `gcode vector reconcile` module, calls it from `job_prune::prune_all` for each
project that prune has just handled, and stores receipts under the daemon's home. A
run holds, and applies nothing, when its proposed change exceeds a volume ceiling of
one delete batch or a tenth of the project, whichever is larger.

**Wipe bound, for the operator's review.** At or below that ceiling a run applies with
no person reading it. One run can delete up to `max(256, points_scanned / 10)` points
and reset versions holding up to `max(256, pg_symbols / 10)` symbols, so a project with
256 points or fewer can lose all of its points in one run, and a project with 256 synced
symbols or fewer can have all of them reset. A hold stops only that run: nothing latches, so a
later inventory at or below the ceiling applies with no review. Vectors are a
rebuildable projection, so the cost is re-embedding and lost recall until the rebuild
finishes. Decision Record 5 has the reasoning.

Out of scope:
- The Live Maintenance Procedure itself, which keeps its source plan and owner.
- Any change to the `gcode vector reconcile` CLI flags or the gcode contract.
- Any Python change. The Python hourly prune stops existing at #24702.
- The operator route `POST /api/code-index/prune`, which never reconciles.

## Decision Record
`kind: framing`

1. **Does this need to exist.** P1 of the source plan landed (#23571 closed
   2026-10-31), so the known bulk drift sources S1 to S4 are closed. What remains is
   the detached writer of source Decision Record 8, regressions of that class, and any
   future change to `Symbol::make_id`. Expected hourly work after the first reviewed
   run is near zero. D1 is still an operator-approved obligation, the build is small,
   and orphan points cost search recall through the overfetch window when they
   accumulate. So the plan builds it and keeps the hourly no-work path cheap. Closing
   #23584 without building would need an operator ruling and a source-plan edit,
   because a deferral target closed `wont_do` fails the source plan's deferral gate.

2. **Carrier: native, in process.** D1's prose names `src/gobby/code_index/prune.py`
   and `gcode_gateway.py`. That prose predates the code-index family plan.
   #24702 (family section 8.4) deletes `prune_all_projects` and the hourly half of
   `prune.py`, and adds `crates/gcode/src/node/hub/job_prune.rs::prune_all`. The
   #25237 stepwise order places #24702 at step 66 and #23584 at step 121. A Python
   build would be scheduled for deletion before it ran. It would also need a
   decomposition of `gcode_gateway.py` (975 lines), and an amendment to #24702 to carry
   the behavior forward. P8 of the family plan runs its jobs in process on the hub's
   bootstrap DSN because gdaemon has no grant issuer, so a native call needs no child
   process, no grant and no contract change.

   This placement differs from D1's prose and keeps its intent: the hourly prune
   reconciles each project, applies only orphan deletion and flag reset, writes a receipt
   under the daemon's private state, and reports counts. The entry is a `pub(crate)`
   function in `crates/gcode/src/commands/vector/reconcile/`, called from
   `job_prune::prune_all`, and node-only projects take the gated second leaf. The
   Orchestrator ruled this on 2026-11-05: it needs no operator ruling, and the
   Orchestrator names the difference when it presents this plan.

3. **No digest handshake in the unattended path.** `--expect-digest` bridges the gap
   between a person reviewing a dry-run and that person applying it. An unattended run
   has no such gap, because no person reviews its inventory. It applies the inventory
   it builds under the maintenance lease. The safety invariant is unchanged and comes
   from source Decision Record 2: a point is deleted only when its ID is absent from
   `code_symbols` under the lease. The CLI keeps its digest requirement unchanged. The
   digest still names the receipt and identifies it. A digest comparison here would add
   no protection and could only produce false skips, because a pre-check outside the
   lease can observe a writer's in-flight state that the lease excludes.

4. **Pre-check outside the lease.** `maintenance_try()` takes the exclusive project key,
   and file writers take the shared key. Holding it across a full collection scroll
   every hour for every project would stall indexing for no work on most hours. The run
   therefore builds a read-only inventory first and returns with no lease when there is
   no work. A second inventory, under the lease, decides what is applied. Only a dirty
   hour pays for two scrolls and an exclusive lease.

5. **Hold ceiling.** A run applies nothing and reports `held` when either count exceeds
   its ceiling:
   - orphans: more than `max(256, points_scanned / 10)`;
   - reset symbols: more than `max(256, pg_symbols / 10)`. These are all the symbols of
     every synced-missing version, because a reset re-embeds the whole version even when
     only one of its points is absent (Decision Record 11).

   The ceiling is a volume guard on one run. The floor of 256 is one delete batch, so a
   small project is never held over a handful of points. The source plan's reason for
   deferring D1 is that a large backlog needs human review, and above this volume the
   ceiling is that review's unattended stand-in. Three concrete failures produce an
   inventory that is internally consistent and wrong to apply, and the ceiling holds each
   one only when its count exceeds the ceiling:
   - A restored or emptied `code_symbols` makes every point an orphan and would empty
     the collection.
   - A dropped or restored Qdrant collection makes every synced version missing and
     would queue a full re-embed of the project.
   - A project that missed the Live Maintenance Procedure would lose its historical
     backlog with no review.

   **Wipe bound.** At or below the ceiling a run applies with no person reading it. A
   project with 256 points or fewer can lose all of its points in one run, and a project
   with 256 synced symbols or fewer can have all of them reset. Vectors are a rebuildable
   projection, so the cost is embedding work and lost recall during the rebuild. Those are
   the costs the source plan's embedding constraint names, and the ceiling caps them for
   each run.

   **No latch.** Each inventory is judged alone, and no hold state is stored. A project is
   held for as long as its inventory exceeds the ceiling. The operator clears a hold by
   reviewing with `gcode vector reconcile` and applying through the CLI, which is the Live
   Maintenance Procedure's path and has no ceiling. A later inventory at or below the
   ceiling applies with no review, because every point it deletes is absent from
   `code_symbols` under the lease (source Decision Record 2) and its volume is within this
   guard. The guard does not bound change across runs either: a source that orphans a
   tenth of a project every hour is applied every hour, and it shows as nonzero counts in
   the job's line.

   The ceiling is two integer comparisons. The constants are compile-time, with no config
   key.

6. **Receipt storage for unattended runs.** This is the decision D1 reserved.
   - Path: `<gobby home>/code-index/reconcile-receipts/<project_id>/<digest hex>.json`,
     where the digest hex drops the `sha256:` prefix. Source item 2.2.8 refuses an
     existing receipt for a different digest, so a fixed per-project path would fail on
     every run after the first. The digest keeps a retry of the same inventory on one
     file, which 2.2 step 4 allows.
   - Home: `gobby_core::gobby_home()`, which honors `GOBBY_HOME`. `~/.gobby` is mode
     0700 and `~/.gobby/logs` is 0755 (observed 2026-11-05), so receipts get their own
     directory.
   - Creation: `run_unattended` canonicalizes the home only, joins
     `code-index/reconcile-receipts/<project_id>` to it, and runs `receipt::no_symlinks`
     on that path. It then creates the directory with
     `std::fs::DirBuilder::new().recursive(true).mode(0o700)`, as
     `crates/gcode/src/debug_output.rs` does. The home may sit under a symlinked prefix,
     such as `/var` on macOS, and `no_symlinks` walks every ancestor, so checking the
     home's original spelling would refuse a valid home. Below the home no component may
     be a symlink. The run never canonicalizes the joined path, because that would resolve
     such a component and hide it from the location check. A directory that already exists
     with other permissions fails the location check and the run reports `failed` with no
     mutation.
   - Retention: after each applied or failed run the project's directory keeps its 20
     newest receipts by modification time. A clean or held run writes no receipt and
     prunes nothing. Removal errors go to stderr and do not change the outcome.

7. **Reporting.** D1.1's "prune result" is the hourly job's result: a `ReconcileTotals`
   value and the job's stderr line. `GlobalPruneOutcome` stays as it is, because it is
   the route's response body, which family item 8.4.6 pins to Python's compact shape,
   and `gcode prune`'s parser reads the same type. P8 of the family plan already moved
   hourly outcomes to gdaemon's stderr. A project that is held, applied or failed gets
   its own line, so a hold is visible and names what to review. A failed run may already
   have reset flags and deleted a batch, because apply spans two stores. Its line and the
   totals carry its confirmed counts and receipt path, and its error says which write is
   unconfirmed. Only an `Ok` from `apply_inventory` is `applied`, because a receipt
   reading `complete: true` does not prove success (source 2.2).

8. **Reconcile outcomes never change the prune outcome.** A project whose prune
   succeeded stays in `completed` whatever its reconcile did. Reconcile failures are
   counted and logged, and the next hour starts over from a fresh inventory.

9. **Which projects run.** Only a project whose prune just succeeded in the `active`
   branch of `prune_all`, or in the `live` branch of the node-only step (1.2). A project
   with pending files is not reconciled that hour: its flags are moving, and a run would
   only add resets. That also gives apply its own back-off, because the versions it
   resets are pending until the workers drain them.

10. **No time budget.** Content GC takes a 90 s deadline because its backlog can be
    arbitrarily large. Reconcile's writes are bounded by the ceiling, and its reads by
    the collection size. Each Qdrant delete carries its own request timeout
    (`qdrant_delete_timeout`), so a failed request ends the run as `failed`. The job runs
    on its own thread, so a long pass delays only the next prune and any route caller
    waiting on `GLOBAL_PRUNE`.

11. **No repeat-reset guard.** `points_for_symbols` embeds every symbol of a version or
    returns an error, and it skips none (`crates/gcode/src/vector/code_symbols/lifecycle.rs`,
    excerpt_hash `dc729653332327c5357b92a3239ee70b9e2a79288f7dbf7d5e3d4e6a5984f0cf`). A
    version can therefore return to synced-missing only if points are lost after the
    sync. If that recurs it shows as a nonzero `versions_reset` every hour in the job's
    line. The plan adds no suppression for it, because suppression would hide a real
    fault.

12. **Gate.** The source plan requires the first reviewed live apply and its receipt
    before unattended apply. That requirement is a dependency edge on #25766, which owns
    the Live Maintenance Procedure, carried in 1.1's heading. There is no runtime gate. In
    a project the procedure missed, the ceiling holds a backlog above its volume, and a
    smaller backlog applies under the wipe bound in Decision Record 5.

Rejected:
- A config key for the ceiling or for receipt retention, which would have one value.
- A durable hold latch, or a runtime "first receipt reviewed" marker per project. Each
  adds per-project state to protect vectors, which are a rebuildable projection (Decision
  Record 5).
- Extending `GlobalPruneOutcome`, which changes the route's body and parity corpus.
- Reconciling from the operator route, which D1.1 does not ask for and which would make
  an operator prune delete vectors with no receipt review.

Implementation:

- **Split `reconcile.rs`.** Separate the printing from the work so that both paths share
  it. `build_inventory(ctx) -> anyhow::Result<Inventory>` returns the inventory.
  `apply_inventory(conn, ctx, &inventory, &mut receipt, persist) -> anyhow::Result<()>`
  runs steps 5 to 8 on a receipt value its caller builds and owns, so the confirmed
  `versions_reset` and `deleted` lists survive any error. A commit error reads
  `flag reset unconfirmed`, and a `persist` error after step 6 reads
  `receipt write unconfirmed`. The CLI path keeps steps 1 to 4 and its output, so the 2.2
  tests stay green unchanged.
- **`unattended.rs` (new).** It exposes:

  ```rust
  pub(crate) enum UnattendedOutcome {
      Clean,
      Applied { deleted_points: usize, versions_reset: usize, receipt: PathBuf },
      Held { orphans: usize, reset_symbols: usize, digest: String },
      Busy,
      Failed { error: String, deleted_points: usize, versions_reset: usize, receipt: Option<PathBuf> },
  }

  pub(crate) fn run_unattended(ctx: &Context, receipt_root: &Path) -> UnattendedOutcome
  ```

  A private `run_unattended_with(ctx, receipt_root, after_precheck: &mut dyn FnMut(), persist: &mut dyn FnMut(&Path, &ReconcileReceipt) -> anyhow::Result<()>)`
  holds the body. Its last two arguments are the test seams for a change between the
  pre-check and the lease, and for a receipt write that publishes and then fails, which
  no filesystem fault can target (source 2.2). `run_unattended` passes a no-op and
  `receipt::write_atomic`. `receipt_root` is the gobby home; the job passes
  `gobby_core::gobby_home()`.

  The sequence:
  1. No Qdrant configured on the context returns `Clean`, because there is no projection
     to reconcile.
  2. `build_inventory` with no lease. An error returns `Failed` with no receipt. Zero
     orphans and zero synced-missing versions return `Clean`. Pending classes count as no
     work, because they wait for workers or adoption.
  3. `over_ceiling(&inventory)` returns `Held` with no lease.
  4. Canonicalize `receipt_root`, join `code-index/reconcile-receipts/<project_id>/`,
     refuse a symlinked component with `receipt::no_symlinks`, and create the directory
     (Decision Record 6). An error returns `Failed` with no mutation and no receipt.
  5. Open a read-write connection and take `lease_project_lock(maintenance_try())`. `None`
     returns `Busy`.
  6. `build_inventory` again under the lease. From here on this inventory alone decides.
     No work returns `Clean`. `over_ceiling` returns `Held`.
  7. Name the receipt `<digest hex>.json`, then run `receipt::validate_location` and
     `receipt::read_existing`. A refusal returns `Failed` with no mutation.
  8. `apply_inventory` with the `persist` seam. An error returns `Failed` with the
     receipt path and the confirmed counts from the receipt value. `Ok` alone returns
     `Applied`. Every earlier `Failed` carries zero counts.
  9. After the lease drops, prune the project's receipts to the 20 newest. An error goes
     to stderr.

  `over_ceiling` compares orphan count to `max(HOLD_FLOOR, points_scanned / HOLD_DIVISOR)`
  and reset symbols to `max(HOLD_FLOOR, pg_symbols / HOLD_DIVISOR)`, with constants
  `HOLD_FLOOR = 256` and `HOLD_DIVISOR = 10`, and the keep count as `RECEIPT_KEEP = 20`.
  Reset symbols are the symbol IDs summed across every `versions` entry in the two
  synced-missing classes. It does not read a class's `symbols` output, whose unit source
  2.1 leaves open.

  `commands/vector/reconcile.rs` declares the module and re-exports the entry so that
  `crate::commands::vector::reconcile::run_unattended` resolves. `unattended.rs` makes no
  direct database call: every query stays in `reconcile.rs`, and the lease goes through
  `index_lock`. `tests/code_index/test_gcode_privilege_manifest.py` compares exact
  per-file call counts, so moving a query would need a manifest entry this leaf does not
  plan.
- **`job_prune.rs`.** Add `pub struct ReconcileTotals` (`clean`, `applied`, `held`,
  `busy`, `failed`, `deleted_points`, `versions_reset`, deriving `Default`), and give
  `prune_all` a final parameter `reconcile: Option<&mut ReconcileTotals>`. In the `active`
  branch, after `prune_project_unattended` returns `Ok` and the project is added to
  `completed`, a `Some` runs `run_unattended(&ctx, &home)` and records the outcome. A
  `gobby_home()` error counts as `failed` for that project. A private
  `record_outcome(&mut totals, project_id, outcome) -> Option<String>` adds to the totals
  and returns one line for each non-routine outcome, which `prune_all` writes to stderr.
  `Applied` and `Failed` both add their counts to `deleted_points` and `versions_reset`:
  - `code_index_reconcile: project=<id> applied deleted_points=<n> versions_reset=<n> receipt=<path>`
  - `code_index_reconcile: project=<id> held orphans=<n> reset_symbols=<n> digest=<d>`
  - `code_index_reconcile: project=<id> failed deleted_points=<n> versions_reset=<n> receipt=<path|none>: <error>`

  `Clean` and `Busy` only count. A prune error skips reconcile for that row. The reconcile
  outcome never changes the project's entry in `GlobalPruneOutcome`.
- **`jobs/prune.rs`.** Pass `Some(&mut totals)` and extend the log line to
  `code_index_prune: completed=<n> failed=<n> skipped=<n> reconcile_clean=<n> reconcile_applied=<n> reconcile_held=<n> reconcile_busy=<n> reconcile_failed=<n> deleted_points=<n> versions_reset=<n>`.
- **`family/prune.rs`.** Pass `None`. The route's behavior and body do not change.
- **Docs.** `docs/guides/code-index.md` says gdaemon's hourly job reconciles each project
  after its prune, what it applies, where its receipts live, the wipe bound, and what a
  hold means: it stops that run only, and a later inventory at or below the ceiling
  applies.
  `recovery.md` currently says apply runs only through the Live Maintenance Procedure.
  Change it to: the first apply for each project runs through that procedure; after it,
  the hourly job applies automatically; a project logged as `held` is reviewed with the
  dry-run and applied through the CLI. Its `_Version` line takes a MINOR bump from the
  version at the leaf's start, and `_Last verified` takes the leaf's date.

**Research context:**

- D1.1 says "for each project". A project that only nodes index has no hub-machine row,
  so 1.1's `active` branch never sees it. #24703 (family section 8.5) adds a node-only
  step to `prune_all`: a file pending for any of its machines completes the project with
  nothing collected, and a `live` project gets `HubScope::context` for the hub machine at
  an empty root, with `ServiceConfigSelection::projection_cleanup()`, and runs
  `commands::status::prune_content_by_age(&ctx, retention_days, Some(now + 90 s))`.
- Projections are hub-hosted (source Decision Record 1), so the inventory needs only the
  project ID and the collection. A version only another machine references drains through
  that machine's worker (source Decision Record 3), which for a node is its heartbeat
  vector sync (family section 4.3).
- `receipt::validate_location(path, root_path)` carries the retire-files check that the
  path is outside the repository root. An empty `root_path` breaks that check:
  `Path::starts_with("")` is true for every path, so every receipt would be refused. An
  empty root means the hub has no checkout for this project.
- Rejected: asking #24703 to carry this. The D1.1 obligation belongs to this plan, and a
  cross-plan wait is expressed as a dependency edge, never as a transfer of the work.

Implementation:

- **`job_prune.rs`.** In the node-only step's `live` branch, after `prune_content_by_age`
  returns `Ok`, a `Some(reconcile)` runs `run_unattended(&ctx, &home)` and records the
  outcome exactly as 1.1 does. Pending, soft-deleted, overlay and purged node-only
  projects do not reconcile.
- **`receipt.rs`.** `validate_location` skips only the repository-root comparison when
  `root_path` is empty. Every other check stays.
