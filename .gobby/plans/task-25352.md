# Hub-node sprint without ceremony: drain, push, build, review, flip, smoke

**Plan ID:** task-25352

## Overview
`kind: framing`

Josh, 2026-10-30 (memory 039886fb), verbatim: "Let's go with this suggestion.
Drain first, then push, then sprint on hub-node without the ceremony, then
review, flip, smoke test?" Task #25352 asks for this plan. It supersedes the
same day's runner-first direction. Research #25351 (535a5e79cd) is background
input only, and the #25341 cloud port comes after hub-node and stays
unexpanded.

The six steps and their sections:

1. Drain: every tree is landed and removed, and the baseline is 0.5.0 plus
   the wiki (Drain and Push).
2. Push: Josh approves the exact SHA, and the Orchestrator pushes it (Drain and
   Push).
3. Build: a build seat works the hub-node queue in one dedicated branch and
   tree, with no per-task claims and no DevTeam live review. Close gates are
   deferred to flip step 8, and independent batch review still checks every
   commit (Review Protocol). Each task gets
   one `[gobby-#N]` commit, tracked in a committed status ledger. The build
   seat's rule exemptions are declared in its agent definition (P2, P3).
4. Review: a review seat checks each task's commit against its criteria,
   starting with the first batch (Review Protocol).
5. Flip: the reviewed sprint tip lands on 0.5.0 and hub-node is switched on
   (Flip and Rollback).
6. Smoke: Josh's two-machine live smoke (#24604, #25217) records the latency
   baseline (Smoke Gate).

This plan adds only the sprint machinery: two agent definitions (P2) and the
ledger (P3). It references the existing hub-node tasks by number and orders
them. Each task keeps its own description and validation criteria, and the
review checks commits against those criteria.

## Mechanism Facts
`kind: framing`

These facts were observed in this checkout on 2026-10-30.

- Exemptions. A definition's `workflows.rule_selectors.exclude` removes rules
  from its sessions.
  - Source: `src/gobby/workflows/selectors.py::rule_matches_agent` and
    `_rule_excluded_by_agent`.
  - The engine filters rules by the session's `_agent_type`
    (`src/gobby/workflows/engine/core.py`, `_filter_by_active_rules`).
  - Claude native subagents hook under the parent's session id
    (`src/gobby/hooks/adapter_execution.py`, line 294). Exclusions therefore
    cover the seat's native subagents and its ultracode workflow agents.
  - `seat-no-spawn` blocks `gobby-agents:spawn_agent`, so neither seat has
    Gobby-spawned children. Its subagent tree is native only.
- Claim rules. `require-task-before-edit` and `require-task-before-commit`
  (`workflows/rules/task-enforcement/`) block edits, repo mutations and
  commits without a claim. A `git merge` counts as a repo mutation
  (`src/gobby/hooks/_normalization_git.py::classify_git_mutation`).
  `require-task-close` fires only while a task is claimed.
  `block-native-task-tools` gates the native tracker on a claim. Native
  subagents are exempt from it, and the sprint uses the ledger as its tracker.
- Code-review gates. `require-code-review-skill` and
  `require-code-review-self-review` carry the `default` tag, so both seats
  select them (`workflows/rules/skill-discovery/require-code-review-skill.yaml`).
  Each commit, merge, rebase, cherry-pick or revert needs the `code-review`
  skill loaded and a fresh `ocr delegate rule` call since the previous such
  operation. Documentation-only commits are ungated. A clean `--ff-only` merge
  is ungated only when every imported commit is already reachable from 0.5.0.
- Commit links. `link_commit` passes `require_claim_authority` on an
  unclaimed task for any session
  (`src/gobby/mcp_proxy/tools/task_commits.py::link_commit`).
- Step records (`src/gobby/tasks/step_records.py`):
  - The writer must hold a definition granting the step (`_writer`). No
    claim is required.
  - A step's commit must be the task's latest linked commit.
  - A review needs a session that never claimed, implemented or edited the
    task (`_require_independent_reviewer`).
  - Three rejections in one epoch need an audited reset
    (`REVIEW_REJECTION_LIMIT = 3`).
  - The project sets `task_close_policy.enforce_step_records: true` in
    `.gobby/project.json`. That requires implementation and closing records,
    plus a review record for code, docs and research tasks
    (`required_task_steps`). No test record is required.
- Close gates (`gobby:references/tasks/closing.md`): `children_closed`,
  `linked_commits`, `uncommitted_task_edits`, `integration_ancestry` and
  `step_records`. `integration_ancestry` needs every linked commit on 0.5.0,
  so sprint tasks close only after the flip. `seat-no-task-close` and
  `unassigned-session-no-task-close` block closes unless the definition
  excludes them. `close_task(preview=true)` is open to every seat.
- Landing. `land_commit` merges a reviewed, linked candidate into the main
  checkout (`src/gobby/tasks/land_commit.py::land_candidate`).
  - It requires an approved review record on the exact SHA and a caller with
    `land_tasks`.
  - When the 0.5.0 tip is an ancestor of the candidate, the landing is a
    fast-forward.
  - Paths that both the moved tip and the candidate changed, or merge
    conflicts, escalate.
- Hub mode. `hub: true` with `datastore_mode: local` is the `hub` run mode
  (`src/gobby/config/bootstrap.py::BootstrapConfig.run_mode`), and
  `gdaemon serve` registers `HubNodes` only in that mode
  (`crates/gdaemon/src/serve.rs`). `gobby datastores expose --bind <ipv4>
  --host <dns>` is the only CLI that sets `hub: true`
  (`src/gobby/cli/datastores.py::expose_datastores`). `GET /api/health`
  reports `mode`.
- Backup. `gobby hub-backup` writes `~/.gobby/backups/hub/<UTC timestamp>`
  with PostgreSQL, Qdrant, FalkorDB and the bootstrap.
  `gobby hub-backup restore <dir> --database-url <DSN> --clean` restores
  PostgreSQL. It requires a stopped daemon and an explicit DSN.
- Node bundles. `gobby node install` runs only from a signed bundle
  directory (#24865 criterion 3.2.2). A local bundle signed by Josh serves
  the smoke, and no published release is needed.

**Batch rules.**

- A batch is up to the seat's ultracode run size of queue rows. It is taken
  from the queue head. Every row's dependencies are BUILT, and the rows'
  Targets are pairwise disjoint apart from the release carriers.
- Release carriers are `Cargo.lock`, crate `Cargo.toml` version lines and
  `src/gobby/install/version_pins.py`.
- Workflow agents implement rows concurrently and never edit release
  carriers.
- The build seat applies each row's carrier edits itself, in queue order. It
  runs the row's focused verification, runs
  `ocr delegate rule --format json <row paths>` as its self-review, and then
  commits that row alone with
  `git commit --only -m '[gobby-#N] <type>: <summary>' -- <row paths>`. The
  same self-review precedes each merge and cherry-pick. Ledger commits are
  documentation-only and ungated.
- After the batch's task commits, the build seat writes one ledger commit,
  `[gobby-#L] docs: ledger batch <k>`, where #L is 3.1's task. That commit is
  the batch tip. The seat links every `[gobby-#L]` commit to #L with
  `link_commit`, so #L's latest linked commit is always its newest ledger
  commit. It then sends the review seat `BATCH <k> <tip-sha> rows: #a #b ...`.
- Per row, after its commit, the build seat calls
  `gobby-tasks:link_commit(task_id, sha)`, then
  `record_implementation_step(task_id, status="approved", epoch=<task review_epoch>, round_number=<prior rejections + 1>, commit_sha=sha, feedback=<verification commands and results>)`.
- Every task bumps its binaries per its own release-ownership criterion, so
  versions climb one patch per touching row.
- Before the rows that need it, the build seat runs
  `git merge --no-ff 0.5.0 -m '[gobby-#L] chore: merge 0.5.0 into hub-node sprint'`.
  That brings in #25357 before #24690, and refreshes the branch at each
  batch boundary when 0.5.0 has moved. The seat never rebases, so commit

### 3.1 Hub-node sprint ledger [category: docs] (depends: 2.1, 2.2)
`kind: deliverable`

Targets:
- `.gobby/plans/sprints/hub-node-ledger.md`

Research context:
- The ledger is the sprint's single status record. Its task (#L) also
  carries the flip: its last commit is the sprint tip C, which
  `land_commit(#L, C)` lands. A fast-forward brings every task commit onto
  0.5.0, which satisfies each task's `integration_ancestry` gate.
- Only the build seat writes it, and only in its own ledger commits, never
  inside a task commit. The review seat stays independent of #L.
- Verdicts come from the review seat's `REVIEW` messages, which are backed by
  `record_review_step` records.

Format:

- Header fields:
  - plan `.gobby/plans/task-25352.md`;
  - branch `hub-node-sprint`;
  - Push, the approved remote baseline;
  - base B0;
  - build seat and review seat session refs;
  - status vocabulary.
- Snapshot rule: a ledger commit records only facts known before it is
  written. It never holds its own SHA or a later verdict.
- Rows table: `Q | Task | Title | Status | Commit | Verify | Review`.
  - One row per Queue entry, in Queue order.
  - Status is one of QUEUED, BUILT, APPROVED, REJECTED(n), BLOCKED,
    FINAL-REVIEW-PENDING or POST-FLIP. POST-FLIP is for live rows.
    FINAL-REVIEW-PENDING is B00's status in every ledger commit, C included.
  - Commit is the task's latest linked commit, as 10 hex characters.
  - Verify is the build seat's exact verification command(s) and results,
    run in the pre-commit batch worktree, which may hold other rows of the
    batch. It claims no standalone row-commit verification. The independent
    run at the batch tip is the Review cell's.
  - Review is the verdict, the reviewer session ref and the batch tip the
    review ran at. A ledger commit holds only reviews completed before it,
    so batch k's reviews appear in batch k+1's ledger commit, or in C for
    the last batch.
  - B00's Commit, Verify and Review cells stay empty. Every ledger commit
    becomes #L's latest linked commit, so #L's evidence lives only in its
    step records (its batch-1 review and its review at C) and in the
    `land_commit` result. No ledger commit follows C.
- Batches table: `k | Rows | Last task commit | Date`. The batch tip, batch
  k's own ledger commit, travels only in the `BATCH` message.
- Found work: each item is either fixed inside a row, with that row named,
  or reported to Triage, with the message id. A fix inside a row lists the
  failing command, the paths outside the row's Targets, the impact and the
  ownership check.
- Flip record, written in the final ledger commit: pre-flip SHA P and backup
  path B.

## Review Protocol
`kind: framing`

Owner: the review seat.

On each `BATCH <k> <tip>`, the seat runs
`ocr delegate rule --format json <batch paths>` and then
`git merge --ff-only <tip>` in the review tree. The tip is not yet on 0.5.0,
so the code-review gate applies. Then, for each row in the batch, possibly in
one ultracode run under the usage gate:

1. Read the task with `get_task` (description and validation criteria). On a
   first review, read the row's diff with `git show <sha>`. On a repaired
   row, read every commit linked to the task, from the oldest through the
   latest, and recheck each earlier rejection finding. The latest fix alone
   is not the task's full patch.
2. Check the diff against every behavioral acceptance and verification
   criterion. Only the process evidence the Decision Record waives (claims,
   the DevTeam, the TDD red/green transcript) is waived. Name each such
   waiver in the review feedback, and waive no behavioral criterion. Touched
   paths must stay within the task's Targets, the release carriers and the
   paths in the row's ledger found-work entry. An undocumented extra path
   rejects the row. The commit subject must carry `[gobby-#N]`.
3. Run the task's focused verification commands in the review tree at the
   batch tip, on the isolated test hub.
4. Record `record_review_step` with `approved` or `rejected`, on the task's
   latest linked commit. Feedback holds the commands and results, or the
   findings.
5. Send the build seat `REVIEW <k> #N APPROVED|REJECTED <summary>`.

First-batch gate. For every batch-1 row, the seat also runs
`close_task(task_id, commit_sha, preview=true)`. Every gate except
`integration_ancestry` must pass, apart from `step_records`, which may list
only `closing` as missing (the closing record is written at close). Any other
failure stops the line: the
seat sends Triage the preview output, and the build seat starts no new batch
until the Orchestrator rules.

Rejections:

- After a first rejection, the build seat fixes the row in a later batch with
  `[gobby-#N] fix: ...`, then a new link and a new implementation record.
- After a second rejection, the row goes BLOCKED. The review seat sends
  Triage the findings, and the Orchestrator decides: a task edit, an audited
  epoch reset or dropping the row. The third rejection that exhausts an epoch
  is never reached in-sprint.

## Flip and Rollback
`kind: framing`

Flip gate. All of the following hold:

- every build row other than B00, including the precondition leaves, is
  APPROVED (B00 is approved at C in step 4);
- no row is BLOCKED;
- #25357 has landed.

Flip steps, in order:

1. Orchestrator: send a `global` heads-up and a HOLD to every Dev Manager.
   No other landing happens until step 8.
2. Activation owner: record P, the current 0.5.0 tip.
3. Build seat:
   `git merge --no-ff 0.5.0 -m '[gobby-#L] chore: merge 0.5.0 into hub-node sprint'`.
   Then write the final ledger commit with the Flip record (P, and the
   backup path B that step 6 will write). That commit is candidate C, and P
   is its ancestor. The seat links C to #L and records #L's implementation
   step on C.
4. Review seat:
   - fast-forward to C;
   - rerun every build row's verification command at C;
   - run `uv run ruff check src/`, `uv run ruff format --check src/`,
     `uv run mypy src/` and
     `uv run gobby test-types audit tests/ --baseline .gobby/test-types-baseline.json --fail-on-new`;
   - approve #L at C with `record_review_step`.
   A failure there is a REJECTED row, handled as in the Review Protocol.
5. Orchestrator: `land_commit(task_id="#L", commit_sha=C)`. This is a
   fast-forward, because P is C's ancestor and HOLD kept the tip at P.
6. Activation owner: run `uv run gobby hub-backup --output <B>`. Then, outside
   04:45 to 06:45 CT and after a `global` announcement, run
   `uv run gobby cutover` from the main checkout. Cutover proves the start
   half before stopping anything, and it promotes the binary set and gclient.
   Report DAEMON BACK.
7. Josh:
   - If `GET /api/health` does not already report `mode: hub`, run
     `gobby datastores expose --bind <tailscale-ipv4> --host <dns>` on the
     hub machine, then restart.
   - Build the node bundle from C through the release path #24858 delivers,
     and sign it with his key.
   - On the second machine, run `gobby node install --hub <url> --email <email>`
     from the bundle.
8. Orchestrator: lift HOLD. The review seat closes every build task:
   `record_closing_step`, then `close_task(task_id, commit_sha=<latest linked>, reason="done")`.
   It closes #L last. The Orchestrator then removes the sprint tree and the
   review tree, and ends both seats.

Closing at step 8, before the smoke, is required: live rows depend on these
tasks being closed.

Rollback triggers:

- the cutover's start-half proof refuses;
- the daemon is unhealthy after cutover;
- Josh rules that a smoke regression blocks the fleet.

Rollback steps:

1. Orchestrator: send a `global` announcement and HOLD.
2. Josh: stop the node service on the second machine.
3. Josh: in the main checkout, run `git reset --keep P`. It refuses rather
   than overwrite uncommitted work; if it refuses, the Orchestrator has the
   owners commit first.
4. Activation owner: run `uv run gobby cutover`, which rebuilds and promotes
   P's binary set. Only if the start-half proof refuses on schema identity:
   Josh stops the daemon, runs
   `uv run gobby hub-backup restore <B> --database-url <DSN> --clean --yes`,
   and the activation owner restarts. Data written after B is lost.
5. `hub: true` stays, because P already serves hub mode. The sprint branch
   keeps C for a fix-forward re-flip. Closed sprint tasks stay closed, and
   the re-flip lands their commits again. The ledger records the rollback in
   that re-flip's final commit.

The post-flip 0.5.0 is pushed only after the smoke verdict, with Josh
approving the exact SHA, and CI runs as usual.
