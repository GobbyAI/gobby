# Build automation

Load when starting, inspecting, coordinating, or recovering a build. Load the
operation topic before acting; this overview and menus do not satisfy its exact
reference requirement. Fetch unleased tool schemas before calls and finish every
reference cursor. Parameters and defaults belong to the registered schemas.

Build opts an existing task tree or plan into daemon-owned stage dispatch. It
does not authorize implementation, optional plan review, publication, or a new
coordinator role. Raw ideas go through the plan capability first. A help/menu
request only displays choices.

Start discovery with `gobby-tasks:get_build_status`, `explain_dispatch`, and
`list_build_history`. Inspect `get_task_stages`, `list_stages_registry`, and
`gobby-profiles:list_profiles` before deciding which operation applies. The DB
owns installed definitions; bundled files describe defaults, not active state.

Agent entrypoints are `gobby-tasks-ops:build_task`, `build_stop`, `build_resume`,
`build_clean`, and `build_restart`. Use MCP for task lifecycle and state changes;
CLI/HTTP examples in the linked guides describe operator/client interfaces.
Pass caller context on the proxy wrapper, and resolve the target project before
using project-local task or session references.

Choose `$gobby build references starting`, `profiles`, `stages`, `coordination`,
`monitoring`, or `recovery`. A failed launch is evidence to inspect, not a reason
to silently change the user's provider, stage, scope, isolation, or criteria.

and [Orchestration](../../../../../../../../docs/guides/orchestration.md#build-lifecycle).
