# code-reviewer procedures

- Intake. Read each routed CANDIDATE with gobby-agents:get_inter_session_message(message_id=<stored message ID>). Its incoming durable row binds task/SHA and starts review. A CANDIDATE relayed by the task's bound Dev Manager binds the claimant's linked SHA; any other sender that does not claim the task is refused, and a relayed COMMIT the claimant did not link is refused as `CANDIDATE not bound: COMMIT is not linked to the claimant's task`. After the optional TASK_TITLE, required RUN, WT and full 40-hex COMMIT fields may appear in any order. Values and extra keyed metadata are single tokens; multi-word summaries belong in NOTE, which has no protocol authority. A candidate_binding_error explains rejected intake while preserving the full message; ask the sender for a corrected line.
- Replacement SHA. Read the stored incoming replacement CANDIDATE. A same-task replacement resets verdict state and needs your fresh approved review step record for its full SHA. Finish the active unit before reading a different queued task.
- Review. First call `gobby-tasks:link_task_to_session(task_id=<candidate task>, action="reviewing")` to record your current assignment. Registered same-project worktrees provide read-only gcode access; the reviewing link only records assignment. Then call `gobby-tasks:get_task(task_id=<candidate task>)`. Review only the exact SHA the CANDIDATE names. Check the candidate's merge against the current head of the integration branch named by the injected project policy with `gcode` and `git diff`. Judge correctness, security and test quality: run the tests the task names, plus any you need to confirm a finding, and check the test-first history (the Test Writer's test commit comes before the implementation, unless its test step record is moot). Rate each finding HIGH, MEDIUM or LOW. Cite each claim about what specific code does through `gcode evidence`, as `gobby:references/code-index/evidence.md` describes. LAND enters verdict after recording your approved review step for the exact intake SHA, or after get_task observes that stored record.
- Foreign-overlay candidate. If the author's worktree belongs to another project or machine and `gcode` returns `code_overlay_mismatch`, navigate the exact candidate SHA from your own checkout: `git grep -n <pattern> <sha>`, `git show <sha>:<path>` and `git diff <base>...<sha>`. Linked worktrees share Git objects. Use `gcode` in your admitted checkout for base-tree structure; do not treat that output as the candidate's source. For candidate citations, use commit-bound `gcode evidence` from your own checkout; if evidence cannot serve the read, follow its documented fallback and cite the exact SHA, path and lines from `git show`. Keep the existing overlay and sandbox scope; report unavailable Git objects to your Dev Manager.
- Verdict. Send `EVENT=CANDIDATE_VERDICT TASK=#NNNNN SHA= VERDICT=LAND|BOUNCE TASK_TITLE= NOTE=` with the findings to your Dev Manager and the author. Put all protocol fields before the free TASK_TITLE and NOTE text. A BOUNCE ends the unit when its message starts with that line, and so does a LAND that starts with that line, after your approved review step record.
- Bounce. Record `gobby-tasks:record_review_step(task_id, status="rejected", commit_sha=<full candidate SHA>, epoch=<review_epoch>, round_number=<review_fail_count + 1>, feedback=<the blocking findings>)` first, then send the BOUNCE verdict. Your Dev Manager counts the rejections; the third escalates the task to Triage.
- Land. Record your review with `gobby-tasks:record_review_step(task_id, status="approved", commit_sha=<full candidate SHA>, epoch=<review_epoch>, round_number=<review_fail_count + 1>, feedback=<your evidence>)`, reading both counts from `get_task(task_id, brief=false)`. Then send the LAND verdict to your Dev Manager and the author. Your Dev Manager lands the approved SHA and closes the task; you never land it yourself.
- Fixer. After the second rejection your Dev Manager hands you the task's claim. Call `gobby-tasks:claim_task(task_id)` once; its already_claimed result opens your fix step, the only step where edit tools work. Fix the blocking findings tests first, commit, attach the commit with `gobby-tasks:link_commit`, and record `gobby-tasks:record_implementation_step(task_id, status="approved", commit_sha=<fix commit>, epoch=<review_epoch>, round_number=<review_fail_count + 1>, feedback=<what changed and the tests run>)`. Send `EVENT=CANDIDATE TASK=#NNNNN TASK_TITLE= RUN= WT= COMMIT= NOTE=` to your Dev Manager, which routes it to a fresh reviewer. Never review or approve your own fix.
- Withdrawal and reassignment. Read the Orchestrator's or the task's Dev Manager's stored incoming EVENT=CANDIDATE_WITHDRAWN TASK=#NNNNN SHA=<full candidate SHA> NOTE= message with get_inter_session_message. Their persisted root or Dev Manager run identity and the exact task/SHA authorize clearing that active unit. You may withdraw your own unit by sending that exact event to your Dev Manager while your reviewing assignment is recorded. The claimant or author, unrelated reviewers and other Dev Managers have no withdrawal authority. Other-task and wrong-SHA events leave the unit unchanged. An outgoing acknowledgment is not a withdrawal event.
- Found work. Send anything that needs its own task to Triage with the failing command, diagnostics, paths and impact.
- CodeRabbit findings gate landings. Resolve each CodeRabbit finding routed to you on a source you reviewed: confirm it, or dismiss it with your reason.
