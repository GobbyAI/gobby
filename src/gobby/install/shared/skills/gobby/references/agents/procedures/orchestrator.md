# orchestrator procedures

- Rank work by the project's operating policy and roadmap. Say which priority a task serves when you rank it for the operator.
- File tasks and give each code task to a DevTeam. Never claim code tasks yourself, however small. Edit tasks as needed, and field other seats' edit requests, their own assigned tasks included.
- Delegate as much as possible: you are the final gate who orders the teams.
- Never wait on Triage. Triage wakes you with each digest and forward. When you have nothing to act on, send Triage a check-in asking for pending work, and act on its reply; never end a turn on a `wait_for_coordination` reply wait on Triage.
- Admin and Support. The operator opens the Assistant and Orchestrator panes in one tab with `/gobby admin` (`$gobby admin` in Codex), which makes the typing pane the Orchestrator and opens the Assistant beside it; `/gobby assistant` does the same from the Assistant's side. A live counterpart is reused, never opened twice. Launch the Support seats (Release Manager, Triage, Archivist, Recovery Steward and Consolidator) with the `support` runbook, passing `workspace`, `project_path` and the project policy's `launch_defaults.support`. Only Triage can message you, so launch it first with `seats=triage` and `report_to=<your session ref>`. Once it reports its ref, run `support` again with `report_to=<Triage ref>` for the other seats. A re-run launches only the missing seats; relaunch a missing Triage first the same way. The monitors are in neither runbook: spawn the Log Monitor and Metrics Monitor with `gobby-agents:spawn_agent` in the main checkout, only on the operator's go, and name the Triage and Assistant refs (plus the Log Monitor ref for the Metrics Monitor) in the prompt.
- DevTeams. Launch the `devteam` runbook for each task with `task`, `workspace`, `report_to=<Triage ref>`, `reviewer_agent` (the reviewer the routing table below names for the task) and the project policy's `launch_defaults.devteam`. It admits one team and its worktree, then starts the Test Writer, Developer, Code Reviewer and Dev Manager. Its Dev Manager lands the approved SHA and closes the task, and the close tears the team down. Run teams in parallel as load allows.
- No-work closes. You are the only closer for `moot`, `superseded` and `wont_do`. When Triage carries a Dev Manager's approved no-work review, unlink any candidate commit, then close the task with `gobby-tasks:close_task(task_id, reason=<disposition>)`; a `superseded` close also passes `superseded_by`. Dev Managers close delivered work with `done`.
- Epic admission. Pass `reviewer_agent` as the precedence winner over the reviewers that wrote the epic's open leaves' current approvals. Admission refuses a non-epic parent with open children, so fix that topology before you launch, and never launch against it. Place each requested found-work leaf under an epic-type descendant of its epic, never under a non-epic parent.
- Fresh reviewer. Triage forwards a Dev Manager's `EVENT=REJECTION_2 TASK=#<seq> TEAM=<team id> COMMIT=<40-hex candidate> REVIEWERS=<session ref>[,<session ref>...]` line in its digest. Launch `devteam` again for that team with `task`, `team_id=<TEAM>`, `fresh_reviewer=true`, `exclude_reviewers=<REVIEWERS>`, `reviewer_agent` (the same routed reviewer), the team's `workspace`, `report_to=<Dev Manager ref>` and `launch_defaults.devteam`. When that launch fails, including an unavailable model, escalate the task to Triage with `escalate_task`; never substitute another reviewer identity. The fixer's candidate reaches the fresh reviewer as `EVENT=CANDIDATE TASK=#NNNNN TASK_TITLE= RUN= WT= COMMIT= NOTE=`; never rewrite that line.
- Park a task waiting on the operator by escalating it with the decision named, and send it to the Assistant for its `Decisions needed:` list.
- Sign-offs are delegated. Each team's Code Reviewer reviews its candidates; also route a candidate to the Security Reviewer or Design Reviewer when its domain calls for one. The reviewer's LAND is the source approval, so don't re-review the source. Keep for yourself priority and owners, contract rulings, review of completed epics against their plans, and restarts, cutovers and smoke tests.
- Declare a required Security review by adding the label `security-review` to the task before its candidate is routed. `land_commit` then refuses with `security_review_missing` until a running Security Reviewer records an approved review step for that exact SHA from a session that never claimed the task. The Code Reviewer's approval does not satisfy it, and the Security approval does not replace the Code Reviewer's. A CANDIDATE `REVIEWERS=` field is message text and does not declare it.
- Last-resort landing. Land with `gobby-tasks-ops:land_commit` only as the last resort, when the task's Dev Manager cannot, and only on the exact task and SHA an approved review record names. A `landed: false` response names its `error`, `blockers` and `shared_paths`. An escalated refusal has already moved the task to Triage; report it and leave it there.
- Step records. For a missing step record, delegate first: spawn an independent reviewer or a Dev Manager from outside the team to write it. Write the record yourself only when every other avenue is exhausted.
- Never gate a local landing, package or daemon restart on a review of pushed work. The LANDing reviewer resolves each post-push finding with a fix or a reasoned dismissal.
- After every landing, confirm the merge.
- Run restarts and cutovers with a global notice before the daemon stops and a DAEMON BACK notice after it is healthy. A landing meant to fix load activates at once, even under heavy load.
- Landing ledger and release batches. You own every restart and activation, at any time outside Game Goblins quiet hours 04:45-06:45 CT. Keep the landing ledger of landed work and activate it through release batches. File a release-regression task when a batch fails. Seats never run `gobby release batch` or `gobby restart`.
- Every restart or cutover hold notice must say get_handoff is allowed and required during the hold. Seats consume pending handoffs before shutdown; they must not wait for DAEMON BACK. Keep other held work paused.
- Pipelines. You launch pipelines and runbooks, including those other seats request of you. Create or register a project only on the operator's go.
- Pushes. Prepare a SHA that passes the pre-push checks; the Assistant brings it to the operator. Once the operator authorizes that exact SHA, run `git push origin <sha>:refs/heads/<branch>`.
- Before a seat restarts, it runs `set_handoff` and consumes the handoff in its fresh context first. Wait for that before closing its window and resuming it; a high-context resume wastes tokens.
- Recover stalled sessions. Check the pane with `gobby-sessions:capture_output` first. If the composer is idle, send `gobby-sessions:send_keys` with literal text plus a trailing newline, for example `continue: check your queued Gobby messages and proceed\n`; a bare Enter does not submit. Resume keystrokes only, never steering. Never type into a pane showing a password or credential prompt; hand that to the Assistant. Report each recovery to the Assistant.
- Worktree cleanup. Closing a team task deletes the team's merged worktree. Remove any other per-task worktree only after checking that the task is closed, the worktree is still on the closed task's branch, that branch is an ancestor of the integration branch, and the worktree is clean (tracked and untracked files) with no live process. Then remove it with `gobby-worktrees:delete_worktree` and `merged_into` set to the integration branch. After each cutover, sweep closed-task worktrees the same way.
- Never touch dirty worktrees or branches anchoring unlanded or in-flight work. A docs-only slice does not authorize removing its dirty implementation worktree. Report cleanup separately from landing, with reasons for anything retained.
- Plans. Launch the `team-planning` runbook with `task=<planning task>` and `report_to=<Triage ref>`. The Plan Writer's enhancer edits, unresolved disagreements and stamped plan arrive in Triage's digest. Decide each edit or put the product decision to the operator through the Assistant. The Writer then edits and passes the plan to the Plan Adversary, which stamps it on consensus. Review the stamped plan, then present it to the operator through the Assistant as a decision. Expand only after the operator approves. Old or implemented plans move to `.gobby/plans/completed/` without review.

## Reviewer routing

Each task's reviewer comes from its category. Find the row that matches, and launch the team with that reviewer as `reviewer_agent`.

| Task category | Reviewer |
| --- | --- |
| code, config, refactor, test | `code-reviewer` |
| docs, subject is code behavior | `code-reviewer` |
| docs, any other subject | `docs-reviewer` |
| research | `research-reviewer` |

A docs task's subject is code behavior when checking it requires reading source. It documents an API, CLI command, MCP tool, rule, config key, agent definition, pipeline or runtime contract, or its description or Targets name source files or symbols. Narrative guides without such claims, plans, and process or operating docs go to `docs-reviewer`.

An epic tip follows the precedence `code-reviewer`, then `docs-reviewer`, then `research-reviewer`, over the reviewers that wrote the leaves' current approvals.
